# llmproxy 3.0 企业集团场景说明（工作包 G）

本文是 `examples/enterprise/` 的场景文档，与 `docs/3.0-university-scenarios.md` 平行：同一套通用对象（`internal/identity` 的 claim 映射 + `internal/policy` 的 `ScopeRef`/`Entitlement`/`PolicyBundle`），换一个垂直场景。对象语义以 `docs/3.0-policy-domain.md`（A 包冻结契约）为准，分工以 `docs/3.0-agent-playbook.md` §3.G、§2.8、§2.9、§6 为准。企业侧的字段映射沿用 `docs/optimization-plan.md` §「高校与企业集团的对象映射」那张表。

**所有取值都是合成值**：主体 `uid-*`、邮箱 `@example.invalid`（RFC 2606 保留域）、手机号 `13900000000`（文档号段）、出网目标 `*.invalid`、IdP 名 `*-fake-idp`。没有真实企业账号，也没有任何网络依赖。

验证命令：

```bash
cd llmproxy && go test -race -count=1 ./examples/enterprise/...
```

本文每条断言都指向 `examples/enterprise/*.go:行` 或测试函数名；与代码不符时以代码为准并请回报主线。

## 1. 定位与边界

`examples/enterprise/enterprise.go:1-33` 的包注释就是边界声明：企业特有概念（集团、子公司、部门、项目组、客户项目、合作方）**全部**通过 claim 名单 + 范围规则 + 目录别名表表达，一个字段都不写进 `internal/`。

| 允许 | 禁止（playbook §3.G） |
|---|---|
| 在 `examples/` 内声明企业概念（集团、子公司、部门、客户项目、合作方） | 把企业字段写进 `internal/` 的 policy / identity 包 |
| 用 claim 名单 + 范围规则表达映射 | 为企业新增核心包类型或新原因码 |
| 用通用对象（`ScopeRef`/`Entitlement`/`PolicyBundle`）表达策略 | 在前端或示例里另建一套权限判定 |

一条自检，与高校示例同款：**本包对 `internal/` 只调用导出的构造函数与常量**。示例里出现 `if dept == "财务部"` 这类分支就是污染核心模型的信号。

对象映射（`docs/optimization-plan.md` 的那张表，`enterprise.go:9-15` 复述）：

| 通用对象 | 高校示例 | 企业示例 |
|---|---|---|
| Tenant | 某大学 | 集团公司（`organization` 范围 `ent-group`） |
| Department | 学院、图书馆 | 子公司 / 部门（`organization` 范围 `sub-*` / `dept-*`） |
| Team / Project | 课程、实验室 | 项目组 / 客户项目 / 成本中心（`project` 范围） |
| Identity | 教师、学生 | 员工 / 管理者 / 合作方 |
| KnowledgeScope | 课程资料、制度库 | 产品库、制度库、客户资料 |

四个文件各司其职，与高校示例一一对应：

- `enterprise.go` —— 身份侧：目录别名表 `Directory()`（`:97`）、claim 映射 `Mapper()`（`:126`）、员工画像 `employeeProfiles()`（`:149`）、合作方画像 `partnerProfiles()`（`:209`）、离线身份来源 `Providers()`（`:241`，**两个** provider）；
- `bundles.go` —— 策略侧：三层规则包 `systemBundle()`（`:86`）/ `groupBundle()`（`:122`）/ `departmentBundles()`（`:159`）/ `projectBundles()`（`:214`）与 `Bundles()`（`:256`）；
- `scenario.go` —— 运行侧：候选池 `OffersFor()`（`:108`）、装配与全链运行 `World.Run()`（`:304`）、审计投影 `AuditRow`（`:179`）；
- `scenario_test.go` —— 十条端到端断言（`:63` 起）。

**相对高校示例刻意走通的四条差异**（`enterprise.go:17-29`，每条对应一个真实的采购/合规诉求）：

1. **身份来源要分家**：员工走 `corp-oidc`，合作方走 `partner-oidc`（§5）；
2. **保底靠范围、点名靠规则**：合作方不进集团组织范围，另有一条 system 范围的显式 deny 把「碰内部模型」说成规则；
3. **数据出境**：境外区域在集团层显式 deny，路由侧的区域约束只是第二道防线；
4. **客户资料与员工手册分栏**：客户资料到 restricted，只在财务/法务的部门层发放，研发拿不到 —— 权限按**范围命中**叠加，不是按人打标签。

## 2. 身份：显示名必须先换成稳定 ID

claim 里的组织与部门是**中文显示名**（`集团`、`云服务子公司`、`财务部`、`合作方`），它们会改名、会重名，不能当授权键。`Directory()`（`enterprise.go:97-117`）登记「显示名 → 稳定范围 ID」，其余取值交给 `DefaultSlugDirectory()` 兜底（项目代号 `team-pay` 本来就编码化）。

两条刻意的设置与高校示例一致：

1. **默认只登记显示名形态**。全表登记会把目录变成第二套组织架构系统，没人及时更新，结果是解析失败率随组织调整涨；
2. **`AllowUnknown` 保持 `false`**。认不出的显示名必须报错，不能静默把中文原名当范围 ID 写进授权判定面 —— 那会让一条规则永远匹配不上，而错误报告里看起来像「策略变严了」。

`Mapper()`（`:126-142`）的映射表：

| claim | 处理 | 落到哪里 |
|---|---|---|
| `sub` | 稳定主体 | `Identity.Subject` |
| `displayName` / `name` | 只用于展示 | `Identity.DisplayName` |
| `realm_access.roles` → `roles` | 多名单按序取第一个非空 | `Principal.Roles` |
| `memberOf` → `groups` | 同上 | `Principal.Groups` |
| `projects` → `projects` | 多名单 | `PolicyContext.Project`（primary）+ project 范围 |
| `organization` | 目录换算，进 organization 范围（primary） | 范围链 |
| `department` | 目录换算，进 organization 范围 | 范围链 |
| `amr` | 认证方式 | `Identity.AuthMethods` |
| `email` / `phone` | **不读** | —— |

角色名单写两个的理由与高校侧相同：集团历史上把角色放在 `roles`，换到 Keycloak 后放到 `realm_access.roles`。只写一个名字的话，切换 IdP 那天解析会**静默**产出「无角色身份」。

**集团与子公司/部门同属 organization 一种范围**（`enterprise.go:60-74`）：内核只有一种组织范围，两档对应高校的「本校 + 学院」—— 集团层（`ent-group`）发基线，子公司/部门层（`sub-cloud`/`dept-*`）发各自的模型与知识栏位。上表里 `organization` 与 `department` **两条规则都映射到 `ScopeOrganization`**，只是 `organization` 标了 primary。

范围链的展开顺序（实测到的形态，`TestPolicyVersionIsScopedToChain` 钉住）：链是一个**按 (kind, id) 排序的集合**，不是树 —— 没有任何自动的祖先层级展开，claims 声明了几个范围就加几个：

```
# 员工 1001（集团 / 云服务子公司）
organization:ent-group,organization:sub-cloud,project:team-pay,user:uid-emp-1001
corp-group-default@3|sub-cloud-default@1|legacy-batch-retired@2|corp-system@1

# 研发 4001（集团 / 研发中心，同时在两个项目）—— 项目范围按 id 排序
organization:dept-rnd,organization:ent-group,project:client-acme,project:team-pay,user:uid-rnd-4001
dept-rnd-default@1|corp-group-default@3|client-acme@1|legacy-batch-retired@2|corp-system@1

# 合作方 7001（对方组织，只进 ACME 一个项目）
organization:partner-org,project:client-acme,user:uid-partner-7001
client-acme@1|corp-system@1
```

`partner-org` 这一档不是业务概念，是 `Principal.Validate` 的硬要求：有 project 就必须有 organization（`internal/identity/principal.go`），否则上下文直接不合法。合作方落在**自己的**组织范围里，因此集团层发的规则对他们天然缺席（§3）。

版本串必须**先按范围过滤再取**（`scenario.go:314`，`w.Bundles.Filter(principal.Chain)`）。拿全集版本进审计，等于写下「生效规则里包含与本次请求无关的包」。注意合作方的版本串里**没有** `corp-group-default`（`TestPolicyVersionIsScopedToChain:407`）—— 他没进集团范围，集团包对他不生效，也不该出现在他的审计里。

## 3. 策略：规则包与层级

`Bundles()`（`bundles.go:256`）装载九个包，层级越高越宽、层级越低越具体：

| 包（作用域） | 版本 | 发放什么 | 关键点 |
|---|---|---|---|
| `corp-system`（system） | 1 | 全员基线 `corp-lite`≤internal；员工手册可读；一条**通配原文出网 allow**；两条合作方 deny | 通配那条是故意的错配示范，见 §5；deny **刻意不写 Scope**（见下） |
| `corp-group-default`（organization:ent-group） | 3 | 员工 `corp-general`≤confidential；境内合规云 `frontier-cloud-cn`；处理器 `corp-dlp`；管理者原文授权（用途绑定 + 90 天）；**deny 全员用境外部署** | 每条组织级规则都带 `Scope`，防止跨集团同名角色蹭授权 |
| `dept-finance-default`（organization:dept-finance） | 1 | 财务模型 `corp-finance`≤restricted；客户资料可读 | 客户资料的正规出口之一 |
| `dept-legal-default`（organization:dept-legal） | 1 | 客户资料 + 制度库可读 | 客户资料的另一个出口 |
| `dept-rnd-default`（organization:dept-rnd） | 1 | 代码模型 `corp-code` + 产品库，发给 `group:rnd` | 按**组**发，实习生够不着 |
| `sub-cloud-default`（organization:sub-cloud） | 1 | 子公司自有模型 `cloudops-assist` | 证明第二档组织范围同样能独立发资源 |
| `client-acme`（project:client-acme） | 1 | 客户助手 `acme-assist`（**带 `source: corp-oidc` 条件**）+ 交付资料可读 | 来源条件的落点，见 §5 |
| `cc-finance-2026`（project:cc-finance-2026） | 1 | 点名授权：`uid-fin-3001` 可用 `pilot-longcontext`，180 天期限 | 点名主体压过组级 allow；**永不过期的点名授权等于后门** |
| `legacy-batch-retired`（project:team-pay） | 2 | `uid-emp-1001` 可用 `legacy-batch`，**授权带过去的 `ExpiresAt`** | 「策略过期」与「压根没配」是两个原因码，必须分开钉 |

主体选择器的取舍口径（`bundles.go` 注释里逐条写明）：角色与组吃 IdP claim 原值，改名就漂移；组织与项目吃结构化范围，才是能长期授权的键。因此集团级规则用 `role:`/`group:` + `Scope=organization:ent-group`（角色名 + 范围两道），子公司/部门级用同组织的 Scope，项目级用 `project:` 选择器。

**两条 deny 的写法差异是要点**：

- 数据出境那条（`bundles.go:148-151`）写 `Subject: "*"` + `Scope: organization:ent-group` —— 它管的是「从集团网络里发出的请求」，合作方自带网络，不在这一层；
- 合作方那条（`bundles.go:103-110`）写 `Subject: "group:contractors"` 且**不写 Scope** —— 因为合作方不在集团组织范围里，加了 `Scope` 就永远不生效，等于把最该看得见的一条禁令藏起来。范围缺席本身已经挡住了他们，这条 deny 是把它从「恰好没配」变成「一条规则」。

## 4. 判定矩阵（e2e 的第一组断言）

`TestScenarioDecisionMatrix`（`scenario_test.go:63`）跑 18 个场景。下面只列结论，实现细节见测试表：

| 主体 / 模型 | 结论 | 原因码 | 这条在证明什么 |
|---|---|---|---|
| 员工 / `corp-lite` | 允许 | `group_allow` | 集团基线 |
| 员工（internal→confidential）/ `corp-lite` | 拒绝 | `data_level_denied` | 档位收紧是 allow 的条件 |
| 合作方 / `corp-lite` | 拒绝 | `model_not_allowed`（链上带 `deny_rule`） | 范围缺席 + 显式 deny 都成立 |
| 合作方 / `corp-general` | 拒绝 | `model_not_allowed` + `deny_rule` | 组织层模型他们够不着，另有规则说清楚 |
| 员工（confidential）/ `corp-general` | 允许 | `group_allow` | `role:employee` + 集团范围的限档 |
| 员工（restricted）/ `corp-general` | 拒绝 | `data_level_denied` | 上限之上没有兜底 |
| 员工 / `frontier-cloud-cn` | 允许 | `group_allow` | 集团层境内合规云 |
| 员工 / `frontier-cloud-global` | 拒绝 | `model_not_allowed` + `deny_rule` | 数据不出境是第一道防线，路由区域约束只是第二道 |
| 员工 / `cloudops-assist` | 允许 | `group_allow` | 子公司层按组织范围发放 |
| 管理者 / `cloudops-assist` | 拒绝 | `model_not_allowed` | 不在 `sub-cloud` 范围里，蹭不到 |
| 研发 / `corp-code` | 允许 | `group_allow` | 部门层发给 `group:rnd` |
| 实习生 / `corp-code` | 拒绝 | `model_not_allowed` | 在部门范围里但**不在 `group:rnd`**，组与范围是两个维度 |
| 财务（restricted）/ `corp-finance` | 允许 | `group_allow` | 财务模型可到 restricted |
| 研发 / `corp-finance` | 拒绝 | `model_not_allowed` | 缺席即否，不是「按部门猜」 |
| 财务 / `pilot-longcontext` | 允许 | `explicit_allow` | 点名授权压过组级 |
| 员工 / `legacy-batch` | 拒绝 | `entitlement_expired` | 授权配过、过期了 |
| 管理者 / `legacy-batch` | 拒绝 | `model_not_allowed` | 对他是「压根没配」，与上一条是两个结论 |
| 员工 / `no-such-model` | 拒绝 | `model_not_allowed` | 目录外的名字没有默认放行 |

每个拒绝用例都额外断言**上游调用增量为 0**（`scenario_test.go:127` 用 `callsBefore` 比对，因为 `World` 在子用例间复用），并断言审计里没有上游响应事实（`Status==0 && !HasUsage`）。被拒的请求「计划给不出」是结论，「发出去了」才是事故。

`TestCustomerDataStaysInFinanceAndLegal`（`:179`）补上客户资料的分栏边界：财务与法务都能读 `corp-customer`，研发**读不到** —— 同一个人可以同时在研发中心与某客户项目组，权限按范围命中叠加，客户资料只在财务/法务的部门范围里发放。

## 5. 来源条件：同一个范围，两种身份来源

这是企业示例最该钉死的一条，也是 §0.3 让 `identity_source` 落库的直接动机。

`rnd-4001`（集团自签，`corp-oidc`）与 `partner-7001`（对方签发，`partner-oidc`）**都**落在 `project:client-acme` 范围内。`client-acme` 包里那条 `acme-assist` 授权带一个条件 `source: corp-oidc`（`bundles.go:221-224`），于是同一个范围命中、两种来源给出**相反结论**：

| 主体 | 模型 | 结论 | 原因链 | 审计里的 `identity_source` |
|---|---|---|---|---|
| 研发 4001（corp-oidc） | `acme-assist` | 允许 | `group_allow` | `corp-oidc` |
| 合作方 7001（partner-oidc） | `acme-assist` | 拒绝 | `condition_unmet` | `partner-oidc` |
| 两边 | `acme-spec`（交付资料） | 允许 | —— | —— |

`TestIdentitySourceSeparatesSameScope`（`scenario_test.go:143`）三段断言：

1. 员工在 ACME 项目里能用客户助手，且 `Audit.Source == corp-oidc`；
2. 合作方在同一项目范围内**拿不到**客户助手，且原因链里必须是 `condition_unmet`（**指认来源条件本身**，而不是一句笼统的 `model_not_allowed`）；
3. 交付资料 `acme-spec` **不**加来源条件，两边都读得到 —— 项目文档本来就该给项目里的人看，来源条件只加在需要它的那一条规则上。

为什么这条推动了 §0.3：事后拿到一条「某人用了 `acme-assist`」的记录，必须能回答**他当时是不是集团自签身份**。范围链相同、判定结论相反，唯一能事后区分两者的就是那条 `requests.identity_source`。

`source:` 条件的求值口径一字未动（§0.3 只补耐久副本）：`policy.CondSource` 在 `rule.conditionsMet` 里按 `ctx.Identity.Source != want` → `ReasonConditionUnmet` 求值。当唯一命中的 allow 条件不满足时该规则不生效，模型资源回落成主原因 `model_not_allowed`、原因链里保留 `condition_unmet`。

## 6. 原文出网：授权怎么贯通整条链

§2.9 规则 4 要求原文授权同时具备：组级以上主体、绑定范围、自带期限；用途走 `Conditions.purpose` 精确相等。`corp-group-default` 里那条三样齐备，且只绑 `internal-eng`（`bundles.go:141-146`）。

`TestRawBodyGrantReachesProcessor`（`scenario_test.go:202`）分三段断言：

1. **管理者 + 内部工程用途 + 原文型 sidecar**：`Result.IsRawBodyAllow=true`，sidecar 收到的投递文档 `content_mode=raw` 且正文里手机号**在**（`w.Sink.lastBody`），而发往上游的正文里手机号**不在**（`Result.Sent`）。原文授权只放开「给 sidecar 的那一份」。
2. **换一个用途**（`customer-support`）：处理器 `PipelineErr` 里带出 `raw_body_grant_missing` —— 授权按用途精确绑定，不能沿用内部工程的。
3. **普通员工**不是 `group:managers`：`IsRawBodyAllow=false` 且 sidecar 必须 fail-closed。系统包那条通配 allow 对他生效，但 `AllowsRawBody` 只认显式与组级授权，**通配 allow 不算授权**。这就是合规演练里最常见的错配：有人以为写了全局 allow 等于授权。

顺序也有讲究：原文型 sidecar 排在 `corp-pii-mask` **之前**（`processorNames()`，`scenario.go:479`），否则它读到的是掩码文，那份授权等于白配；默认链不带它，普通 sidecar 收 `content_mode=masked`。`AllowRawBody` 不因「这次没授权」而降为 false —— E 包规定无授权即失败，降级成摘要会把合规缺口伪装成请求成功。

**已知取舍（必须让人看见，不要藏）**：范围授权会落到范围内**每一个**成员。校内若要收紧，正确写法是给那条授权再加 `Conditions.role=manager`，而不是把整条链改成按主体硬编码。

## 7. 路由：候选池、排除原因、确定性

`OffersFor()`（`scenario.go:108`）给每个下游模型名固定四家候选，档序「集团私有化集群主/备 → 境内合规云 → 境外云」：

| provider | 执行器 | 区域 | 可承载分级 | 档 | 权重 | 健康 | 价目 |
|---|---|---|---|---|---|---|---|
| `corp-vllm-a` | vllm | corp-dc1 | confidential | 0 | 3 | 是 | 是 |
| `corp-vllm-b` | vllm | corp-dc2 | internal | 0 | 1 | 是 | 是 |
| `frontier-cloud-cn` | http-compat | cn-east | internal | 1 | 2 | 是 | 是 |
| `frontier-cloud-global` | http-compat | us-west | public | 2 | 5 | 是 | 是 |

写死档序与权重，`fixed-order` 的回放断言才有唯一答案。境外那家**健康**但被策略 deny，用来证明「能不能路由」与「准不准用」是两件事。

`TestCandidateExclusionsAreVerifiable`（`scenario_test.go:313`）钉住排除各有原因码，而不是一句「没候选」（§6）：

| 场景 | 首选 | 被排除的候选与原因码 |
|---|---|---|
| `Regions=["cn-east"]` | `frontier-cloud-cn` | 集团两家 `candidate_region_excluded` |
| internal 请求（默认） | `corp-vllm-a` | `frontier-cloud-global` = `candidate_level_excluded` |

`TestRoutingIsDeterministicAndReplayable`（`:246`）钉 §2.8：`routing_seed = H(request_id ‖ policy_version ‖ routing_epoch)`，同输入两次 seed 相同、候选次序相同；把 `Result.Replay` 交给 `routing.Replay()` 能独立复原同一份计划并返回 64 位十六进制的候选摘要；换 `request_id` 必须换 seed。

`TestStickyKeepsPrimary`（`:285`）钉粘性两面：会话内钉住 `corp-vllm-b` 就不漂移；钉到一家被策略禁止的候选（`frontier-cloud-global`）时必须换，不能硬粘。

`TestPlanProcessorChainMatchesPipeline`（`:413`）钉「计划里写的链」与「实际装配的链」是同一份。

## 8. 执行器与审计

执行器按候选声明的名字取实现（`executorFor()`，`scenario.go:504`）：`vllm` / `http-compat`，未注册的名字回落到确定性 fake（`:511-513`）。两类都注入同一个假传输 `w.Upstream`（`fakeTransport`，`:74`）：**注入 RoundTripper 而不是起监听**，这样请求编码、逐跳头过滤、`CheckRedirect` 与生产完全相同，只有「拨号」这一步被替换。

### 8.1 哪些是 fake，哪些已经就是生产那一套

这份示例是**判定与选路的可执行基线**，不是出网基线。逐面标清楚，免得读的人把「示例跑通了」当成「这类执行器线上也有」：

| 面 | 示例里的实现 | 性质 | 与生产的差距 |
|---|---|---|---|
| 执行器实现 | `executor.NewVLLM` / `NewHTTPExecutor`（`scenario.go:508-510`） | **就是生产那一套**：都返回 `*executor.HTTPExecutor`，只是协议形态不同（`openai_chat` / `ollama_native`，`internal/executor/local.go:35-64`，`NewHTTPExecutor` 在 `internal/executor/http.go:75`） | 零差距，被替换的只是下一行的传输 |
| 出网传输 | `fakeTransport`（`:74`） | **假** | 一次真实拨号都不发；合成目标全部用 `.invalid`（`:59-63`），换成真客户端也解析不出地址 |
| 未注册执行器名 | `executor.NewFake`（`:513`） | **假**，且**只允许在示例里出现** | 生产注册表里未注册的名字是**拒候选、不出网**，不是回落 fake |
| 身份来源 | `Providers()` 离线画像（`enterprise.go:241`） | **假**（合成 claim） | 迁移要换成真实 OIDC 字段名，映射表本身不动 |
| 上游响应正文 | `SampleReply`（`:50`） | **假** | 只用来证明结果过滤链有东西可滤 |
| 审计落盘 | `AuditRow`（`:179`） | **假 sink**（真实 sink 归 H 包） | 结构体语义（无正文字段、只留 `body_sha256`/`body_bytes`）与生产一致 |

一句话口径：**示例里唯一不能带进生产的是「未注册名字回落 fake」这一条**。其余都是同一批对象与同一份实现，只是把拨号那一层换掉了。这条边界不是靠约定守住的，是靠源码扫描守住的：`TestExecutor30FakeExecutorStaysOutOfProductionCode`（`internal/server/executorwiring_test.go`）遍历 `cmd/`、`internal/`、`examples/` 下所有非测试文件，命中 `executor.NewFake` / `executor.Fake*` 的路径只允许落在 `examples/university/` 与 `examples/enterprise/` 内。

对照生产侧当前注册的那一个名字：网关注册表今天只有 `http-openai` → `openai_chat`（`internal/server/executor30.go`），因此本示例的四家候选里，只有 `frontier-cloud-cn` / `frontier-cloud-global` 走的 `http-compat` 在**协议形态**上能对上生产已注册的那一条；`vllm` 形态虽然 `internal/executor` 已实现，注册进生产需要配置面新增声明（§2.7 规则 4 的口径），不在示例侧顺手加。

`AuditRow`（`:179`）是审计**投影**（真实 sink 归 H 包），结构体里没有正文字段：正文只以 `body_sha256` 与 `body_bytes` 出现。字段里有一条是 §0.3 落地的耐久副本：

```go
Source string `json:"identity_source"` // §0.3：这次按哪个身份来源判的
```

`TestAuditRowCarriesNoBodyOrPII`（`scenario_test.go:350`）直接序列化审计行并断言 `13900000000`、`employee-1001@example.invalid`、`sk-corpsyntheticcredential00`、`请联系` 一个都不出现；同时断言摘要长度 64、`body_bytes`/`content_bytes` 都非零、候选侧事实（provider / executor / tier）齐全、`policy_version` 与 `routing_seed` 能回指当时，并且 `Source` 非空（§0.3）。

响应侧也有过滤链：`SampleReply` 里同时埋了手机号与合成凭证，`corp-result-filter` 把它们换成 `[phone-redacted]` / `[credential-redacted]`。

时间全部钉在 `BaseNow = 2026-03-01T08:00:00Z`（`enterprise.go:46`），fixture 的签发时刻与两个 `FakeProvider` 的内部时钟共用这个基准。用墙钟的话，同一个用例在跨过 TTL 边界时会改变结论，回放断言当场失去意义。

## 9. 怎么把它接到真实网关上

示例自带的运行器是**装配顺序的可执行基线**，不是最终接线器（那是 H 包）。迁移时按这个顺序：

1. `identity`：把 `Mapper()` 的 claim 名单换成企业内部 OIDC 真实字段名，`Directory()` 换成从企业目录服务同步的别名表，`AllowUnknown` 保持关闭；**两个来源要各自配一个 provider**（`Providers()` 示范了拓扑：员工与合作伙伴从不同 IdP 登录），否则 `source:` 那一列永远只有一个取值；
2. `policy`：把规则包写成策略包文件放进 `policy.bundles_dir`，`bundle()` 的版本戳补齐逻辑不要省（漏了 `Version` 的规则会在版本串里与真实内容脱钩）；
3. `routing`：候选池来自 provider 配置，`RoutingEpoch` 在池子或权重变化时 +1；
4. `processor` / `executor`：链名与处理器版本在注册期绑定，出网目标必须走 `AllowedEndpoints` 白名单并由接线方注入客户端；候选里的执行器名要换成**本网关注册表里存在的名字**（今天只有 `http-openai`，见 §8.1），未注册名在生产是「拒候选、一次都不出网」，不是示例那样的回落 fake —— 这条差异是迁移时最容易照抄错的一处；
5. 先 `mode: shadow` 跑差异报告，再 enforce —— 示例的判定与线上判定走同一个 `policy.Resolver`，影子期的差异才是策略差异，不是实现差异。

**落库相关的一条额外要求**（§0.3）：迁移时 `requests.identity_source` 这一列要真的被写侧填上（`internal/server/policy30.go:376` 把 `idn.identity.Source` 落进 `shot.idSource`，再由 store 写进记录），否则 §5 那条「事后问出当时按哪个来源判的」在真库里问不出来 —— 示例里它只是投影字段，耐久副本归 H 包。
