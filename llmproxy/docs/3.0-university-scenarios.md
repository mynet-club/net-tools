# llmproxy 3.0 高校场景说明（工作包 G）

本文是 `examples/university/` 的场景文档：一套真实租户怎么只用**通用对象**（`internal/identity` 的 claim 映射 + `internal/policy` 的 `ScopeRef`/`Entitlement`/`PolicyBundle`）把 3.0 的六层拼起来。对象语义以 `docs/3.0-policy-domain.md`（A 包冻结契约）为准，分工以 `docs/3.0-agent-playbook.md` §3.G、§2.8、§2.9、§6 为准。

**所有取值都是合成值**：主体 `uid-*`、邮箱 `@example.invalid`（RFC 2606 保留域）、手机号 `13800000000`（文档号段）、出网目标 `*.invalid`。没有真实学校账号，也没有任何网络依赖。

验证命令：

```bash
cd llmproxy && go test -race -count=1 ./examples/university/...
```

本文每条断言都指向 `examples/university/*.go:行` 或测试函数名；与代码不符时以代码为准并请回报主线。

---

## 1. 定位与边界

| 允许 | 禁止（playbook §3.G） |
|---|---|
| 在 `examples/` 内声明高校概念（学生、学院、课程、实验室、科研组） | 把高校字段写进 `internal/` 的 policy / identity 包 |
| 用 claim 名单 + 范围规则表达映射 | 为高校新增核心包类型或新原因码 |
| 用通用对象（`ScopeRef`/`Entitlement`/`PolicyBundle`）表达策略 | 在前端或示例里另建一套权限判定 |

一条自检：**本包对 `internal/` 只调用导出的构造函数与常量**。如果哪一天示例里出现了 `if dept == "计算机学院"` 这类分支，就是污染了核心模型的信号。

三个文件各司其职：

- `university.go` —— 身份侧：目录别名表 `Directory()`（`:66`）、claim 映射 `Mapper()`（`:92`）、六份画像 `Profiles()`（`:119`）、离线身份来源 `Provider()`（`:174`）；
- `bundles.go` —— 策略侧：五个层级的规则包与 `Bundles()`（`:236`）；
- `scenario.go` —— 运行侧：候选池 `OffersFor()`（`:108`）、装配与全链运行 `World.Run()`（`:291`）、审计投影 `AuditRow`（`:180`）。

## 2. 身份：显示名必须先换成稳定 ID

claim 里的组织与院系是**中文显示名**（`本校`、`计算机学院`、`第七实验室`），它们会改名、会重名，不能当授权键。`Directory()`（`university.go:66-90`）登记「显示名 → 稳定范围 ID」，其余取值交给 `DefaultSlugDirectory()` 兜底（课程号 `CS101` → `cs101` 本来就编码化）。

两条刻意的设置：

1. **默认只登记显示名形态**。全表登记会把目录变成第二套课程数据库，没人及时更新，结果是解析失败率随学期涨；
2. **`AllowUnknown` 保持 `false`**。认不出的显示名必须报错，不能静默把中文原名当范围 ID 写进判定面——那会让一条规则永远匹配不上，而错误报告里看起来像「策略变严了」。

`Mapper()`（`:92-110`）的映射表：

| claim | 处理 | 落到哪里 |
|---|---|---|
| `sub` | 稳定主体 | `Identity.Subject` |
| `displayName` / `name` | 只用于展示 | `Identity.DisplayName` |
| `realm_access.roles` → `roles` | 多名单按序取第一个非空 | `Principal.Roles` |
| `memberOf` → `groups` | 同上 | `Principal.Groups` |
| `researchProjects` → `projects` | 多名单 | `PolicyContext.Project`（primary） |
| `organization` | 目录换算，进 organization 范围（primary） | 范围链 |
| `department` | 目录换算，进 organization 范围 | 范围链 |
| `projects` / `course` / `lab` | 进 project 范围 | 范围链 |
| `amr` | 认证方式 | `Identity.AuthMethods` |
| `email` / `phone` | **不读** | —— |

角色名单为什么要写两个：校内 IdP 历史上把角色放在 `roles`，新版 Keycloak 放在 `realm_access.roles`。只写一个名字的话，切换 IdP 那天解析会**静默**产出「无角色身份」，靠角色匹配的规则全部失效。

范围链的展开顺序（测试里实测到的形态，`TestPolicyVersionIsScopedToChain` 钉住）：院系 → 组织 → 项目 → 主体，策略版本串按同序排列并以系统包收尾：

```
# 学生 1001
organization:cs-college,organization:university,project:cs101,user:uid-stu-1001
cs-college-default@1|university-default@3|cs101-course@1|campus-system@1

# 交流生 5001（主组织是合作院校，只选了 CS101 的课）
organization:ee-college,organization:partner-institute,project:cs101,user:uid-exg-5001
cs101-course@1|campus-system@1
```

版本串必须**先按范围过滤再取**（`scenario.go` 里 `w.Bundles.Filter(principal.Chain)`）。拿全集版本进审计，等于写下「生效规则里包含与本次请求无关的包」。

## 3. 策略：五层规则包

`Bundles()`（`bundles.go:236`）装载七个包，层级越高越宽、层级越低越具体：

| 包（作用域） | 版本 | 发放什么 | 关键点 |
|---|---|---|---|
| `campus-system`（system） | 1 | 全员可读公开知识库；一条**通配原文出网 allow** | 那条通配是故意的错配示范，见 §5 |
| `university-default`（organization:university） | 3 | 学生基线 `campus-lite`≤internal；教师 `campus-general`≤confidential；职工岗可读仪器日志；教师可调 sidecar 处理器；**deny 学生用 `campus-restricted`**；**deny 全员用境外部署** | 每条组织级规则都带 `Scope`，防止合作院校同名角色蹭授权 |
| `cs-college-default`（organization:cs-college） | 1 | 院系自有模型 `cs-code-review`≤internal | 主体选择器写 `organization:cs-college`，不写中文组名 |
| `cs101-course`（project:cs101） | 1 | 课程模型 + 课件库 | 选课即入范围 |
| `cs305-course`（project:cs305） | 2 | 课程模型 + 原文授权，**两条都带过去的 `ExpiresAt`** | 「策略过期」与「压根没配」是两个原因码，必须分开钉 |
| `lab7-research`（project:lab7） | 1 | 受限模型、实验笔记库、**用途绑定的原文出网授权（带期限）** | 高危授权只在这一层发放 |
| `grant-2026`（project:proj-grant-2026） | 1 | 点名授权：`uid-pi-3001` 可用 `pilot-reasoning`，带 90 天期限 | 点名主体压过组级 allow；**永不过期的点名授权等于后门** |

主体选择器的取舍口径（`collegeBundle`/`labBundle` 注释里各写了一条）：角色与组吃 IdP claim 原值，改名就漂移；组织与项目吃结构化范围，才是能长期授权的键。因此院系级规则用 `organization:cs-college`，实验室级用 `project:lab7`——后者还专门避开了 `PolicyContext.Project`：链上的 `lab7` 来自 `lab` claim，而 PI 的 primary project 是另一个项目，只有链上命中才能让「不在主归属也依然有效」的项目级授权成立。

## 4. 判定矩阵（e2e 的第一组断言）

`TestScenarioDecisionMatrix` 跑 17 个场景。下面只列结论，实现细节见测试表：

| 主体 / 模型 | 结论 | 原因码 | 这条在证明什么 |
|---|---|---|---|
| 学生 / `campus-lite` | 允许 | `group_allow` | 全校基线 |
| 学生（internal→confidential，任一路） | 拒绝 | `data_level_denied` | 分级由 `Conditions.max-data-level` 挡，且**检测器抬档与用户自报同等有效** |
| 学生 / `campus-restricted` | 拒绝 | `model_not_allowed`（链上带 `deny_rule`） | deny 压过一切 allow |
| 研究生助理（lab7 成员）/ `campus-restricted` | 拒绝 | `model_not_allowed` + `deny_rule` | **deny 不看层级高低**：实验室层的 allow 压不过全校层的 deny |
| 学生 / `cs101-tutor` | 允许 | `group_allow` | 选课即入范围 |
| 学生 / `cs305-tutor` | 拒绝 | `model_not_allowed` | 没选过 = 规则缺席 |
| 教师 / `cs305-tutor` | 拒绝 | `entitlement_expired` | 结课即回收，且与「缺席」是两个码 |
| 教师（confidential）/ `campus-general` | 允许 | `group_allow` | 教师上限 |
| 教师（restricted）/ `campus-general` | 拒绝 | `data_level_denied` | 上限之上没有兜底 |
| 教师 / `cs-code-review` | 允许 | `group_allow` | 院系层按组织范围发放 |
| PI / `pilot-reasoning` | 允许 | `explicit_allow` | 点名授权档位 |
| 交流生 / `campus-lite` | 拒绝 | `model_not_allowed` | 跨组织蹭不到本校组织层授权 |
| 交流生 / `cs101-tutor` | 允许 | `group_allow` | 课程层是按范围发的，与主组织无关 |
| 教师 / `foreign-frontier` | 拒绝 | `model_not_allowed` + `deny_rule` | 数据不出境是第一道防线，路由区域约束只是第二道 |
| 实验员 / `campus-lite` | 拒绝 | `model_not_allowed` | 基线只发给 `role:student` 等名单，缺席即否 |
| 任意 / `no-such-model` | 拒绝 | `model_not_allowed` | 目录外的名字没有默认放行 |

每个拒绝用例都额外断言**上游调用增量为 0**（`TestScenarioDecisionMatrix` 用 `callsBefore` 比对，因为 `World` 在子用例间复用）。被拒的请求「计划给不出」是结论，「发出去了」才是事故。

`TestDenyIsScopedToItsResource` 补上 deny 的作用域边界：研究生助理在 `campus-restricted` 上被 deny，但同一主体在同一范围内读 `lab7-notes` 仍然 `group_allow`。**deny 只压它点名的那个资源**。把「模型被 deny」实现成「该主体在 lab7 内一律否」的过度拒绝，在影子期差异报告里长得像「新策略更严了」，很容易被当成预期结果放过。

## 5. 原文出网：一条授权怎么贯通整条链

§2.9 规则 4 要求原文授权同时具备：组级以上主体、绑定范围、自带期限；用途走 `Conditions.purpose` 精确相等。`lab7-research` 里那条三样齐备，且只绑 `research-writing`（`bundles.go:197-219`）。

`TestRawBodyGrantReachesProcessor` 分三段断言，任何一段单独看都可能是另一段的巧合：

1. **PI + 科研写作 + 原文型 sidecar**：`Result.IsRawBodyAllow=true`，sidecar 收到的投递文档 `content_mode=raw` 且正文里手机号**在**（`w.Sink.lastBody`），而发往上游的正文里手机号**不在**（`Result.Sent`）。原文授权只放开「给 sidecar 的那一份」。
2. **换一个用途**（`purpose=chat`）：处理器 `PipelineErr` 里带出 `raw_body_grant_missing`——授权按用途精确绑定，不能沿用科研组的。
3. **教师**（系统包那条通配 allow 对他生效）：`IsRawBodyAllow=false`。`AllowsRawBody` 只认显式与组级授权，**通配 allow 不算授权**。这就是合规演练里最常见的错配：有人以为写了全局 allow 等于授权。

顺序也有讲究：原文型 sidecar 排在 `pii-mask` **之前**（`processorNames()`，`scenario.go:465`），否则它读到的是掩码文，那份授权等于白配；默认链不带它，普通 sidecar 收 `content_mode=masked`。`AllowRawBody` 不因「这次没授权」而降为 false——E 包规定无授权即失败，降级成摘要会把合规缺口伪装成请求成功。

**已知取舍（必须让人看见，不要藏）**：范围授权会落到范围内**每一个**成员。测试里研究生助理（学生角色）在 `research-writing` 用途下同样拿到原文授权（`TestDenyIsScopedToItsResource` 断言了这条）。这不是 bug，是范围授权的既定代价——「不是 PI 就自动没有原文」是不成立的想当然。第二道防线只能是同层的模型 deny 与分级门，实例就是上一段那条 deny。校内若要收紧，正确写法是给那条授权再加 `Conditions.role=teacher`，而不是把整条链改成按主体硬编码。

## 6. 路由：候选池、排除原因、确定性

`OffersFor()`（`scenario.go:108`）给每个下游模型名固定五家候选，档序「校内 vLLM 主/备 → 无价目本地小模型 → 境内云 → 境外云」：

| provider | 执行器 | 区域 | 可承载分级 | 档 | 权重 | 健康 | 价目 |
|---|---|---|---|---|---|---|---|
| `campus-vllm-a` | vllm | campus-dc1 | confidential | 0 | 3 | 是 | 是 |
| `campus-vllm-b` | vllm | campus-dc2 | internal | 0 | 1 | 是 | 是 |
| `campus-ollama-mini` | ollama | campus-lab | internal | 1 | 1 | 是 | **否** |
| `frontier-cloud-cn` | http-compat | cn-east | internal | 2 | 2 | 是 | 是 |
| `frontier-cloud-us` | http-compat | us-west | public | 2 | 5 | **否** | 是 |

写死档序与权重，`fixed-order` 的回放断言才有唯一答案。

`TestCandidateExclusionsAreVerifiable` 钉住三类排除各有原因码，而不是一句「没候选」（§6）：

| 场景 | 首选 | 被排除的候选与原因码 |
|---|---|---|
| `Regions=["cn-east"]` | `frontier-cloud-cn` | 校内三家 `candidate_region_excluded` |
| `Objective=cheapest` | `campus-vllm-a` | `campus-ollama-mini` = `candidate_cost_unknown`（无价目不能当零成本参与） |
| internal 请求（默认） | `campus-vllm-a` | `frontier-cloud-us` = `candidate_level_excluded` |

`TestRoutingIsDeterministicAndReplayable` 钉 §2.8：`routing_seed = H(request_id ‖ policy_version ‖ routing_epoch)`，同输入两次 seed 相同、候选次序相同；把 `Result.Replay` 交给 `routing.Replay()` 能独立复原同一份计划并返回 64 位十六进制的候选摘要；换 `request_id` 必须换 seed。线上模式（注入 `Random`）下 `Result.RoutingSeed` 与 `Plan.RoutingSeed` **都为空**——没有逐位复现的把握就不能声称有。

`TestStickyKeepsPrimary` 钉粘性两面：会话内钉住 `campus-vllm-b` 就不漂移；钉到一家不健康/超分级的候选时必须换，不能硬粘。

`TestPlanProcessorChainMatchesPipeline` 钉「计划里写的链」与「实际装配的链」是同一份——路由按链选路、接线按链执行，两边不一致就等于选出了一个跑不出来的计划。

## 7. 执行器与审计

执行器按候选声明的名字取实现（`executorFor()`，`scenario.go:490`）：`vllm` / `ollama` / `http-compat`，未注册的名字回落到确定性 fake。三类都注入同一个假传输 `w.Upstream`（`fakeTransport`，`:73`）：**注入 RoundTripper 而不是起监听**，这样请求编码、逐跳头过滤、`CheckRedirect` 与生产完全相同，只有「拨号」这一步被替换。

`AuditRow`（`:180`）是审计**投影**（真实 sink 归 H 包），结构体里没有正文字段：正文只以 `body_sha256` 与 `body_bytes` 出现。`TestAuditRowCarriesNoBodyOrPII` 直接序列化审计行并断言 `13800000000`、`student-1001@example.invalid`、`sk-campussyntheticcredential00`、`请联系` 一个都不出现；同时断言摘要长度 64、`body_bytes`/`content_bytes` 都非零、候选侧事实（provider / executor / tier）齐全、`policy_version` 与 `routing_seed` 能回指当时。

响应侧也有过滤链：`SampleReply` 里同时埋了手机号与合成凭证，`campus-result-filter` 把它们换成 `[phone-redacted]` / `[credential-redacted]`——证明这条链确实有东西可滤，而不是碰巧没命中。

时间全部钉在 `BaseNow = 2026-03-01T08:00:00Z`（`university.go:31`），fixture 的签发时刻与 `FakeProvider` 的内部时钟共用这个基准。用墙钟的话，同一个用例在跨过 TTL 边界时会改变结论，回放断言当场失去意义。

## 8. 怎么把它接到真实网关上

示例自带的运行器是**装配顺序的可执行基线**，不是最终接线器（那是 H 包）。迁移时按这个顺序：

1. `identity`：把 `Mapper()` 的 claim 名单换成校内 OIDC 真实字段名，`Directory()` 换成从校内目录服务同步的别名表，`AllowUnknown` 保持关闭；
2. `policy`：把七个包写成策略包文件放进 `policy.bundles_dir`，`bundle()` 的版本戳补齐逻辑不要省（漏了 `Version` 的规则会在版本串里与真实内容脱钩）；
3. `routing`：候选池来自 provider 配置，`RoutingEpoch` 在池子或权重变化时 +1；
4. `processor` / `executor`：链名与处理器版本在注册期绑定，出网目标必须走 `AllowedEndpoints` 白名单并由接线方注入客户端；
5. 先 `mode: shadow` 跑差异报告，再 enforce——示例的判定与线上判定走同一个 `policy.Resolver`，影子期的差异才是策略差异，不是实现差异。
