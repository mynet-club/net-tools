## 1. 检索结果是否自动注入模型上下文

> **裁决（2026-10-04，§0）：B｜声明式注入（处理器类型 `kb-context-inject`，由平台配置声明）；三个子口径见 §0。** 下面「推荐」保留原文，是裁决前把代价摆出来的那一个，不要当现状读。
> **2026-10-05 三个子口径复核结掉（§0.1 第 8′/9′/10′ 行）**：超限按**整篇丢弃**（那句「截断」由主线改写）、合级**先不跑检测**认现状、注入成本**不新增计量**。P5 已按这三条读法落地，不再有悬置口径。
>
> **但 B 落不了地，缺的不是代码：见 §8。** 「注入」的前提是网关手里有可注入的内容，
> 而 §3.C 的委托协议明令不返回正文（`ReturnedDocument` 只有摘要，`leak_test.go` 把这件事
> 锁成了验收线）。正文通道要不要开，是一条没上过桌的政策。

**现状。** 检索只有一个入口：`/v1/_me/knowledge/search`（internal/server/knowledge30.go:463）。
它把准入过的源逐个问一遍，把 `citations` 交给**调用方**，并且逐源落审计
（`kbAuditSink` → `s.db.AuditScope(..., kbAuditAction, ...)`，落库失败则本次结果**不交付**）。
请求路径上没有任何一处把检索结果写进将要出网的正文：正文的唯一改写者是处理器链
（forwarder.go 的 `pc.runRequest`），而处理器声明里没有「读知识源结果」这个输入面。

**影响。** 这不是"要不要方便一点"，是**谁授权内容进入上游 prompt**：

- 数据分级：注入的文档算哪一级？它必须过 provider 的 `max_data_level` 门，否则
  「一条 internal 文档经由自动注入进了 public 上游」就是一次没人授权的出网。
- 计量与费用：注入直接涨 prompt token，而 §3.F 边界 1 要求计量语义一个字不改 ——
  自动注入等于网关替用户改了账的输入。
- 可解释性：回放记录描述的是「当时判用了哪些结论」。注入发生在接线层里而不在
  声明面里，回放就看不见那次交换为什么长这样（§2.8 的证据链会掺进无法解释的差异）。

**候选方案。**

- **A｜保持显式**（现状）：调用方检索、自己拼上下文。代价：每个客户端都要接两个口，
  RAG 体验最差，但也最没有隐式行为。
- **B｜声明式注入 = 新增一个处理器类型**（例如 `kb-context-inject`，phase
  `before-upstream`、access `transform-body`），沿用 E 包已有的声明表、范围选择器与
  shadow/enforce 生效面。检索的准入结论仍然只来自策略内核，处理器只是搬运工。
- **C｜接线层内建注入**（forwarder 直接拼）。**明确不推荐**：注入策略从配置面消失，
  管理台看不出「这条链会带什么进上下文」，回放与审计都无法解释正文为什么变了。

**推荐。** 若主线要自动注入，走 **B**：它不新增第二个真值源，把「谁授权」这件事
仍然留在策略内核与声明表里；C 违背 §2.7 规则 4（新语义要带版本与迁移说明）的精神。

**迁移影响。** B 需要：处理器类型注册（processor.NewRegistry 的已知类型清单自动跟着，
internal/config/procconf.go:151 那一处已经按注册表取）；配置校验新增「注入源的数据分级
不得高于该上游声明的上限」这类硬规则；管理台的声明面板要能显示"这条会带内容进上下文"。
schema_version 是否要 +1 由主线定（同一份配置在新版本下行为变了）。

**测试影响。** 至少四条：注入内容不得越过源 ACL；注入后 usage 计费与不注入时同口径
（只多不少，且多的是真实 token）；被策略拒的源一个字都进不去；回放能解释注入后的正文差异。

**需要谁决定。** 主线（是否把它列为对外能力）+ C 包 owner（检索结果的分级归属）+
E 包 owner（新处理器类型的接口冻结）。

## 2. 流式 Attempt 的总时限与 idle timeout 如何取舍

> **裁决（2026-10-04，§0）：B｜扩 Attempt 语义（`Timeout = 0` = 以调用方 ctx 为准）。** 下面「推荐」保留原文，是裁决前把代价摆出来的那一个，不要当现状读。

**现状。** 流式**不委托**（executor30.go 文件头边界 3）：`executor.Attempt.Validate`
强制 `Timeout > 0` 且 `MaxResponseBytes > 0`，而现网流式刻意「无总时限」
（idle.go 的看门狗按**空闲**掐，因为长回答会被总时限正常掐断）且「边收边转发、
不缓存全文、不设字节上限」（§2.9 规则 7）。§3.F 因此只打通了非流式那一段。

**影响。** 流式是线上主流形态。不委托意味着执行器这一层对占大头的流量没有约束力：
新协议形态（Anthropic、本地后端）在流式上无处安放，"绕过出网控制"的下一句话就问不到流式。

**候选方案。**

- **A｜维持不委托**：流式永远走 2.x 传输。代价是上面那句。
- **B｜扩 Attempt 语义**：允许 `Timeout = 0` 表示「以调用方 ctx 为准」，
  `MaxResponseBytes = 0` 表示「不缓存、不设字节上限、逐段透传」。Attempt 是 F 包的
  冻结接口，改它等于改契约 —— 需要接口裁决，不能在接线里偷偷做（playbook 的原话）。
- **C｜给流式套一个很大的总时限**：**不推荐**，这是功能回退：现网刻意无总时限的理由
  （长回答被正常掐断）不会因为接线而消失。
- **D｜新增 `Attempt.IdleTimeout`，把空闲看门狗搬进执行器**：**不推荐现在做** ——
  relay 里的触达统计与三类归因（客户端走了 / 空闲超时 / 我们的时限到了）会同时存在两份，
  而 §3.F 边界 1 的方向是「计量与归因留在 relay」。

**推荐。** 若要打通流式：**B**，并且空闲看门狗继续留在调用侧（relay 里），执行器只表达
「本次交换不限总时长、不缓存」。B 的判定门槛写清楚：`Validate` 放宽后，必须有测试证明
「0 不是忘了填」，否则接线层会重新长出猜默认值的分支。

**迁移影响。** F 包的 Attempt 与 HTTPExecutor / Fake 两侧同步；`executor30.go` 的边界 3
整段作废并重写；relay 的流式分支要么保留（两套传输并存）要么重构（改动面大得多）。
文档面：§2.9 规则 7 的表述要跟着改。

**测试影响。** 流式委托的三类必测（正常/拒绝/失败）+ 与 2.x 的计量逐字段一致（现有
`TestExecutor30MeteringMatchesLegacyPath` 的同形版本）+ 断连三分归因 +
「总时限为 0 时不缓存全文」的内存上界测试。

**需要谁决定。** 主线 + F 包 owner（Attempt 契约）。

**执行记录（2026-10-04，P2）。** 按 B 落地，流式从这一包起**也交给执行器承载**。

## 3. ExecutorRegistry 的唯一生产调用点

> **裁决（2026-10-04，§0）：A｜删除 `Registry`（含 `ResolvePlanPrimary`）。** 下面「推荐」保留原文，是裁决前把代价摆出来的那一个，不要当现状读。

transport 绑在实例上，同一个名字必然对应多实例（自有上游带出网校验的拨号层与系统池

- 用哪个执行器由 `RoutingPlan.Executor` 选择，不是由注册表按优先级挑；

## 4. 执行、检索、策略三类明细是否落库

| --- | --- | --- |

## 5. 首选顺序逐位复现是否需要 D 包新增接口

> **裁决（2026-10-04，§0）：B｜D 包新增按声明算法回放的窄接口。** 下面「推荐」保留原文，是裁决前把代价摆出来的那一个，不要当现状读。

**现状（裁决前的快照，P4 已把它改掉 —— 见本节末尾的执行记录）。** 状态口明确写着不做逐位复现：`/v1/_admin/replay` 的
`bit_exact_primary_order = false`（internal/server/replayadmin.go:82），并声明两侧算法名
`routing-seeded-splitmix64-v1`（线上抽样，replay30.go:60）与
`replay.SamplingAlgoReplayV1`（回放默认）。D 包已经具备确定性随机源与快照回放：
`routing.SeededSource`（source.go:47，sha256 + splitmix64）、
`Planner.PlanWithReplay`（plan.go）与吃「当时逐个问过 gate 的结论」的
`ReplayOffer`（replay.go:17）—— 回放**不问活的策略**，这是它成立的前提。
RoutingRecord 已带 `RoutingSeed` / `RoutingEpoch` / `SamplingAlgo` / `CandidatesDigest`。

**缺口到底在哪一层，需要先说清。** 记录里已经有 seed 与算法名，而 `trace` 端点对
「没 seed 的请求」刻意不声称逐位可复现（§2.8）。剩下的分歧点有两层，**不是同一件事**：

1. **记录模式（schema）不够**。`RoutingRecord` 带的是
   `RoutingSeed`/`RoutingEpoch`/`SamplingAlgo`/`CandidatesDigest` 加一份按稳定顺序写入的
   `Candidates []policy.RouteCandidate`（internal/replay/record.go:396-412）。而 D 包的
   快照回放入口 `routing.PlanFromReplay` / `routing.Replay` 吃的是 `ReplayInput`
   （internal/routing/replay.go:63-95），它额外要求 `Objective`、`Requirement`、`Sticky`、
   决策时间基准 `Now`/`TTL`，以及**顺序即当时候选顺序**的 `[]ReplayOffer` —— 每位带
   `Healthy`/`CooldownUntil`/`ObservedLatencyMs`/`CostKnown` 这类**运行时事实**。
   `RouteCandidate` 是配置级候选，没有这些位；`CandidatesDigest` 是摘要，不可反推。
   所以今天**没有任何一条路径能从记录文件重建 `ReplayInput`**：跨进程回放用的是
   `internal/replay` 自己的抽样器（replay/routing.go:23），只核候选摘要、排除原因与授权，
   不声称首选逐位相同。补这一位要么改记录 schema（v1→v2，历史文件要能读），要么由 D 包
   提供一个「从记录输入重建快照」的接口 —— 这正是标题问的那件事。

   一个有利于 B 的事实：**那份输入在判定当场就已经算出来了**。接线侧每次规划都调
   `PlanWithReplay` 并同时拿到 `plan` 与 `replay`（internal/server/policy30.go:416），
   只是当前只从 `replay` 里取了 `CandidatesDigest()` 写进快照，其余字段当场丢弃
   （policy30.go:425-427）。所以这不是「要新造一套采集」，是「把已经握在手里的那份
   决定留不留、留在哪、留多大」—— 而后一半是体积与隐私问题（`ReplayInput` 带 subject、
   范围集合与全部候选的运行时事实），因此必须主线定口径，不能由接线侧默认全量落盘。
2. **算法实现是否同一个**。用同一个 seed 重跑，是否必然得出与线上同一次
   `weightedSample`/`choosePrimary` 相同的**次序**，还取决于 (a) 线上与回放用的是否同一算法
   实现（今天算法名是两个不同的串：`routing-seeded-splitmix64-v1` 与
   `replay.SamplingAlgoReplayV1`），(b) 并列同分时的比较次序是否稳定（与 offers 切片次序
   绑死，不依赖 map 遍历）。

也就是说：**schema 那一层不补，接口那一层再怎么加也复现不出来**；反过来只补 schema、
算法名仍是两个事实源，声称逐位仍然是空头承诺。

**影响。** 逐位承诺是一次**对外口径变更**：一旦声称，「回放给出不同首选」就是缺陷报告；
不声称，回放只是解释性工具（现网文档就是这么写的）。

**候选方案。**

- **A｜维持解释性回放**：不动 D 包，状态口继续报 `false`。
- **B｜D 包新增一个窄接口**：例如按声明算法回放的入口（`ReplayWithAlgo(input, algo)` 或
  常量表 + 校验「快照声明的算法与本次重跑一致，否则拒绝声称逐位」），线上与回放共用
  同一份实现，`bit_exact_primary_order` 才允许翻成 true。**这一条隐含第 1 层的先决条件**：
  记录要先带得上 `ReplayInput` 那几位（新增字段或新增一份快照），否则接口拿到的是残缺输入。
- **C｜不加接口，只在 I 包用现有 `PlanWithReplay` 重跑并把差异当缺陷**：**不推荐** ——
  这等于在没有契约的地方对外承诺，一次无关的次序改动就会让历史回放"看起来坏了"。

**推荐。** **B 的最小版本**（只做算法一致性校验 + 一个显式入口），前提是主线接受逐位
成为对外承诺；否则 **A**。判定标准也一并交给主线：只有当快照带 seed **且** 声明算法与
重跑实现一致时才承诺，其余一律降级为解释性回放（这一位今天已经用
`exactly_replayable` 表达，B 是把它的作用面从「有 seed」收紧到「有 seed 且算法可核对」）。

**迁移影响。** D 包公开接口新增（不改既有签名）；`SamplingAlgo` 的取值口径统一
（两个串收敛成一个事实源）；管理台/文档里「解释性回放」那句要跟着改。

**测试影响。** 跨进程逐位复现用例（同一 seed 在另一个进程重跑，首选与次序逐字段等）；
算法名不一致时必须**拒绝**声称逐位的负例；并列同分次序的稳定性用例（打乱 offers 输入
次序不改结论）。

**需要谁决定。** 主线（是否对外承诺逐位）+ D 包 owner（新增接口）。

**执行记录（2026-10-04，P4）。** 按 B 落地，而且这一条**两层缺口都补了**——本节上面那句
「schema 那层不补，接口再怎么加也复现不出来；只补 schema、算法名仍是两个事实源，声称逐位
仍是空头承诺」是这包的设计约束，不是修辞：

- **第 2 层（算法实现是否同一个）——接口放在 D 包，只有 D 知道自己哪条路径逐位**。
  `internal/routing/replay.go` 新增：`SamplingAlgoSeededSplitmix64V1` 成为算法名的**唯一事实源**
  （此前接线侧 `replaySamplingAlgoOnline` 写的是同一内容的字面量，两处「碰巧一致」不算证据）、
  封闭集合 `bitExactAlgos` + `AlgoSupportsBitExact` / `BitExactAlgos()`、哨兵 `ErrNotBitExact`，
  以及窄接口 `ReplayWithAlgo(in, algo)`：算法不在集合里就返回 `ErrNotBitExact`（**带原因**），
  绝不返回一个不保证逐位的计划来冒充逐位结论。**既有签名一字未改**（`Replay` /
  `PlanFromReplay` 行为不变），所以这一包对 D 是纯增量。标识描述的是
  `source.go` 四个魔数 + `weightedSample` 累积扫描 + `Objective.less` 次序**合起来**的那条路径，
  改其中任何一项都要新增 v2 标识并把旧值留在集合里，否则历史记录会被新实现误报成可逐位。
- **第 1 层（记录模式不够）——`replay.File` 升 v2，v1 仍可读写之外仍可读**。
  `SchemaVersion = 2` / `SchemaVersionRoutingOnly = 1`，可读清单只有一份
  （`ReadableSchemaVersions()`，`supportsSchemaVersion` 也从它读），且是**逐个等值**判断而不是
  区间：出 v3 时区间写法会把没实现的版本静默当可读，于是按 v2 字段解释 v3 内容。
  `RoutingRecord.Replay *routing.ReplayInput`（`json:"replay_snapshot,omitempty"`）——
  承认但**不要求**：版本号必须为此而变，因为「文件里没有这个字段」和「文件承认有、这条没写」
  是两种不同的证据状态。`Encode` 保留文件自己声明的版本；v1 文件里出现 `replay_snapshot`
  直接 `ErrRecordInvalid`（版本与内容矛盾，不是"多带一位没关系"）。
- **凭证之间必须互相咬合**（否则"证据齐全"是假的）。`RoutingRecord.Validate` 新增四条交叉核对：
  快照的 `Seed` / `PolicyVersion` / `RequestID` / `CandidatesDigest` 必须与记录顶层那四位一致；
  `BitExactReplay()` 三道闸门（v2 承认快照 → 快照存在且自校验通过 → 算法在封闭集合里），
  任一不过都返回**说明原因的** `ErrNotBitExact`。采集侧同样把矛盾挡在门口：
  `RoutingRecordFrom` 里「带快照 + 声明了一个不逐位的算法」是**构造期错误**，而不是留给回放猜。
- **隐私与体积口径**（裁决文档点名「必须主线定，不能接线侧默认全量落盘」——本包落的是
  主线给的 B，形状如下，若主线换口径改动集中在采集那一处赋值）。落盘的是**导出文件**，
  不是数据库：窗口缺省关、按千分率与范围采样、进程内、`collect` 产物 0600、`replay.export`
  落审计且 detail 只有条数。新增暴露面相对 v1 是每条选路记录多带候选的**运行时事实**
  （健康位、冷却截止、观测延迟、成本已知位）、`allowed_regions` / `scopes` / `objective` /
  `requirement`，以及此前只有决策记录才带的 `subject` —— 文件级敏感类别没变（那份文件本来就
  回答「谁在什么时候被授权用了哪个模型」）。禁词扫描一字未松，且 `leak_test.go` 把新嵌套的
  `ReplayInput` / `ReplayOffer` / `Requirement` / `StickyState` 的 JSON tag 与 Go 字段名逐个过了一遍词表。
- **采集接线只有一处赋值**（`internal/server/policy30.go`）：那份输入**判定当场就已经算出来了**
  ——每次规划都调 `PlanWithReplay` 并同时拿到 `plan` 与 `replay`，此前只取
  `CandidatesDigest()` 其余当场丢弃。现在把 `snap.Validate() == nil` 的那份留在 `policyShot`
  上；组不出的（缺 seed、运行时事实不齐）留 nil，记录于是退化成解释性回放。**宁缺毋假**：
  写一份自相矛盾的快照换来的是导出侧 500，或一条看起来证据齐全却永远只能降级的记录。
  刻意**不重新规划一次**去"补全"——那已经不是当时的现场。
- **对外口径翻 true 的那一面必须带条件**。状态口 `bit_exact_primary_order` 改成 `true` 的同时
  新增 `bit_exact_algos`（取值空间摊开）与 `bit_exact_condition`（只对 v2 + 声明该算法 +
  带快照的记录成立），CLI `replay status` 把条件单独占一行全文打印，面板 tooltip 直接引用
  服务端那句话——**界面不自己拼条件**。只回 `true` 会比原来的 `false` 更误导：窗口里混着导入的
  v1 记录时，那一条永远只能解释性回放。`record_schema_version` / `_readable` 一并出来，
  运维据此判断旧文件能不能直接回放。
- **降级不许静默**（这条是本包唯一的验收线）。`ReplayRouting` 有快照时逐位比对
  `plan_digest` / `routing_seed` / `fallbacks_count` / `order/第 i 位`（次序按位逐个比，
  因为 `RoutingPlan.Digest()` 内部排序，摘要相同不代表次序相同）；三道闸门任一不过就在报告里
  写「为什么只能解释性回放」。报告新增 `[首选逐位]` 行内标记、`Outcome.BitExact`
  （`omitempty`：老路径不附新字段，历史基线摘要才不用重钉）与摘要行末段
  「首选逐位复现 N」——**这个数字刻意不并进「通过 N」**，因为一条解释性回放照样可以 passed，
  它证明的是「结论没变」，不是「顺序能逐位复现」。
- **测试**（`docs/3.0-verification.md` §20 有逐条名字与门禁数字）：D 包侧 8 条新增
  （快照逐位复现、Encode/Decode 往返后逐位仍成立、乱序 offers 不改逐位次序、算法标识不符时
  拒绝声称逐位、快照与记录三处矛盾各自被拒、`RoutingRecordFrom` 的算法判定两条、
  两个抽样器**确实不是**同一算法的 200 seed 反证、逐位算法集合是封闭的）；
  schema 侧 2 条（v1 文件仍可读且逐位计数为 0、v1 带快照被拒）；接线侧闭环测试改成
  A/B 对照（原文件逐位 1 且无降级备注，`stripSnapshot` 后逐位 0 且报出解释性回放）；
  golden fixture 的头从 1 改成 2 而**报告摘要常量未变**（`61dd8998…`）——
  「记录形状变了、结论面没变」在这里是可证的而不是宣称的。
- **测试影响清单三项的兑现情况**：跨进程逐位复现（同 seed 另一进程重跑，首选与次序逐字段等）
  ——已做，第 23 节那条走的是真 CLI + 磁盘策略包；算法名不一致必须拒绝声称逐位——已做，
  正负两条都有；并列同分次序稳定性——已做（乱序输入不改结论，且次序来自 `Objective.less`
  的全序 tiebreak：provider → upstream_model → executor）。

**遗留（不算本包完成面）**：逐位承诺今天闭合的是**同一台机器上的跨进程回放**（独立 CLI、
磁盘策略包、钉住的时钟）。「把导出文件拷到另一台机器、喂另一天的策略包」这一半当时仍然只有
§15/§17 那种同机跨目录/跨二进制/跨时钟的等价演练，缺的是真机现场 —— **现场已在 §24 补掉**
（2026-10-04；「另一天的策略包」那一半仍是等价演练级别的断言，§24 用的是采集当时那套包）。另外 `ReplayInput`
的体积今天**没有上限位**：窗口容量按条数收（1~4096），而实测一份真实导出的单候选记录里
`replay_snapshot` 约 743 字节（≈ v1 那条选路记录 962 字节的 0.8 倍；其中每个候选约 324 字节，

如果主线认为需要「按字节截断快照并如实降级」，那是新的对外口径，接线侧不自行拍板。

## 6. 拒绝证据与原文出网授权的审计口径

> **裁决（2026-10-04，§0）→ 复核结掉（2026-10-05，§0.1 第 6′ 行）：主线认 C。** 接线侧按原则取
> C（`policy.deny` + `egress.allow`）落地，P6 已在树上并过门禁。**这一条今天不再是悬置口径**；
> 下面「推荐」保留原文，是裁决前把代价摆出来的那一个，不要当现状读。

**现状。**

- 管理写侧动作已落审计并带范围（`auditAt`：policy.mode.set、policy.bundle.publish、
  replay.sampling.set / export / clear 等，全部 `system:global`）。
- **请求期的策略拒绝没有审计行**：只有 `requests` 里的 403 + 错误文案 +
  `policy_version`，加上（窗口开着时）回放 `DecisionRecord` 里的 `Reason` / `Reasons` /
  `Winner` / `Matched`。窗口是有界内存、缺省关闭，被挤掉就没了。
- **原文出网授权**今天有两处结论、零处长期留痕：策略内核
  `Resolver.AllowsRawBody` 的结论进 `DecisionRecord.ExternalPlaintextAllowed`
  （record.go:191，回放会重跑并比对，replayer.go:157），而 sidecar 处理器在运行时按
  这一位决定是否拿到未脱敏正文（sidecar.go:387、procruntime.go:236）。上游侧的对应闸门是
  provider 的 `max_data_level` 分级门 + dialer 拨号层出网校验，它们的结论只体现在
  「这一发有没有成」上。

**影响。** 事后取证的能力不对称：管理员改了开关查得回来（§2.7 规则 2），而
「这条请求为什么被拒（哪条规则拒的）」「凭什么这份内容能出网（授权结论是什么）」
在窗口之外问不回来。反过来，如果长期记每一次拒绝，审计表体积随请求量线性增长，
而 detail 字段又是自由文本 —— 一条带正文的 detail 就是隐私事故的入口。

**候选方案。**

- **A｜维持现状**：拒绝与授权结论只在请求记录 + 有界窗口 + 日志里。诚实的代价是
  「超过窗口期就问不回来」，这句要写进交付说明。
- **B｜请求期拒绝落审计**：新增 `policy.deny` 动作（actor=subject、target=`model:<名>`、

### 6.2 执行记录（P9，2026-10-05，按 §0.1 第 15′ 行与 21′ 行落地）

**裁决要的那件事。** 15′ 认了「审计永久保留」，但它同时要求「代价写成承诺而不是默认」。
这句话的可执行版本只有一条：运维读得到这张表现在多大。读不到，「永久保留」就是

**落了三处，一句清理都没加。**

**失败语义分两态，绝不报凭空的 0。** 从没读成功过（`s.db == nil` 或一次都没成功）→
两条序列**缺席**、`/healthz` 不带 `audit` 段；曾经读过 → 继续报旧值（滞后由 TTL 界定），

「审计表是空的」，而那恰好是这一位最不该被误读的状态。失败也按 TTL 退避：
一个坏掉的审计库不该被每一次抓取重打一遍。

### 6.3 执行记录（P11，2026-10-05，按 §0.1 第 17′ 行落地）

**裁决要的那件事。** 17′ 认的是「面板加运行态红灯」：状态接口现返每条声明的装配结果，
**不落库**，重启后只看得到当前。它要堵的是一段很具体的静默窗口 —— 声明保存成功了、
界面说「这条存在」，而网关从来没把它装起来过。这段差距今天只在日志里说一次，
没人翻日志就永远读不到；而它下游的后果不是「少个脱敏」，是 enforce 下**命中它的请求直接被拒**。

**读数一个都不新算。** 装配代码本来就把失败算出来了，只是没人往上搬：
处理器看 `procRuntime.regErrs[声明名]`（参数文件缺失 / 类型未注册 / 工厂构造失败），
知识源看 `knowledgeSource.err`（transport 不可用 / 委托客户端装配失败）。
`assemblyInspect()`（`policyadmin.go:178`）把这两张表投影成两段
（`procAssemblySection` `policyadmin.go:199`、`knowledgeAssemblySection` `policyadmin.go:226`），
挂在 `adminPolicyInspect` 的 `assembly` 键上（`policyadmin.go:113`）—— 那条接口是 3.0 唯一的
状态面，所以这里**不新建第二个真值源**，也不新增端点。拒因**直接用装配当时那句话**，
不重述、不美化：重述一遍就是维护第二套判据。

**不装配的时候不逐条打分。** `policy.mode=legacy` 或策略包加载失败时，`rt == nil`，
这一段只给**段级原因**（`reason` + `load_error`）和声明条数，`declarations` 直接**缺席**。
把「没跑」复制成 N 条「每条都失败」是撒谎 —— 那 N 条声明的形状可能全都好，只是当前模式不用它们。

**「不落库」用两侧锁住。** `TestAssemblyInspectWritesNothing` 先落一条基线审计行，
连读三次状态接口，再断言 `AuditVolume()` 前后**完全相等**。只断言「代码里没有 INSERT」
不够，因为任何走 `s.Audit(...)` 的顺手埋点都能把它漏掉。

**红灯只跟真的重装配走 —— 这条是实测撞出来的语义。** `Store.Reload` 用
`configEqual(prev, new)` 判等，**只有 config.yaml 内容变了才 bump 修订**；而运行参数文件
不在 config.yaml 里。所以「补好 `processor_params/<声明名>.json`」这一步**不会**让红灯自己灭，
必须再改一次配置（或重启）。这不是缺陷，是同一套修订语义的必然结果，但如果界面不说，
运维就会把它读成「我明明补了文件，为什么还是红的」。这句话写进了三处：接口 `note`、
面板说明段（`ui/admin.html:130-135`）、OpenAPI 描述；并钉成断言 ——

## 7. 导出过滤键是否按 scope kind 放开

> **裁决（2026-10-04，§0）→ 复核结掉（2026-10-05，§0.1 第 7′ 行）：主线认 C（采集侧键改 `(kind,id)` 全串、导出支持 org/project）。** 下面「现状」与「推荐」都是裁决前的快照，**P7 已按 C 落地，见本节末尾 §7.1 的执行记录** —— 按 §7.1 读现状，不要按「现状」那段读。org 级导出的授权闸门同日认「**`admin_token` 即够**」，按范围显式授权并入 P8（§0.1 第 14′ 行）。

**现状。** 采样开关与导出的 `scope` 过滤**只认 `user:<用户名>`**
（replayadmin.go:152-158），因为窗口按 2.x 的路由作用域名（用户名）键控 ——
`replayWindow.file(scope)` 比的就是 `captureReplay` 收到的那个 `scope` 形参
（replay30.go:156、244），它是用户名而不是 kind:id 全串；其它 kind 会被显式拒掉并把
原因说破。

值得注意的是：**记录本身已经带全链** —— `DecisionRecord.Chain` 是
`[]policy.ScopeRef`（record.go:178）。今天缺的不是"记录里没这个事实"，
而是"过滤键没用到它"。

**影响。** 「把这次事故涉及的那个组织的全部判定导出来」今天做不到，只能逐个用户导；
逐用户导在 org 范围策略出问题时恰好会漏掉「被同一条规则影响、但用户名我不知道」的那些。
反过来，放开到 kind 级意味着一次导出的暴露面从一个人涨到一个组织，而导出端点响应体带
subject 与规则标识 —— 这是 §2.9 规则 6 意义上的暴露等级变化，不是便利开关。

**候选方案。**

- **A｜维持 user-only**：过滤键与窗口键控同形，隐私面最小。
- **B｜导出按 `Chain` 过滤，支持 `kind:id` 精确匹配**：不改采集侧键控（窗口照旧按
  路由作用域采），只把导出过滤从"键控列相等"改成"链上任一 ref 匹配"。改动集中在
  `replayWin.file(scope)` 的过滤语义与参数校验；通配（`organization:*`）另议。
- **C｜采集侧改键为 (kind,id) 全串**：语义最干净，代价是 `routeScopeOf` 那一路与
  「按 2.x 作用域采集」的既有口径都要重写，还会牵动 §4 那条落库裁决。

**推荐。** **B 的精确匹配版本**（只支持完整 `kind:id`，禁通配）：它把「过滤能力」和
「采集口径」解耦，不动窗口键控，也不引入通配带来的静默空采（采样开关那段注释已经
指出通配按字符串相等会一个都不匹配 —— 那种"看起来过滤了其实是空"的结果在证据链里比报错更糟）。
放开前必须同时定：**谁能导 org 级**（管理凭证够不够，还是要按范围的显式授权）与
导出审计的 target 写法（现在 target 只有用户名）。

**迁移影响。** 无结构迁移。API 面：`/v1/_admin/replay/export` 与 `…/sampling` 的
`scope` 参数校验放宽（错误文案要跟着改，现在那句点名「只认 user:」）。文档面：
README 与 §2.8 的口径、管理台证据链面板的提示文案。

**测试影响。** 按 chain 过滤的正例（org 范围策略包下，多个用户的记录都能被一次 org 导出取到，
且不混入别的组织）；负例（通配仍被拒、kind 不匹配时明确报错）；隐私断言（导出不因过滤
放宽而多带任何正文字段）；审计断言（org 级导出记的是 org 引用，不是某个随机用户名）。

**需要谁决定。** 主线（跨用户导出的授权口径 —— 这是一个权限问题，不是过滤参数问题）。

### 7.1 执行记录（P7，2026-10-04，按 C 落地）

**落地了什么。** 三处，都是一句话的展开：「过滤键和采集键是同一个类型，命中规则只有一条」。

- **窗口键控改成 `policy.ScopeRef`**（`replay30.go`：`replayEntry.key`、`replayWindow.filter`）。
  采集侧的键由 `requestAuditScope30` 给出 —— 也就是 P6 那条归属规则的同一个函数，
  于是「这条证据关于谁」在审计与回放两条链上不可能各说各话。复合键用 struct 而不是
  `Display()` 字符串，沿用 `statscache.go` 的既有先例（`Display()` 只能进日志与界面）。
- **一条命中规则被采集与导出共用**（`replayScopeMatch(filter, key, chain)` = `filter.Is(key)`
  **或** `chain.Includes(filter)`）。这不是省事：两个调用点各写一遍，就会出现「采得到但导不出」
  或「导出能看见但当初没被采到」——而后者意味着报告里的分母是错的。范围过滤从「键控列相等」
  放开成「键控相等 **或** 当时的范围链含它」，后者才是 org/project 级导出有意义的原因：
  请求范围永远是一个人，一次判定同时落在 user / organization / project 上。
- **参数校验只在一处**（`parseScopeParam`，管理口与用量导出本来就共用它）。导出不再拒绝
  非 `user` 的 kind；**通配仍然 400** —— 通配按字符串相等会静默空采，在证据链里比报错更糟，
  这条负例现在有测试钉着（端到端 23l）。`configure` 收的是已经校验过的 `*policy.ScopeRef`，
  窗口自己不再解析语法。
- **导出审计的 target 写成范围全串**（`organization:university` 这样的 `kind:id`，
  不过滤时写 `replay`）。原来是裸用户名，那正好是本条裁决要修的形态。0 命中也是一条 200
  一条留痕，并且 detail 里明写「命中 0 条 —— 窗口里没有一条记录的请求范围或范围链是这个范围」，
  不靠调用方自己数空数组。

**这一段暴露出两处真的代码缺陷（不是文档口径问题）。** 第一处：旧接线在管理口把 `user:alice`
校验成合法，却把**裸字符串原样**存进窗口做过滤键，而 `shouldCapture` 比的是路由作用域名
（裸用户名 `alice`）。结果：**任何带范围过滤的采集都是静默空采** —— 开关开着、流量在跑、
窗口里一条没有，而 `/replay` 状态口只报计数，报不出「你的过滤条件写错了」。旧单元测试
没抓到它，因为它绕过 HTTP 直接拿裸形式去调 `configure()`，测试与线上喂的是两种形态。
修法是把形态钉在类型上（两侧都是 `policy.ScopeRef`，这种写法通不过编译），
再补两条门禁：HTTP 路径上的单元断言 + 端到端 23l 的 `entries == 1`（真进程、真请求、真开关）。

第二处同形不同面，长在面板上：导出提示用 `f.routings` 读**导出文件**，而记录文件的 JSON 键
是 `routing`（单数，`internal/replay/codec.go:94`），`routings` 是**状态接口**的计数键。
JS 没有类型检查，`(undefined || []).length` 安静给 0，于是「导出成功但选路永远 0 条」；
文件本身是对的，所以它不会让人拿错证据去回放，但会让人去查采集 —— 与第一处同一个错方向。
`ui/openapi.yaml` 把导出响应体写成 `routings[]` 是这一处的**来源**（面板照文档写 JS），
所以文案与代码一起改，并在 `scripts/check-ui-refs.sh` 里加第二段：面板计数行与 openapi
响应描述读的键名必须出现在 `File` 结构体的 json tag 里，两个锚点各自「一行都没命中」也判红
（措辞变了而检查没跟上 = 空跑的门禁，比没有更糟）。这一段的浏览器读数与三次 Edit 往返在
docs/3.0-verification.md §23.11。

**今天 org 级导出导得到什么。** 一个都不到 —— 而且这是已知的接线缺口，不是过滤能力没做完：
`internal/identity` 的成员关系映射（claim → organization）**没有接进请求路径**，
`policyChainFor` 拼出的实时链只含 `user:` 与 `system:`。所以本次落地在真机上的可寻址收益是
「静态 key 流量可按 `system:global` 单独导出」「过滤条件写错时不再静默空采」，org/project
那一半只有单元层证据（手工构造的链）。文档、OpenAPI 与 README 三处都按这句话写，
没有写成「org 级导出已可用」。

**谁能导 org 级 —— 这条留给主线。** 今天的授权口径就是**管理凭证**：拿到 `admin_token` 就能
按任意精确范围导出，一次导出的暴露面从一个人涨到一个组织（记录带 subject）。按范围的显式
授权（例如「只能导你在其内的组织」）需要一条新的判定，且它必须落在 `parseScopeParam` 之后、
`file()` 之前这一个点上——接线侧没有自行加这层，因为没有可校验的成员关系真值源可用。

**如果主线改口径。** 换 A（回到 user-only）：删 `replayScopeMatch` 的 chain 那半与 kind 放开，
类型化的键可以留着（它顺手修掉了静默空采那个缺陷）；换 B（只放开导出过滤、不动采集键）：
`replayEntry.key` 回退为字符串、`file()` 只比链，其余不动。两种都无结构迁移。

**测试。** 单元 `TestReplay30*` 共 12 条全绿，本包重写 1 条（默认关与范围过滤：类型化键、
HTTP 路径上的 `system:global` 采集/导出、org 导出 0 命中 + 留痕字段与文案、通配 400），

另 2 条（逐出与指针语义、管理面鉴权与留痕）改到类型化键调用 `configure()` ——
上一段那句「旧测试喂的是另一种形态」就是这两条的历史问题。守卫证据：把 `chain.Includes(filter)` 改成 `return false` 后，
`TestReplay30ScopeFilterMatchesChain` 当场失败（replay30_test.go:558，"按 organization 过滤应只拿
a-1，实际 []"），改回即绿 —— 这条断言不是恒真的。端到端 23l 十五条在真进程上跑

`dist/` 重出过一批（管理台是构建期内嵌的），两批产物与跨机/跨构建的口径见

**随包修掉一处演练脚本自身口径**（第三类失败，不是代码缺陷）：
`drill-release-artifact.sh` 判优雅退出用的是 `pgrep -f "$BIN"` —— 按**命令行字符串**匹配，

属于构建脚本变更，**交主线**。

## 8. 「声明式注入」隐含的正文通道：B 已裁决，但它的前置没被裁决过

> **状态（2026-10-04，主线裁决）：已裁决 —— 正文通道做成配置开关，默认关。**
> 主线原话：「我好像前面说过, 把这个做成一个配置开关? 其他你决策。」
> **裁决与执行口径见本节末尾 §8.1**（这一条从此不是阻塞项）。
>
> 下面的「现状三条硬事实」与「候选方案」保留原文，是为了让下一位看见当时桌上还有哪些读法、
> 以及为什么 C2 那个形状不能拿来当「B 已落地」汇报。
>
> 历史状态（2026-10-04，P5 开工前置检查）：待主线裁决 —— 接线侧当时没有写一行投机代码。
> 这一条不是「第 1 条要换个方案」，而是第 1 条的 B 方案**依赖一个本仓库明令禁止的能力**，
> 那个能力从来没有单独上过桌。§1 的裁决行仍然有效，但按当时的现状它落不了地。

**现状（三条硬事实，各自可核）。**

1. **委托协议里没有正文。** `knowledge.ReturnedDocument` 的字段集合是刻意收死的：
   `source_id / knowledge_base / owner_kind / owner_id / data_level / digest /
   title_digest / allowed / rule_id / decision_reason / acl_version / expires_at / score`
   （internal/knowledge/delegation.go:94-118），注释原话是「**只有摘要，没有正文，
   也没有标题明文**」。协议侧的禁止条款写在 docs/3.0-knowledge-delegation.md:144
   （「不得返回文档正文与标题明文」）与 :207、:371、:395。
2. **这条禁止是被测试锁住的，不是文档愿望。** `internal/knowledge/leak_test.go` 的
   `TestNoStructInThisPackageHoldsDocumentBody` 用反射词法扫描本包 15 个结构体的字段名与
   `json:` 标签，命中 `content / text / snippet / excerpt / body / raw / fulltext …`
   即失败（唯一例外是布尔位 `AllowRawTerms`），并断言扫描字段数 `scanner.visited >= 80`
   防止「递归没展开、永远绿灯」（`leak_test.go:114-127`）；旁边还有
   `TestBodyFieldWouldBeCaught` 那条反向对照，专门证明这个扫描器**真的会红** ——
   也就是说这条禁止不是文档愿望，是带自证的验收线。
   要让网关拿到正文，先要改的是这条守卫的口径，而它是 C 包 §3.C 的验收线之一。
3. **裁决的三个子口径本身就预设了正文在网关手里。** §0 第三条要求「注入文档的分级取
   **源侧申报级与 `detected_level` 的较高者**」—— 而 `detected_level` 是 E 包分类器
   **对内容**算出来的。C 包今天恒传 `LevelPublic`，理由就是它没有正文可检测
   （docs/3.0-knowledge-delegation.md:77、:459）。所以「按较高者合级」这句话在当前能力面下
   不是一个可以实现的表达式。

顺带两条会让实现变形的现状（不是禁止，是形状）：请求侧处理器**看不见被选中的供应商**，
`processor.Request` 只有 `RequestID / Model / Stream / Metadata / Body / Policy / Chain / Now`
（internal/processor/pipeline.go:75-84，注释明写「刻意不含任何金额、token 计量或供应商凭证字段」），
链条跑在 `PickFromPreferring` 之前（internal/server/forwarder.go:310 对 :327）—— 于是
「注入内容不得越过该上游 `max_data_level` 门」这句今天没有可复用的运行时落点；
而 prompt token 全部由上游回报（forwarder.go:1107 起的 `usageScanner`），网关不数请求字节，
所以注入改了多少 token 今天只体现在账单上，不体现在任何一条留痕里。

**影响。** 这不是「要不要方便一点」，是三件已经冻结的事同时被推开：

- **正文进网关**：§3.C 的委托原则（判定权在源、网关只搬运摘要）与 §2.9 规则 3
  （自动注入等于静默扩大正文访问面）。文档权限会变而网关里的副本不会跟着变，
  这正是 docs/3.0-knowledge-delegation.md:395 点名要防的「已撤销的文档还能被翻出来」。
- **`transform-body` 的语义被换掉**：这一档今天授权的是「改写**客户端发来的**请求正文」。
  往正文里塞网关自己取来的内容，是同一位权限干了另一件事 —— 声明面上看不出区别。
- **计量与回放**：注入直接涨 prompt token，等于网关替用户改了账的输入（§1「影响」段原话），
  而 §3.F 边界 1 要求计量语义一个字不改；回放记录里能看见链条名，看不见「注入了哪几篇的正文」，
  §2.8 的证据链会掺进解释不了的差异 —— 这一条 P4 刚把「解释不了就别声称」立成规矩。

**候选方案。**（都假定第 1 条仍取 B；差别只在正文从哪来、谁授权）

- **C1｜给委托协议加显式的正文能力**：新协议版本 + 一个独立的 opt-in 位（例如
  `ReturnContent`），源侧对**每一篇**再判一次「可交付正文」，网关侧配一个新的审计动作
  （`knowledge.content`，与 `knowledge.search` 分开），并且只在能力成立时注入。
  代价：C 包接口与 leak 守卫要重写成「按能力分级」而不是「本包无正文字段」；
  正文在网关内存里的生命周期、是否允许出现在任何持久化字段里，都要单独定版。
  这是唯一能真正满足三个子口径的读法，也是改动最大的一条。
- **C2｜只注入引用（`source_id` + `digest` + 分级），不注入正文**：今天就能实现，
  零新增暴露面。但模型看见的是十六进制串，RAG 收益≈0 —— 把它当成「B 已落地」来汇报
  就是我一直在避免的那类伪装，所以它只在「主线确认只要一个引用清单」时才有意义。
- **C3｜把第 1 条回退到 A（保持显式）**：客户端自己检索、自己拼上下文，正文住在客户端手里，
  网关不经手。代价是 RAG 体验（每个客户端接两个口），收益是**一条隐式行为都没有**，
  且与 §2.9 规则 3、§3.C 现状完全一致。
- **C4｜网关只做「注入的正文合规与否」的判定，不搬运正文**：客户端把 citations 放进
  `messages`，网关按声明表核对这些引用是否属于本次准入过的范围、分级是否越过该上游上限，
  不过就拒或脱敏。这条把「谁授权内容进入 prompt」这件事留在策略内核里（B 的初衷），
  同时不要求网关持有正文 —— 代价是它要求客户端配合携带引用，且它是**新语义**，
  按 §2.7 规则 4 要带版本号与迁移说明。

**推荐。** 若主线不肯让正文进网关，取 **C3 或 C4**；若肯，则只有 **C1** 是诚实的完整实现，
且 C1 必须一次把「协议版本、正文生命周期、独立审计动作、上游分级门落点、计量口径不变」
五件一起定，不能先写处理器再补口径。**不建议**在正文通道未定之前先落一个只能注入摘要的
`kb-context-inject`（C2 的形状 + B 的名义）—— 那会让声明表上出现一条看起来会带内容进上下文、
实际带的是哈希的处理器，而管理台分不出这两者。

接线侧按「不自行拍板」的处理：本包**不写代码**，P5 停在裁决门口，先把 P6 / P7 那两条
（第 6、7 条已按原则取 C、只等复核，且不依赖任何未裁决能力）执行掉。

**迁移影响。** C1 要动 `knowledge.ProtocolVersion` 与 `ValidateDocument` 一整套，
并新增配置面参数（源数上限、字节上限、正文开关）；C4 要动处理器语义表并加一个声明位；
C3 无迁移（回到现状）。`config_schema_version` 是否 +1 仍按 §1 的说法由主线定。

**测试影响。** C1 至少六条：正文只在能力成立时出现；能力不成立时逐字节等于现状；
被策略拒的源一个字都进不去；注入后的 usage 与不注入同口径（只多不少，且多的是真实 token）；
正文不出现在任何持久化字段与日志行（扩 leak 守卫到注入路径）；回放能解释注入后的正文差异。
C4 至少三条：伪造 citation 被拒、越级 citation 被拒、无声明时行为不变。
C3 只需把 §1 的「现状」补一条「已确认维持显式」。

**需要谁决定。** 主线（**正文可否进入网关进程** —— 这是政策问题，不是实现问题）+
C 包 owner（协议版本、leak 守卫的新口径）+ E 包 owner（处理器类型接口与声明位）+
D 包 owner（若要求注入受上游 `max_data_level` 门约束，得先给链条一个能看见候选事实的落点）。

### 8.1 裁决与执行口径（2026-10-04，P5 已落地）

> **主线裁决原话**：「我好像前面说过, 把这个做成一个配置开关? 其他你决策。」
> 于是第 8 条的读法是 **C1 的开关化版本**：正文可否进入网关进程由**平台配置显式声明**，
> 默认关；其余四件（协议版本、正文生命周期、审计动作、上游分级门落点）交接线侧定。
> 上面 C2 那个「只注入引用」的形状从此不是备选 —— 声明表里不会出现一条看着带内容、
> 实际带哈希的处理器。

**开关形状（第一道锁，唯一新增的配置面）。**

```yaml
knowledge_sources:
  - name: campus-rag
    endpoint: https://rag.internal/retrieve
    return_raw_body: true                          # 缺省 false = 这条源只给引用与摘要
    delivery_endpoint: https://rag.internal/deliver # 开关为真时必填
```

四条加载期拒（internal/config/procconf.go:257-287，理由都写在邻行注释里）：
开且入口独立 ⇒ 通过；**关着却配了入口** ⇒ 拒（读配置的人会以为开关是开的）；
**开着却没入口** ⇒ 拒（等到第一次交付才失败会把现场变成「处理器抱怨没有正文」，
而根因是磁盘上一行 YAML）；**入口与检索入口归一化后相同**（只差斜杠或空查询串也算相同）⇒ 拒。
为什么必须两扇门：正文是**另一套授权面**，共用入口就没法在「只开检索」的部署里
于网络层单独关掉正文通路，出网白名单也分不开两种暴露面。
热更新比较把这两个字段算进去了（internal/config/store.go:220-246）：
开关从关到开是一次**出网暴露面变更**（多一条独立协议通路、多一套授权判定），
漏比就会让它在热更新里被当成没变，调用方拿到的还是那份「只给摘要」的旧委托器。

**三道锁（缺任一道，网关一个正文字节都拿不到）。** 本层不替任何一道松口，
也不写「前两道过了就当第三道也过」的推断（internal/server/knowledgecontent30.go:10-31）：

1. **平台开关**（上面那段）决定「哪些源参与」；
2. **管理员授权**决定「这个人、这个范围，这次能不能带内容」—— 两道，
   `knowledge.content` + read 与 `body.raw` + read；
3. **源侧逐篇再判定**决定「这一篇给不给」：每篇必须带 `rule_id`，
   且 `digest` 与准入阶段那批准入的摘要 + 交付字节**双重锚定**，对不上整篇丢弃。

**线侧代定的四件。**

1. **协议版本**：正文交付用**独立**常量
   `knowledge.ContentProtocolVersion = "llmproxy-knowledge-content-v1"`
   （internal/knowledge/content.go:14-24），与检索的 `llmproxy-knowledge-acl-v1` 分开、
   同样精确匹配。理由：共用一个版本等于「换检索协议包版本号顺手改了正文能力」，
   而那是行为变更不是格式变更。检索那条链**一个字段都没动**，
   所以 `return_raw_body` 不写时行为与裁决前逐字节相同。
2. **正文生命周期**：只在**单次请求的内存里活着**，用完即清零
   （E 侧 `defer ClearContent()`，internal/processor/content.go:245 起；
   接线侧交付失败时把已收字节清零后才返错）。载体只有一个，且钉在测试里：
   `knowledge.Passage.Verbatim` 是本包**唯一**登记在册的正文字段
   （internal/knowledge/leak_test.go:64-79），`assertCarrierRegistry` 钉死
   「恰好 1 个类型 / 1 个字段 / 必须是 []byte（string 无法清零）」，
   多一个字段就必须改这条用例、也就是必须过一次评审。
   `ReturnedDocument`（检索响应）仍然没有任何正文字段。手册 §3.C 那句
   「任何结构体都不得持有文档正文」在开关打开后不再逐字成立，换成三条同样硬、可执行的说法：
   词表照旧全量生效且唯一豁免必须逐类型逐字段登记；从任何会被序列化（落库、落日志、回客户端）
   的形状出发沿 JSON 字段图到不了那个载体；真交过一次正文之后审计 JSON、单行日志、
   错误文案、丢弃记录里都不出现那份明文。**守卫没有放松，是换了可执行的表达式。**
   正文不进任何持久字段、不进日志、不进回放记录。
3. **审计动作**：`knowledge.content` 与检索的 `knowledge.search` 分成两行 ——
   「问到过」与「原文真的进过网关」是两条不同的合规事实，合成一行就没法单独统计。
   三种必写形态：真有正文进过内存（`delivered_count > 0`）、这一源交付失败、
   网关侧兜底**丢过篇目**。第三种必须有：那正是「问到过内容但一个字都没进 prompt」的
   唯一留痕处，少了它「摘要不符」这类协议不符在审计表里和「压根没有内容」长得一样。
   「零交付、零失败、零丢弃」**不写行**：那是源侧对这批篇目回答「都没有可交付正文」，
   而注入发生在每一条请求上，逐条抄一遍等于把审计表养成第二张流量表；
   那一次的证据在处理器留痕里（`event=processor` 的 entries 带结论码
   `knowledge_no_content` / `knowledge_grant_missing`）。
   **审计写不进去就不交付**：落库失败 ⇒ 清零 + 报错，正文一个字都不会进 prompt。
   detail 只带条数、源名、字节数与结论码，**不含正文明文与任何凭证**。
4. **上游分级门落点**：注入侧逐篇判 `p.DataLevel.Exceeds(in.Policy.DataLevel)`，
   越级或分级不明（`LevelUnknown`）**整篇丢弃**而不是截断（截断后的字节对不上准入阶段那个
   摘要，等于一边声称「这是那篇文档」一边交付另一份字节）。这一条与路由的候选门
   `ctx.DataLevel.Exceeds(offer.Candidate.MaxDataLevel)` 排除（internal/routing/plan.go:259-264）
   合起来是**传递闭合**：注入内容不超过本次请求的生效上限，而该上限已被选中的供应商承接。
   于是 §8「现状」里那条形状约束（请求侧处理器看不见候选供应商）**不需要被打破**，
   `PickFromPreferring` 的次序与 `processor.Request` 的字段集合一个都没改 ——
   没有为了让链条看见候选而新增隐式输入。

**两条执行期口径（本会话踩实，不是推测）。**

- **通配主体不构成授权。** `AllowsKnowledgeContent` / `AllowsRawBody`
  （internal/policy/resolver.go:217、:246）只认 `ReasonExplicitAllow` / `ReasonGroupAllow`，
  且**命中的授权条目自身**必须带 `expires_at` —— 不能用 `Decision.ExpiresAt` 代替，
  那个值是「规则与身份里较早的到期点」，身份 TTL 会让一条永不过期的授权看起来有期限，
  于是永久出网授权被静默放行。落到现场：`subject: "*"` 走 default allow 判为
  `knowledge_content_grant_missing` / `raw_body_grant_missing`，处理器**跳过而非拒**、零出网。
  因此一份能跑的夹具策略包必须给 `subject: <用户名>`（用户 token 的链只有 `user:<name>`）
  与 `subject: gateway`（静态 key 的链是 `system:gateway`）**两套**显式 allow，
  一条注入声明要同时命中两条链。
- **审计归属跟着主体走。** 用户请求的 `egress.allow`（原文出网授权留痕）写在
  `user:<name>` 而不是 `system:global`（`requestAuditScope30`）；
  按范围查留痕的测试 helper 若统一查 system 就会读出 0 条，看起来像「没出网」而实际是找错格子。

**注入声明自己的五条硬约束**（internal/processor/spec.go:274-318，缺任一条加载期即拒）：
`phase` 只能 `before-upstream`（排在它前面的 pii-mask / sidecar 会把第三方文档当用户正文处理，
前者打码掉本该作为依据交付的内容，后者把整份第三方文档送到外部端点）；
`body_access` 至少 `transform-body`；**必须**声明 `allow_raw_body`
（委托协议只在 `allow_raw_terms` 为真时带检索词，没有「送脱敏检索词」这种形态 ——
不写就是永远取不到内容，而它看起来像「知识库里没查到」）；必须给 `allowed_endpoints`；
`scope` **不能留空也不能写 `*`**（每次命中都要做一次正文准入判定、一次可能出网的委托、
一条 `egress.allow` 留痕；全局命中把这三件变成默认行为，而「哪些范围带内容进上下文」
是运营逐条决定的粒度；`kind:*` 放过）。请求期还会**逐个复查**交付器此刻报出的端点
是否仍在白名单内（知识源段可热更新），少列一个即「配置漂移」拒绝出网 ——
那一发同样是出网，没有只算一半的道理。

   未拍板前不自作主张扩权（详见 docs/3.0-knowledge-delegation.md 正文交付一节）。
3. **「注入多少」超限的处理与子口径不同形，这条要主线认。** §0 第 1 条第三条原话是
   「超限**截断**并记一条差异而不是拒整个请求」，落地的做法是**整篇丢弃 + 按类别计数**
   （`dropped["budget"]`）。不拒请求这一半满足；截断这一半**故意没做**，理由是
   截断后的字节对不上准入阶段那篇文档的摘要，等于一边声称「这是那篇」一边交付另一份字节 ——
   而摘要双重锚定正是第三道锁的实现凭据。要么主线认「整篇丢弃」这个替换，
   要么就得改成「截断的那一篇不再声称对应原摘要」（那是协议形态变更，不是实现细节）。
   字节与篇数上限走声明参数（`processor_params/<名>.json` 的 `max_passages` /
   `max_total_bytes`，可省；缺省 8 篇 / 64KiB，越界一律回落缺省而不是「放到最大」），
   「源数」那一半由 `allowed_endpoints` + 知识源段共同界定。
4. **默认关与「用户级不得自助开启」两条已按子口径落地并锁住**（第 2 条：不写开关逐字节不变，
   `TestKbContentSwitchOffRefusesWithoutEgress`；第 1 条：注入声明的 `scope` 不能是 `*`
   且要逐范围声明，而参数文件里写不出交付器与判定器，所以用户侧没有自助开启的入口）。
   「用户级范围不得自助开启」这一句今天靠**声明表本身在平台配置文件里**这条结构性事实成立，
   不是靠一条运行时权限判断 —— 若以后把处理器声明开放给用户写，这条必须补成显式判定。
5. **计量口径一个字没动，因此注入的成本在账单维度没有对应物。** playbook §3.F 边界
   （docs/3.0-agent-playbook.md:360「禁止：改变现有计量语义」）照旧成立：prompt token 全部
   由上游回报（internal/executor/scan.go:297-299 只从响应体 `usage.prompt_tokens` 取值），
   注入侧不做任何本地计数、不新增计量字段。后果要说全：注入了哪几篇、进了多少字节，
   在**账单与消费维度查不到**（只体现为 prompt token 变多、费用变高），能查到的只有
   `knowledge.content` 那一行审计（条数 / 源名 / `delivered_bytes` / 结论码）。
   如果运营需要「按范围的注入成本」这种报表，那是新增计量口径而不是补一个 bug，
   要另开裁决 —— 接线侧不趁 P5 顺手把成本归因塞进费用表。

## 9. 组织与项目上下文从哪来（org/project 那一半授权的最后缺口）

> **裁决（2026-10-05，§0.1 第 11′/12′/13′/14′ 行）：C｜外部权威签发，落地包 P8。**
> 实施路径同时定了：**每请求带 IdP token、网关校验**（现有网关 key / 用户 token 继续管

> 提出时（2026-10-04，P5 收尾）的原始口径：这一条不是「再改一次过滤逻辑」—— P7 已经把导出侧
> 的 `kind:id` 全串与链匹配打通，缺的是**请求路径上今天没有 org/project 这个事实**。

**现状（三处读数，都可复核）。**

1. `internal/identity` 的 claim → 范围链映射只在领域包里跑：全仓 import 它的只有
   `examples/university/`（两个文件），`internal/server/` 与 `cmd/` 一条都没有。
2. 请求路径上的链由 `policyChainFor(scope)` 拼（policy30.go:495-500；另外三个调用点
   knowledge30.go:224、policyadmin.go:218、procexec.go:73）—— 取值只有两种：有路由作用域
   ⇒ `user:<名>`，没有 ⇒ `system:global`。`policyIdentity`（:505-510）同形。
3. 存储侧没有可 join 的地方：`users` 表没有任何 org / project 列。

**影响要说全，不要只说「导不出来」。** 按 org / project 写的策略规则**在 enforce 下也匹配不上
真实流量** —— 缺的不是证据面，是**授权本身只在 `user:` 与 `system:` 两格上评估**。于是三件事一起
停在门口：① P7 那条链匹配只有单元层证据（docs/3.0-stage-summary.md §4 第 22 条）；
② 组织级 deny（「某学院不得用某模型」）写出来不会命中，而管理台的策略编辑器允许写出这种
永不命中的规则；③ 知识库按组织准入（playbook §2.9 那种 `organization:` 主题形态）在真流量上
只能退化成 subject 相等。

**候选方案。**

- **A｜维持现状**：org / project 只在参考实现与策略包语法里存在，等真实身份源接入再说。
  代价必须在文档与管理台文案里说破：能配出今天永不命中的规则，而静默失配比报错更糟。
- **B｜本地成员关系表**：`users` 加两列或新建一张 `memberships`，管理 API 写、`policyChainFor` 读。
  不需要 IdP，现网当场可部署；代价是多一套**要人维护的归属数据**，一旦与源系统（学校的
  LDAP / HR）漂移，授权结论跟着错，而错的方向通常是「权限还留着」。
- **C｜每请求带范围的凭证**：网关自己签发（OIDC 登录）或校验下游交上来的 IdP token，
  把范围声明放进请求上下文。归属事实由外部权威负责，网关不复制一份；代价是新增一条认证链路
  与密钥面（`PseudonymKey` 那条「密钥不接受文件注入」的理由在这里同样适用）。

**接线侧建议：C，先把「谁签发、谁校验、失效怎么传」定下来；在那之前按 A 走，并把 A 的失配
写进管理台与策略文档的口径里。** 不选 B 的理由不是工作量：它把「权限归属」变成网关里的第二份
真相，而 playbook §3.B 的边界是身份层只提供身份与组织上下文、不决定权限 —— 一份需要人工同步的
归属表迟早长成第三份。

**迁移影响与测试影响（选哪个都要一起定的）。** B 要 `store` 三方言各加列 / 表并过
`test-matrix.sh`（与 §4 那条落库裁决同形）；C 要扩 `policy.Identity` 的 `source` 词汇
（今天只有静态与用户两类），新语义按 §2.7 规则 4 必须带版本与迁移说明。三条不变量与方案无关：
链里带 org 时 org 级 allow / deny 各自命中、subject 与 org 冲突时 deny 优先、
**没有任何 org 数据时行为与今天逐字节相同**（向后兼容这句不能靠「应该没影响」）。

**需要谁决定。** 主线：归属事实的权威源在网关内还是网关外 —— 这是架构与合规口径，不是实现细节。
