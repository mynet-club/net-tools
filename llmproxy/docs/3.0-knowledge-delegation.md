## 1. 这一层的定位与唯一权威来源

本包只做一件事：把「一次请求能触达哪些知识库、上限是哪一级数据」结构化，然后**交给外部知识源，由知识源自己完成文档级鉴权并返回它判定可读的文档**（`doc.go:1-32`）。

「返回它判定可读的文档」在**检索方向**只意味着摘要与判定依据（§4.3），这句话没有因为正文通道而变松；
文档正文字节只能经 §4.8 那条**独立协议、独立入口、独立审计动作**交付，且默认关。

权限判定只有两个现场，且层级不同：

| 层级 | 权威来源 | 入口 | 代码位置 |
|---|---|---|---|
| 知识库级准入 | `internal/policy` 的 `Resolver`：资源 `knowledge:<id>` + 动作 `read` | `AdmitKnowledgeBases(r, ctx, chain, candidates, now)` | `scope.go:188`、`scope.go:204`（资源名由 `ResourceForKB` 生成，`scope.go:97`） |
| 单篇文档准入 | **知识源自己** | `DelegatedRetriever.Retrieve(ctx, req)` | `delegation.go:142` |

**playbook §3.C 的禁止项落在哪里：**

- 「不得根据客户端传来的文档标签自行判权限」——协议里**根本不存在**能声明「这篇对这个主体可读」的入站字段。`RetrieveRequest`（`delegation.go:56-80`）传的只是上下文（主体、范围、用途、分级上限、知识库白名单），没有任何文档级结论；网关侧唯一的文档级判读是 `hardConstraint`（`filter.go:168`）与 `protocolViolation`（`delegation.go:369`），它们只检查「返回项是否**超出**我给它的上下文」和「形态是否合规」，从不读取标签文本。
- 参考实现侧同样自证：`FakeRetriever` 的 ACL 选择器集合 `ReadableBy` 只存在于源侧内部（`fake.go:31-33`、`fake.go:331` `subjectMayRead`），其语义（`*` / `subject:` / `user:` / `organization:` / `project:`，`fake.go:60-66`）**刻意不复用** `policy` 的主体选择器，网关完全不认识它。
- 为什么必须这样分工：文档 ACL 的事实（谁在哪个部门、哪份档案挂在哪个项目、哪份合同归档在哪个库）只在知识源那一侧完整存在；网关这一侧只有「哪个库能碰」。网关若靠客户端传来的标签自行判定，等于把**最不完整的一份数据当成权威来源**（`doc.go:5-7`）；两处规则各判一次必然漂移，而漂移的方向永远是「多放行」（`scope.go:19-21`）。

## 2. KnowledgeScope

`KnowledgeScope` 是**派生物，不是权限模型**（`scope.go:12-20`）：范围取自 `policy.ScopeChain`（B 包展开），分级上限取自 `policy.DataLevel`（A 包判定），知识库集合取自 A 包判定结果。

### 2.1 字段清单（`scope.go:21-30`）

| 字段 | `json:` | Go 类型 | 必填 | 语义 |
|---|---|---|---|---|
| `Chain` | `chain` | `policy.ScopeChain` | 必填，非空 | 本次请求覆盖的结构化范围集合（`user` / `organization` / `project`），直接引用 A 包对象，不复制同构结构体 |
| `KnowledgeBases` | `knowledge_bases` | `[]string` | 可空 | 已准入的知识库**稳定 ID** 集合，排序去重。空集合合法，含义是「一个都不许碰」，`Resolve` 直接短路（`resolve.go:89`） |
| `MaxDataLevel` | `max_data_level` | `policy.DataLevel` | 必填，`Valid()` | 本请求可触达文档的最高分级。零值 `LevelUnknown` 被拒（不是 public） |

构造与校验：`NewKnowledgeScope(chain, maxLevel, knowledgeBases)`（`scope.go:46`）与 `Validate()`（`scope.go:69`）。两者都做同一套检查，因为字段全是导出的、接线方可能手构；手构的空 chain 若不在入口报错，会一路走到 `Filter` 变成「所有文档都被兜底丢弃」这种难查故障（`scope.go:63-68`）。测试：`TestKnowledgeScopeValidation`、`TestBuildRequestRejectsBadInputs`、`TestResolveRejectsMissingInputs`。

错误变量：`ErrScope`（`scope.go:34`）、`ErrKBID`（`scope.go:36`）、`ErrAdmission`（`scope.go:38`）。

### 2.2 与 `policy` 的派生关系

```
policy.ScopeChain（B 展开）──┐
policy.DataLevel（A 判定）  ──┼─► NewKnowledgeScope ─► KnowledgeScope ─► BuildRequest ─► RetrieveRequest
AdmitKnowledgeBases（A 判定）─┘        （scope.go:46）                    （delegation.go:217）
```

- `AdmitKnowledgeBases`（`scope.go:188`）对每个候选库调 `r.Evaluate(ctx, chain, ResourceForKB(kb), policy.ActionRead, now)`，只按 `decision.Allowed` 分入 allowed / denials。**不参与 deny 优先、过期、conditions 排序，也不做兜底放行**；`resolver == nil` 返回 `ErrAdmission` 而不是「全部允许」（`scope.go:189-191`，测试 `TestAdmitKnowledgeBasesRequiresPolicyKernel`）。
- 拒绝明细类型 `KnowledgeBaseDenial{KnowledgeBase, Reason policy.Reason}`（`scope.go:175`）：原因码来自 **A 包**的 `policy.Reason`（如 `ReasonDenyRule`、`ReasonEntitlementExpired`、`ReasonNoMatchingRule`、`ReasonContextInvalid`），不是本包码。测试：`TestAdmitKnowledgeBasesUsesPolicyEngine`、`TestAdmitKnowledgeBasesDenyBeatsAllow`、`TestAdmitKnowledgeBasesHonoursExpiry`、`TestAdmitKnowledgeBasesRespectsScope`、`TestAdmitKnowledgeBasesRejectsDirtyIDs`、端到端 `TestAdmissionFeedsScopeAndAuditEndToEnd`。
- 知识库 ID 形态：`ValidateKnowledgeBaseID`（`scope.go:88`）→ `validateStableID`（`reason.go:151`）：非空、≤256 字节、无首尾空白、**禁冒号**（资源名 `knowledge:<id>` 只允许一个分隔符）、无控制字符。

### 2.3 分级上限如何参与判定

链路是单向的，只有一个生效点：

1. `KnowledgeScope.MaxDataLevel` → `BuildRequest` 写入 `RetrieveRequest.MaxDataLevel`（分级**名**字符串，`delegation.go:231`）；
2. 网关侧兜底：`Filter` 取 `ceiling := req.MaxDataLevelValue()`（`filter.go:106`），逐篇 `doc.Level().Exceeds(ceiling)` → 丢弃并记 `ReasonLevelExceeded`（`filter.go:177`）；
3. 命中集最高分级 `FilterResult.MaxDataLevel = MaxKnowledgeLevel(citations)`（`filter.go:153`、`filter.go:256`）；
4. §2.3 组合：`EffectiveLevelFor(userLevel, hitDocsMaxLevel)`（`filter.go:283`）= `policy.EffectiveLevel(user, public, knowledge)`。**`detected_level` 恒传 `LevelPublic`**，因为本层不读正文、没有正文可检测；检测档位归 E 包分类器，由接线方再合并一次。零命中时 `MaxKnowledgeLevel` 返回 `LevelPublic` 而非 `LevelUnknown`，否则 §2.3 组合直接报错把「没检索到」升级成链路故障（`filter.go:251-256`，测试 `TestMaxKnowledgeLevel`、`TestEffectiveLevelFor`）。

`KnowledgeScope.LevelAllows(level)`（`scope.go:116`）是给接线方复用的等价判断（任一侧 `LevelUnknown` 返回 false），`Filter` 本身走 `req` 派生的 ceiling，两处不同时生效是刻意的：判定只用过线一次的上下文，避免同一规则有两个现场。

### 2.4 有效期与过期语义

`KnowledgeScope` 自身**没有** TTL 字段。时效分三处，口径统一为「`now` 等于边界即过期」：

| 对象 | 字段 | 判定函数 | 过期后果 |
|---|---|---|---|
| 委托上下文 | `IssuedAt` / `Deadline`（`context.go:61-62`） | `RequestContext.Expired(now)`（`context.go:204`）、`Validate(now)`（`context.go:125`） | `Resolve` 直接返回错误，不发委托（`resolve.go:68`；测试 `TestRequestContextValidation` 子用例「过期上下文」、`TestResolveRejectsMissingInputs`） |
| 整份判定结果 | `RetrieveResponse.ExpiresAt`（`delegation.go:126`） | `Filter`（`filter.go:96-104`） | 整份作废：每条都记 `ReasonACLExpired`，`HitCount=0`，`MaxDataLevel=public`（测试 `TestFilterDropsExpiredDecisions`「整份判定过期时一条都不留」、`TestResolveDropsUntrustworthySourceResponses`「判定已过期的整份响应」） |
| 单篇判定 | `ReturnedDocument.ExpiresAt`（`delegation.go:109`） | `hardConstraint`（`filter.go:183`） | 只丢该篇，`ReasonACLExpired`（测试 `TestFilterDropsExpiredDecisions`「单篇判定过期」） |

结果级 TTL 是知识源给的（`delegation.go:124-126` 注释：没有它就会把一次鉴权结论缓存到 ACL 已改之后，形成「已撤销仍可读」）。策略版本变更的归因走 `RequestContext.PolicyVersion`（测试 `TestResolveReflectsPolicyVersionChange`），准入集合随策略包升版收缩（`TestAdmissionFeedsScopeAndAuditEndToEnd` 末段）。

### 2.5 序列化规则

- 时间：`time.Time` 默认编码，即 RFC3339（playbook §5）。断言见 `TestBuildRequestCarriesAuthorizationContextOnly`（检查 `"issued_at":"2026-04-01T12:00:00`）。
- 稳定排序：知识库集合、组织/项目集合、原因码列表一律走 `sortUniqueStrings`（`reason.go:198`）/ `Reasons`（`reason.go:96`）；文档遍历前先 `sortReturnedDocuments`（来源 ID → 知识库，`filter.go:296`）；引用排序 `SortCitations`（知识库 → 来源 ID → 摘要，`citation.go:233`）。目的只有一个：同一输入序列化出同一份 JSON，摘要与回放才谈得上对齐。
- **`policy.DataLevel` 在 Go 结构体 JSON 里是整数**（A 包 `DataLevel` 是 `int`，无 `MarshalJSON`）：`KnowledgeScope.MaxDataLevel`、`RequestContext.EffectiveLevel`、`Outcome.KnowledgeLevel` 落为 Rank 数字。线上协议不同——`RetrieveRequest.MaxDataLevel` 是**分级名字符串**（`delegation.go:68`，用序号会被跨语言实现当自定义档位按字典序比，`delegation.go:93-95`）。结论：`KnowledgeScope` / `RequestContext` 的 JSON 形态只用于内部存储与调试，**不能直接当线上协议体**，上线一律走 `BuildRequest`。
- `Budget`（`time.Duration`）在 `RequestContext` JSON 里是纳秒整数；线上协议另有 `budget_ms`，由 `BuildRequest` 单向转换（`context.go:49-51`、`delegation.go:236`），禁止反向靠默认值猜。
- `omitempty` 对 `time.Time` 无效：零值仍会序列化为 `"0001-01-01T00:00:00Z"`。网关按 `IsZero()` 理解（`filter.go:96`、`filter.go:183`），**源侧实现不要把 `0001-01-01T00:00:00Z` 读成「早已过期」**，它等于「未设置」。

## 3. 检索请求上下文 RequestContext

`RequestContext`（`context.go:52-63`）是一次委托必须携带的上下文。它存在的意义：**没有它，知识源就只能凭「谁在问」猜权限**——缺任何一项，源侧只能选择全给或全不给（`context.go:39-51`）。

| 字段 | `json:` | 类型 | 必填性 | 缺失后果（校验点） |
|---|---|---|---|---|
| `RequestID` | `request_id` | `string` | 必填，≤128 字节稳定 ID（`maxRequestIDLen`，`reason.go:143`） | 响应串号检查失去基准、审计断链；`validateFields` 报 `ErrContext`（`context.go:138`） |
| `Subject` | `subject` | `string` | 必填稳定 ID，且拒邮箱/手机号形态（`validateSubjectID`，`reason.go:176`） | 源侧无从鉴权；PII 形态会被拒——邮箱一旦进审计，「被拒的理由」本身就成了个人信息落库 |
| `Chain` | `chain` | `policy.ScopeChain` | 必填非空，**必须包含 `user:<subject>`**（`context.go:151-157`） | 漏主体自身时组织级/项目级规则会以为自己面向整个组织；报 `ErrContext` |
| `Purpose` | `purpose` | `string` | 必填，≤64（`maxPurposeLen`），禁 `\r\n\t` | 配额、出网与保留策略都按用途区分；空值报错 |
| `EffectiveLevel` | `effective_level` | `policy.DataLevel` | 必填 `Valid()` | 零值 `LevelUnknown` 不等于 public，直接拒（`context.go:167`） |
| `PolicyVersion` | `policy_version` | `string` | 必填，≤512（`maxPolicyVersionLen`），禁空白 | 审计无法归因；必须来自 `BundleSet.Filter(chain).PolicyVersion()`，禁止 handler 拼接（`context.go:45-47`；样板写法见 `admit_test.go:357` `admittedVersion`） |
| `Budget` | `budget` | `time.Duration` | 必填 `>0` 且 `≤ MaxBudget`（30s） | 超上限**报错而不静默夹紧**：夹紧会让调用方以为配了 60 秒实际只有 30 秒，排查方向完全错（`context.go:89-98`，`WithBudget`） |
| `MaxResults` | `max_results` | `int` | 必填 `1..MaxResultsCeiling`（100） | 条数直接放大提示词体积与费用（`context.go:185-190`） |
| `IssuedAt` | `issued_at` | `time.Time` | 必填非零 | 过期判定与 `budget_ms` 推导失去基准 |
| `Deadline` | `deadline` | `time.Time` | 必填且晚于 `IssuedAt` | 源侧没有限时依据；`WithDeadline` 只允许收窄（`context.go:110`，放宽等于让下游替整条链路续期） |

默认值：`NewRequestContext` 填 `Budget = DefaultBudget`（3s）、`MaxResults = DefaultMaxResults`（10），`Deadline = IssuedAt + Budget`（`context.go:19-25`、`context.go:70-87`）。派生方法：`Remaining(now)`（永不为负，`context.go:208`）、`UserScope()`、`ScopeDisplay()`（只进日志，禁止当存储键）。全部缺失/越界用例集中在 `TestRequestContextValidation`、`TestBuildRequestRejectsBadInputs`。

## 4. 委托协议

### 4.1 接口形状

```go
type DelegatedRetriever interface {                                  // delegation.go:142
    Retrieve(ctx context.Context, req RetrieveRequest) (RetrieveResponse, error)
}
type NamedRetriever interface {                                       // delegation.go:150
    DelegatedRetriever
    RetrieverName() string
}
```

实现方必须逐条满足（`delegation.go:131-141`）：

1. **自己完成鉴权**：按 `req.Subject` + `req.Chain` + `req.Purpose` 判定每篇文档是否可读，逐条给出 `Allowed` 与 `RuleID`；
2. 不接受调用方传来的任何「这篇可读」标签——协议里没有这种字段；`req.KnowledgeBases` 只是知识库白名单（A 包判定）；
3. 任何失败（超时、鉴权依赖不可用、字段缺失）必须以 `error` 返回，调用方按 fail_closed 处理成「不可读」；**返回空文档列表 ≠ 失败**，而是「没有可读文档」（`TestResolveStaysEmptyWhenSourceReturnsNothing`）；
4. 必须可并发复用：不得把一次请求的状态存在自身字段上（`TestHTTPRetrieverIsReusableUnderConcurrency`、`TestResolveIsReusableUnderConcurrency`）；
5. 不得返回文档正文与标题明文。**这一条对检索协议（`RetrieveResponse` / `ReturnedDocument`）仍然逐字成立、一个字段都没放开**；文档正文只能走**另一个协议**（`DeliverContent`，见 §4.8），且只在平台开关 + 管理员授权 + 源侧逐篇再判定三道锁同时在场上时才交付。裁决记录见 docs/3.0-decision-packages.md §8.1。

`NamedRetriever` 只允许报名字，不报端点与凭证：审计表很多人能读到，「哪台内网机器在提供检索」本身就是可被利用的信息（`delegation.go:146-153`）。审计里落在 `AuditEvent.Retriever`（`resolve.go:79`、`resolve.go:164`）。

协议版本握手字段 `ProtocolVersion = "llmproxy-knowledge-acl-v1"`（`delegation.go:19`）写在每次请求与响应里，破坏性变更必须升版本号并走主线评审。

### 4.2 请求体 JSON（`RetrieveRequest`，`delegation.go:56-80`）

| `json:` | 类型 | 必填 | 语义 |
|---|---|---|---|
| `protocol_version` | string | 必填，须等于 `ProtocolVersion` | 字段语义对齐 |
| `request_id` | string | 必填 | 链路关联 + 响应串号校验键 |
| `subject` | string | 必填，非 PII 形态 | 主体稳定 ID |
| `chain` | `[{"kind","id"}]` | 必填非空，含 `user:<subject>` | `policy.ScopeRef` 序列化形态（A 包 `scope.go:31-33`） |
| `purpose` | string | 必填 | 用途 |
| `organization` | string | 可选 `omitempty` | 主归属**提示**，鉴权仍以 `chain` 为准；取 `scope.Organizations()[0]`（排序后第一个，保证稳定，`delegation.go:240-243`） |
| `knowledge_bases` | `[string]` | 必填非空，逐个 ID 校验 | 网关侧已准入的集合；源侧**只能在这个集合之内**返回 |
| `max_data_level` | string | 必填，四级名之一 | 分级上限 |
| `policy_version` | string | 上下文层必填 | 注意：`RetrieveRequest.Validate()` 未单独校验它（见 §10 已知限制） |
| `max_results` | int | 必填 `1..100` | 结果数上限 |
| `issued_at` / `deadline` | RFC3339 | `deadline` 必填非零 | 源侧限时依据 |
| `budget_ms` | int64 | 可选 | `Deadline-IssuedAt` 的毫秒数，供无法解析 RFC3339 时兜底限时 |
| `query_digest` | string | 必填 | 检索词的**域分隔**摘要（`Query.Digest`，`delegation.go:53-55`；域常量 `citation.go:42`）；空检索词也有摘要（对空串取摘要），让「没检索词」与「摘要没算」可区分 |
| `search_terms` | string | `omitempty`，仅 `allow_raw_terms=true` 时出现 | 检索词原文 |
| `allow_raw_terms` | bool | `omitempty` | 原文携带授权标志 |

`search_terms` 的门控是 §2.9 正文访问契约在检索层的镜像：检索词本身就是用户内容（「我的裁员赔偿怎么算」），默认只送摘要，只有 `Query.AllowRawTerms=true` 才送原文；**未授权时该字段连出现都不出现**，免得对端把「空检索词」当成「检索全部」（`delegation.go:244-248`；测试 `TestBuildRequestRawTermsGate`、`TestHTTPRetrieverSendsRawTermsOnlyWhenGranted`）。

装配入口 `BuildRequest(rc, scope, q, now)`（`delegation.go:217`）：先 `rc.Validate(now)` + `scope.Validate()`，切片的复制（`Chain`、`KnowledgeBases` 各自 `append(nil, ...)`，测试断言共享切片问题见 `TestBuildRequestCarriesAuthorizationContextOnly`），最后 `req.Validate()` 自检。

### 4.4 HTTP 传输层（`http.go`）

`HTTPRetriever`（`http.go:41-53`）只做四件事：装配 JSON 请求、限时限体积读取、把状态码与失败翻译成稳定原因码、校验响应协议。**不做任何权限判断**（`http.go:37-40`）。

请求：

- 方法与端点：`POST` 到 `Endpoint`（`http.go:166`）。单一入口，路径由管理员配置（测试用 `/retrieve`，`http_test.go:142`），无发现机制、无分页游标。
- 头：`Content-Type: application/json`、`Accept: application/json`、`X-Request-Id: <request_id>`（`http.go:170-173`）。**刻意不设 `Authorization`**：凭证属于注入的 transport 层，一旦在本结构里存 token 就会顺着 JSON 进审计和错误信息（`http.go:174-175`；断言 `TestHTTPRetrieverHappyPath` 检查 `Authorization` 为空）。
- 体：`RetrieveRequest` 的 JSON。

响应约束：

| 约束 | 常量/位置 | 违反后果 |
|---|---|---|
| 媒体类型 | 只接受主类型 `application/json`（`contentTypeJSON`，`http.go:26`；`mimeMainType`，`http.go:298`） | `retrieval_protocol_invalid`；头值原值不回显（对端可控，会顺着 Detail 进审计） |
| 超时 | `context.WithTimeout(ctx, budgetFor(req))`（`http.go:154-164`）+ `TransportDo` 钉死 `http.Client.Timeout`（`http.go:87-108`）。`budgetFor` = `min(time.Until(req.Deadline), FallbackBudget)`，`FallbackBudget` 缺省 `DefaultBudget`(3s)、上限夹到 `MaxBudget`(30s)；`Deadline` 为零值时取 `FallbackBudget`；算出 `≤0` 时**不出网**直接失败 | `retrieval_timeout` |
| 响应体上限 | `MaxResponseBytes`，缺省 `DefaultMaxResponseBytes` = 1 MiB（`http.go:22`）；读 `limit+maxReadOverhead`（1 字节）探测是否超限（`http.go:209-219`）；失败路径的 `drainAndClose` 同样限量（`http.go:312-318`） | `retrieval_response_too_large` |
| 结果条数上限 | 解析层 `maxProtocolDocs` = 1000（`delegation.go:25`，`ValidateEnvelope`）；使用层 `req.MaxResults` ≤ 100（`Filter` 再截一次，`filter.go:143-149`） | 前者整份拒绝，后者逐条 `document_over_result_limit` + `Truncated` |
| 重定向 | 不跟随：`CheckRedirect` 返回 `http.ErrUseLastResponse`（`http.go:106`） | 3xx 原样作为 `retrieval_upstream_status` 报出 |
| transport | 必须由注入方提供 `DoFunc`（`http.go:35`）；`TransportDo(nil, ...)` 返回一个**立刻失败**的闭包，绝不回落 `http.DefaultTransport`（`http.go:88-96`） | `retrieval_transport_not_configured` |

目标约束（playbook §5「所有外部调用必须设置 timeout、body limit 和目标约束」）：本包**没有** `AllowedTargets` 之类的白名单结构。目标约束由三件事共同承担——

1. 端点由管理员固定配置，`validateEndpoint`（`http.go:326-351`）拒：空、非 `http`/`https`、缺主机、**URL 内嵌凭证**、fragment、查询串（可变入口会让端点无法固定比对），并做空白归一化与尾部 `?` 修剪；
2. 不跟随 3xx，避免被改写的 DNS 或反向代理把请求带到出网白名单之外而审计仍记原端点；
3. 出网路径由注入的 transport（通常是 `internal/dialer` 造出的受策略约束的 transport）承担，本包不新建 client。

缺口：本包不校验目标主机名/网段是否在该知识源被授权的集合内（配置被改写时本包无从拒绝）。要更硬的目标约束，需在接线层加 `AllowedTargets` 校验，见 §10。

### 4.5 传输层现象 → 原因码 → Outcome 形态

`Reason` 是本包**独立词表**（`reason.go:23-53`），不与 `policy.Reason` 合并：policy 解释「这次使用为什么被允许/拒绝」，这里解释「检索委托这一步发生了什么、哪一篇被兜底丢弃」。未注册的原因码在 `AuditEvent.Validate` 期直接失败（`reason.go:56-71`、`audit.go:99`）。语义同源的三条显式登记在 `policyMirrors`（`reason.go:82-86`）：`knowledge_level_exceeded → ReasonDataLevelDenied`、`cross_organization_denied → ReasonScopeMismatch`、`knowledge_base_not_allowed → ReasonScopeMismatch`，其余一律无映射（超时等事实策略层根本不知道，硬映射等于给审计造假）。测试：`TestReasonCodesAreStableAndMirrorsRegistered`。

失败错误类型 `RetrievalError{Reason, StatusCode, KB, Detail, Cause}`（`delegation.go:168-181`）：`Error()` 只拼 `reason` / `status` / `kb` / `detail`（`delegation.go:184-197`）；`Cause` 标 `json:"-"`，**只用于 `errors.Is/As` 归类、绝不进 `Error()` 文案**——底层文案可能带内网地址、响应片段甚至文档内容（JSON 解码错误会回显上下文字节），而错误既进日志也可能回显给调用方（`delegation.go:176-179`、`resolve.go:205-213`）。测试：`TestErrorMessagesCarryOnlyStableIDs`。

| 传输层/协议现象 | 原因码 | `Outcome` 形态 |
|---|---|---|
| `retriever == nil` | `ErrRetriever`（普通 error，非 `RetrievalError`） | `Resolve` 返回 `(nil, err)`：无 Outcome、无审计（`resolve.go:65-67`） |
| `rc` / `scope` 前置校验失败（含上下文过期） | `ErrContext` / `ErrContextExpired` / `ErrScope` / `ErrKBID` | `(nil, err)`：无 Outcome、无审计 |
| `BuildRequest` 失败 | `retrieval_protocol_invalid` | `Outcome` 非 nil、`err` 非 nil、零引用、审计 `result_code=retrieval_protocol_invalid`（`resolve.go:99-105`） |
| `req.Validate()` 不通过（未出网） | `retrieval_protocol_invalid`（Detail「请求字段不符」） | `(空响应, RetrievalError)` |
| `Endpoint`/`MaxResponseBytes`/`Do` 配置不全 | `ErrEndpoint`/`ErrNoTransport` 普通 error → 经 `asRetrievalError` 归一为 `retrieval_dependency_unavailable` | `(Outcome, err)`，零引用 |
| transport 为 nil 的注入闭包 | `retrieval_transport_not_configured` | 同上 |
| 剩余预算 `≤0`（未出网） | `retrieval_timeout` | 同上 |

| `context.DeadlineExceeded` / transport `Timeout()` | `retrieval_timeout` | 同上 |
| DNS/连接拒绝/TLS 等其他传输失败 | `retrieval_dependency_unavailable`（`Cause` 保留分类事实） | 同上 |
| 非 2xx（含未被跟随的 3xx） | `retrieval_upstream_status` + `StatusCode` | 同上；响应体**不读**（知识源的 403 页面常带文档标题甚至片段，`http.go:186-195`） |

| 响应 JSON 非法 | `retrieval_protocol_invalid` | 同上（解码错误原文不外流） |
| 外壳不符：版本、缺/串号 `request_id`、条数 > 1000 | `retrieval_protocol_invalid`（Detail「响应外壳校验失败」） | 同上 |
| 知识源返回未授权文档（`allowed:false`） | `document_not_readable_at_source` | **成功**：`err=nil`、该篇丢弃、留 `DropRecord` |
| 判定依据缺失（`rule_id` 空/含空白） | `document_acl_evidence_missing` | 同上 |
| 摘要缺失/非法 | `document_digest_invalid` | 同上 |
| 分级名非法 | `document_level_unknown` | 同上 |
| 协议字段缺失（`source_id`/`kb`/`owner_*`/自由文本码/负分） | `document_protocol_field_missing` | 同上 |
| 知识库不在白名单 | `knowledge_base_not_allowed` | 同上 |
| 分级超上限 | `knowledge_level_exceeded` | 同上 |
| 归属越出本次范围（组织/项目不在 chain） | `cross_organization_denied` | 同上 |
| 归属为他人的 `user` | `document_subject_mismatch` | 同上 |
| 单篇或整份判定过期 | `document_acl_expired` | 单篇丢该篇；整份作废时零引用 + `result_code=retrieval_no_hits` |
| 同 `(kb, source_id)` 重复 | `document_duplicate` | 完全相同留第一条；**摘要冲突则两条一起丢**（无第三种信息可判哪版可信，`filter.go:219-249`） |

`IsFailClosed(err)`（`delegation.go:211`）恒为 `err != nil`。这个函数存在是为了把「任何检索失败都不等于放行」写成代码而不是文档（`delegation.go:206-211`）。

### 4.6 `Filter` / `Resolve` 的兜底与「替知识源判权限」的区别

`Filter` 是**网关侧硬约束的兜底再收一道**（`filter.go:62-80`），不是文档权限判定。区别必须说清，否则这一层看起来像越权：

- 知识源判定：掌握文档 ACL 的全部事实，回答「这篇对这个主体可读吗」——唯一的权限判定现场；
- `Filter`：只知道交给它的那份上下文（`req.Chain` / `req.KnowledgeBases` / `req.MaxDataLevel`），**只丢弃任何超出这份上下文的返回项**。它从不因为「知识源没说不行」而放行，也从不按文档自带的标签文本判权限。一句话：**Filter 只能让结果集合变小，永远不可能变大**（可执行断言：`TestFilterNeverWidensTheResultSet`）。

为什么要这一道：知识源配错（把组织 A 的库挂进组织 B 的白名单）、或响应在并发扇出中被串号时，越权文档会直达模型上下文；网关这一侧唯一还兜得住的就是「你返回的东西不在我给你的范围内，丢弃」。丢弃必须给原因码——没有原因码的丢弃等于「静默几篇没了」，排查只能靠猜。

`hardConstraint` 的检查次序固定：`allowed` → 知识库白名单 → 分级上限 → 归属范围 → 判定时效（`filter.go:159-187`）。次序固定的意义是**原因码可复现**：否则一次策略调整会让同类事件在码分布上随机变化，看不出真实原因。协议形态问题由 `protocolViolation` 先判——形态不符与越界是两种故障，混成同一个码就分不清「对端没实现协议」和「对端给了范围外的文档」。

相关性分数的排序属于呈现层：兜底判定不能被分数影响，否则「分数高」就等于「可以越范围」，那是把排序当权限（`filter.go:292-295`）。`Score` 只是透传到 `Citation.Score`（`citation.go:133`），不参与任何判定。

### 4.8 正文交付通道（决策包 §8.1，2026-10-04 独立落地）

**它是第二个协议，不是 v2。** `ContentProtocolVersion = "llmproxy-knowledge-content-v1"`
（`content.go:14-24`）与检索的 `llmproxy-knowledge-acl-v1` 分开、同样精确匹配。
理由写在邻行注释里：检索 v1 的字段集合是一句被测试锁住的承诺（「只有摘要，没有正文」），
而正文交付的成立条件比检索多两道（平台开关 + 管理员授权 + 源侧逐篇再判）。
塞进同一次握手会让「没开开关的部署」也得在协议层解释正文字段的语义；
分开之后**检索那条链一个字节都没动**，`return_raw_body` 不写时现网行为与裁决前逐字节相同。
入口也分开：`HTTPRetriever.DeliveryEndpoint`（`http.go:424-…`）独立于 `Endpoint`，
配置层禁两者相同（`config/procconf.go:257-287`）——共用一扇门就没法在「只开检索」的部署里
于网络层单独关掉正文通路。这条比较**忽略末尾斜杠**（`/retrieve` 与 `/retrieve/` 也算相同）：
多数路由与按前缀匹配的出网白名单把它们当同一扇门，只按字符串相等判的话，这条禁令就是
改一个字符能绕过的形式。用例 `TestKnowledgeContentSwitchValidation`
（`procconf_test.go`，含斜杠与空查询串两条正反对照）。

**三道锁，缺任一道网关一个正文字节都拿不到**（接线侧口径见
`internal/server/knowledgecontent30.go:10-31`）：

| 锁 | 谁持有 | 判据 | 不成立时的表现 |
|---|---|---|---|
| ① 平台开关 | 管理员（`knowledge_sources[].return_raw_body`） | 决定「哪些源参与」 | 装配期就没有交付器，处理器报「没有开启正文交付的知识源」 |
| ② 管理员授权 | A 包 `Resolver`（**唯一真值源**） | `knowledge.content` + read **且** `body.raw` + read，两者都只认显式或组级 allow、且**授权条目自身**必须带 `expires_at` | E 侧结论码 `knowledge_grant_missing`，`Output{Body: nil}` ⇒ **跳过而非拒**，零出网 |
| ③ 源侧逐篇再判定 | 交付实现自己 | 每篇必须带 `rule_id`；`digest` 要同时等于准入阶段那个摘要与交付字节自己的 sha256 | 整篇丢弃 + `dropped_reasons` 计数 |

`search_terms` 那道门在这里同样存在：交付请求发出前接线侧会**再判一次** `body.raw`
（同一个 Resolver、同一个上下文），因为「把原文检索词写进委托请求」本身就是一次出网；
少任何一次判都是「某一处出网没人问过授权」。
**通配主体不构成授权**：`subject: "*"` 走 default allow 会被判
`knowledge_content_grant_missing` / `raw_body_grant_missing`（`policy/resolver.go:217、:246`）——
一条全局兜底放行不该顺手把原文能力发给所有处理器。

**接口形状。**

```go
type DelegatedContentDeliverer interface {                    // content.go:383-395
    DeliverContent(ctx context.Context, req ContentRequest) (ContentResponse, error)
}
type NamedContentDeliverer interface { ... }                   // 只许报名字，不许报端点与凭证
func DeliverContents(ctx, deliverer, rc, scope, admitted []ReturnedDocument,
                     maxPassages, maxTotalBytes int, now) (*ContentOutcome, error)  // content.go:530-…
```

实现方必须逐条满足（`content.go:385-392`）：① **自己再判一次**这一篇正文可否交付并给 `RuleID`
—— 上一次检索 `Allowed=true` 不等于正文可交付（分级、脱敏状态、库策略都可能不同）；
② 只交付 `req.Documents` 里申请过的那几篇，`Digest` 必须是**本次交付字节**的 sha256；
③ 任何失败以 `error` 返回，调用方按 fail_closed 处理成「没有正文」，
而**返回空 `passages` ≠ 失败**（那是「这些篇都没有可交付正文」，`result_code=content_none`）；
④ 可并发复用；⑤ 不得返回与 `ExpectedDigest` 不符的字节。

**请求体 `ContentRequest`**（`content.go:77-96`）：身份字段与 `RetrieveRequest` 同形
（`subject` / `chain` / `purpose` / `knowledge_bases` / `max_data_level` / `policy_version` /
`issued_at` / `deadline` / `budget_ms`），因为源侧要回答的是同一个问题
「这个人有没有权拿到这篇正文」，而不是复用上次检索的结论（那次结论可能已经过期）。
新增的是 `documents[]`（每篇 `source_id` + `knowledge_base` + **`expected_digest`** + `expires_at`）
与两个预算位 `max_passages` / `max_total_bytes`。
`expected_digest` 必须来自**同一次准入检索**返回的那个摘要（`BuildContentRequest` 保证），
它是网关唯一能把「被授权的那一篇」与「被交付的那一篇」钉在一起的凭据；
`ContentAsk.validate`（`content.go:61-70`）要求**完整摘要**而不是截断形式——
截断会碰撞，撞上了就等于把 A 篇的授权当成 B 篇的。
`Validate`（`content.go:123-…`）另加：链必须含 `user:<subject>`、`documents` 非空且逐项不重复
（同一篇申请两次会被拒，重复申请在正文方向等于给同一份内容两个进 prompt 的机会）、
`max_passages ∈ 1..100`（`maxContentPassages` = `MaxResultsCeiling`，`context.go:25`）、
`max_total_bytes ∈ 1..1MiB`、`deadline` 非零、每个申请项的 `knowledge_base` 都在允许集合内。
预算写成**请求字段**而不是只留在网关本地：源侧知道上限就能在自己的排序里先裁掉给不下的篇目。

**载体与生命周期。** `Passage`（`content.go:200-218`）是本包**唯一**被登记允许持有文档正文字节的类型，
字段是 `Verbatim []byte`——用 `[]byte` 而不是 `string` 是刻意的：string 不可变，
§2.9 规则 2 要的「处理完立即释放」落不了地（赋 nil 只让那份字节继续活在别的字符串头里）。
`ClearContent()`（`content.go:220-231`）就地清零并丢引用；被丢弃的篇目在 `DeliverContents` 里
**按下标**（不是按 Key，重复篇与保留篇同键）清零，外壳不合格时 `clearPassages` 先于返回执行
（`encoding/json` 出错前会写入已完成的字段，「能被 GC」不等于「已清零」）。
`ContentOutcome.Passages` 标 `json:"-"`：这份结构 marshal 出去也不会带正文。
`ContentAuditEvent` 里只有量级：`requested_count` / `delivered_count` /
`delivered_bytes` / `dropped_count` / `dropped_reasons` / `delivered_digests`。
那个字段名刻意不叫 `content_bytes`、方法不叫 `ContentBytes`（`content.go:765-768`），
好让 leak 守卫继续「见 `content` 即红」而不必开特例。

**逐篇兜底（每一条都是整篇丢弃，绝不截断）。** 截断后的字节对不上准入阶段那个摘要，
等于一边声称「这是那篇文档」一边交付另一份字节。`protocolViolation`
（`content.go:258-310`）与后续判定的码表：

| 现象 | 原因码（`reason.go:57-69`） |
|---|---|
| `source_id` / `knowledge_base` / `decision_reason` 形态不符、`rule_id` 缺失或带空白与控制字符、空正文 | `content_field_missing` / `content_evidence_missing` |
| `data_level` 解析不出 | `document_level_unknown` |
| 摘要非 64 位十六进制 | `document_digest_invalid` |
| 单篇超 `AbsoluteMaxPassageBytes`（256 KiB） | `content_too_large` |
| 交付了没申请过的篇 | `content_document_not_requested` |
| `digest` ≠ `expected_digest`，或 `digest` ≠ `sha256(verbatim)` | `content_digest_mismatch` |
| 申请项的库不在允许集合内 | `knowledge_base_not_allowed` |
| 同一篇重复交付 | `document_duplicate` |
| 分级越出本次 `scope.MaxDataLevel` | `knowledge_level_exceeded` |
| **交付方**声明的这篇 `expires_at` 已过（撤权残留：源侧完全可以交一份「当初授权、此刻已撤」的正文） | `content_expired` |

**字节与条数预算是整份门槛，不是逐篇裁**（`ValidateEnvelope`，`content.go:324-360`）：
版本不符、串号、条数超硬上限（100 篇）、**条数超过本次请求的篇数**、条数超 `max_passages`、
总字节超 `max_total_bytes` ⇒ 整份拒绝。逐篇裁会让「哪几篇进了 prompt」
取决于丢弃顺序与对端返回顺序，回放与审计都说不清；整份拒绝是一个可解释的二值事实。
绝对上限（`content.go:29-43`）：单篇 256 KiB、整次 1 MiB、一次申请与一次交付都到不了 100 篇以上；
声明缺省时网关取保守值 8 篇 / 64 KiB，写 0 或越界一律回落缺省 ——
「0 = 不限」这种读法等于允许把任意大的正文留在网关内存里。
`ContentOutcome` 的不变量与 `Outcome` 同形：`Failure` 非空时 `Passages` 必定为空，
调用方不需要（也不应该）写「失败就用已经拿到的部分正文」那种分支，那正是 fail_open 的入口。

**HTTP 传输**（`http.go:418-…`）与检索同一套纪律：`POST` 到 `DeliveryEndpoint`、
只接受主类型 `application/json`、不设 `Authorization`（凭证属于注入的 transport）、
不跟随 3xx、非 2xx 一个字节都不采纳（知识源的 403 页面常写着文档标题甚至正文片段）、
transport 必须由注入方提供且预算为零时**不出网**。读取上限取
「配置上限」与「`max_total_bytes` + 每篇 1 KiB 外壳」的较大值（`contentLimit`，`http.go:404-416`）：
只按配置判会把一份合法交付误读成超限，而字节预算本身已被绝对上限钉死，不会因此放开无限内存。

**出网端点必须两个都算。** 接线层用
`KnowledgeContentEndpoints()` 枚举 `endpoint` + `contentEndpoint` 并排序
（`internal/server/knowledgecontent30.go`），E 侧 `checkEndpoints`
（`processor/content.go:367-385`）在**每次请求**复查交付器此刻报出的每个端点仍在
`allowed_endpoints` 内 —— 知识源段可热更新，只信构造期那一次校验，白名单就成了
「注册当时的白名单」而不是「每次出网的白名单」。检索入口也算进来不是凑数：那一发同样是出网。

**审计动作**：`knowledge.content`，与检索的 `knowledge.search` 分行 ——
「问到过」与「原文真的进过网关」是两条不同的合规事实。
三种必写形态（真交付 / 本源交付失败 / 网关侧丢过篇目）与「零交付零失败零丢弃不写行」的取舍、
以及「审计写不进去就不交付」这条硬线，记在决策包 **§8.1**。

**fake 腿**：`FakeRetriever.DeliverContent`（`fake.go:562-…`）实现同一套源侧再判定，
单篇选择器 `VerbatimBy` / `VerbatimRuleID` 用来演示「检索说可读、正文却不给交付」和
「缺 `rule_id` 的交付」这两种真实缺陷形态；fake 里的明文只活在 `IndexedText` 与交付字节里，
`TestFakeNeverPutsPlaintextOnTheWire` 与 `TestContentChannelKeepsPlaintextInOneCarrierOnly`
钉住它不出现在协议响应、引用、审计 JSON 或丢弃记录上。

## 6. 引用摘要 Citation

`Citation`（`citation.go:100-117`）是文档在本包里的唯一存在形式：**只有摘要，没有正文，也没有标题明文**。

| 字段 | `json:` | 必填 | 来源 |
|---|---|---|---|
| `SourceID` | `source_id` | 是 | 知识源侧稳定文档 ID（不是标题、不是 URL） |
| `KnowledgeBase` | `knowledge_base` | 是 | 请求白名单内的库 ID |
| `OwnerKind` / `OwnerID` | `owner_kind` / `owner_id` | 是（`system` 归属时 `OwnerID` 可空） | 文档归属，供回源与展示 |
| `DataLevel` | `data_level` | 是，四级名（`NewCitation` 统一小写去空白） | 源侧声明 |
| `DigestAlgorithm` | `digest_algorithm` | 是，恒 `sha256` | 常量 `DigestAlgorithm`（`citation.go:19`） |
| `Digest` | `digest` | 是，64 位小写十六进制 | **由知识源侧计算**，网关在检索方向不重算——那边没有正文可算，这正是「不持有正文」的证据。正文交付方向**反过来必须重算**：`sha256(交付字节)` 不等于申报摘要就整篇丢弃（§4.8 的摘要双重锚定），因为那一侧确实拿到了字节 |
| `TitleDigest` | `title_digest` | 是，同上形态 | 源侧对标题做域分隔摘要 |
| `Score` | `score` | 否，非负 | 透传，不参与判定 |
| `RuleID` | `rule_id` | 是 | 源侧判定依据（审计链的关键，缺失等于「网关不知道这篇为什么可读」） |
| `AclVersion` / `RetrievedAt` | `acl_version` / `retrieved_at` | 否 | 源侧世代；时刻取 `evaluated_at`，否则 `now` |

摘要构成：

- 内容摘要：`Digest(content []byte)` = `sha256` 小写 hex（`citation.go:44`）。`content` 参数是**唯一**允许正文出现的地方，且只在本次调用的栈上存活；本包任何结构体与字段都不保存它，也不保存切片视图。`DigestString(s)` 是 string 入口（`citation.go:50`）。
- 摘要算法名写进结构而不是靠约定：摘要没有自描述能力，将来迁移更强哈希（或某源用了别的算法）时，不带算法名的历史审计再也分不清是哪套算的（`citation.go:14-19`）。
- 标题摘要：`TitleDigest(title)` = `sha256("<len(domain)>:llmproxy-kb-title-v1;<len(trimmed)>:<trimmed>")` 的小写 hex（`citation.go:35-59`）。长度前缀避免「A|B」与「AB」撞摘要（`TestDigestAndTitleDigest`）；`TrimSpace` 归一化让同一标题两次索引能对上。
- **为什么标题也要摘要**：标题经常含人名与项目代号（`doc.go:26`、`delegation.go:85-86`），落进网关审计就是个人信息落库。另外标题低熵、词汇可枚举，直接 `sha256(title)` 可被字典攻击离线还原——域前缀只挡住「跨系统复用同一份彩虹表」这一条路，**不能当成加密手段**。因此展示一律走 `ShortTitle`/`ShortDigest`（截断 48 bit，`citation.go:24-31`、`citation.go:66`），需要精确等值关联时才用完整摘要。检索词摘要 `Query.Digest` 与标题摘要共用同一个域前缀规则（`citation.go:49-72`，两个域常量分别为 `llmproxy-kb-title-v1` / `llmproxy-kb-query-v1`），口径一致才不会让同一段明文在 query 位和 title 位撞出同一个值（见 §10 第 17 条）。**两者现在只在一处不同**：检索词在网关这一侧算，所以它有带密钥的那一半 —— `Query.Pepper` 非空时走 `keyedDomainDigest`（HMAC-SHA256），为空时退回无密钥的 `domainDigest`；标题摘要在知识源侧算，网关无从加密钥，所以恒为无密钥形式（`citation.go:38-47`）。
- 等值判定必须用完整摘要：`SameDocument` 比 `SourceID` + `KnowledgeBase` + 完整 `Digest`（`citation.go:214`）。用截断形式会把两篇不同文档当成一篇，进而**把 A 篇的授权当成 B 篇的授权**。`Key()` 用 `\x00` 分隔（`citation.go:208`）同理。
- `ValidateDigest`（`citation.go:77`）拒空值、非 64 位、非十六进制、大写——审计里出现「半截摘要」时事后无法判断是被截断还是原始就短，回放和取证失去依据（用例 `TestDigestAndTitleDigest`、`TestFilterDropsMalformedDocuments`「内容摘要被截断」）。
- `Display()`（`citation.go:224`）是 `kb/sourceID@sha256:<12 位截断>`，只出现摘要与稳定 ID。
- **正文从不入库的口径**：本包不写库（`audit.go:207-212` 只定义 `AuditSink` 接口，落库由实现方负责），任何结构体都没有正文字段；`Outcome`、`FilterResult`、`AuditEvent`、`DropRecord`、`RetrievalError` 一律只带摘要与稳定 ID。下游要展示内容时凭 `SourceID` 回源知识源、由源侧重新鉴权，而不是让网关缓存副本——文档权限会变，网关里的副本不会跟着变，于是「已撤销的文档」还能被翻出来（`citation.go:96-99`）。
  **开关打开之后这句话怎么读**（§8.1）：「不入库」从来没有依赖过「内存里没有正文」这个前提，它依赖的是**没有任何持久形状能到达正文**。§4.8 那个载体（`Passage.Verbatim`）只在一次请求的内存里活着、用完 `ClearContent()` 清零，`ContentOutcome.Passages` 标 `json:"-"`，`ContentAuditEvent` 只带 `delivered_count`/`delivered_bytes`/摘要；`TestContentCarrierIsUnreachableFromPersistedShapes` 把「从任何会被序列化落库、落日志、回客户端的形状出发沿 JSON 字段图到不了那个载体」钉成用例。缓存副本仍然禁止：交付到的正文只进本次请求将要出网的 prompt，不进任何跨请求结构。

引用排序：`Filter` 内部按稳定键判定后产出，`SortCitations` 是唯一排序函数（知识库 → 来源 ID → 摘要），`TestSortCitationsIsStable` 钉死「与输入顺序无关」；`TestFilterIsDeterministicRegardlessOfInputOrder` 钉死整条兜底路径的确定性。

## 7. 审计事件 AuditEvent

`AuditEvent`（`audit.go:27-74`）字段集合是刻意收窄的**白名单**：

`request_id`、`subject`、`subject_ref`、`chain`、`purpose`、`allowed_knowledge_bases`、`queried_knowledge_bases`、`query_digest`、`hit_count`、`dropped_count`、`dropped_reasons`、`max_data_level`（命中文档最高分级，即 §2.3 的 `knowledge_level`）、`request_max_data_level`（本次上限；两者一起才看得出被上限截掉多少）、`result_code`、`failure_detail`、`policy_version`、`acl_version`、`truncated`、`duration_ms`、`started_at`、`finished_at`、`retriever`、`citation_digests`。

明确**不记录**：文档正文、标题明文、检索词原文、知识源侧 ACL 规则内容。连检索词原文也不记——检索词就是用户提问的一部分，记原文等于把正文换个表再存一遍，§2.9「正文不落库」当场失效；要复盘具体内容，用 `request_id` 去对齐知识源侧的访问日志，那里才有完整事实和做鉴权的那套权限上下文（`audit.go:21-26`）。

`allowed_knowledge_bases` 与 `queried_knowledge_bases` 的区分用来回答「查不到是因为没授权，还是因为授权了但库里没有」——短路时 `queried` 为空（`TestResolveShortCircuitsWithoutAdmittedKnowledgeBase`、`TestResolveStaysEmptyWhenSourceReturnsNothing`）。

保证不记录正文的四层手段（测试名点名）：

1. **类型层面的词法关**：`leak_test.go` 的反射词法扫描 `fieldScanner.walk` 递归展开 `scannedStructs()`（`leak_test.go:112-136`，检索与正文两套协议 + 引用 + 审计 + 失败 + 结果，**载体自己也进扫描**）的字段名与 `json:` 标签，命中 `body / payload / fulltext / content / text / snippet / excerpt / paragraph / raw / secret / password / credential / api_key / token / private_key / base_url / verbatim …`（`leak_test.go:54-62`）即失败。断言扫描的字段数 `≥ 150`（`leak_test.go:161`）——防止「递归其实没展开、测试永远绿灯」。测试：`TestNoStructInThisPackageHoldsDocumentBody`。
   **`verbatim` 是随正文通道新加的禁词**，而唯一的豁免必须是 `contentCarriers` 里**逐类型逐字段**登记的条目（`leak_test.go:64-79`：`Passage.Verbatim`）。豁免不写成「按字段名放行」，否则 `Passage` 以后再加第二个正文字段就自动过关。`assertCarrierRegistry`（`leak_test.go:179-203`）把这条钉成三条断言：登记项**恰好 1 个类型 / 1 个字段**（多一个就要改测试、也就是必须过一次主线评审）、登记的字段必须**真实存在**于那个类型上（改过名却留着登记 = 豁免给了一个不存在的字段，而真正的新字段反而自由放行）、字段类型必须是 `[]byte`（`string` 无法清零，§2.9 规则 2 落不了地）。对照用例：`TestSecondCarrierFieldOnTheCarrierIsCaught`（换个类型抄一份 `Verbatim` 照样红 / 登记类型上的同名字段必须绿）、`TestContentChannelKeepsPlaintextInOneCarrierOnly`。
   其余例外只有两类，都写在 `isAllowedException`（`leak_test.go:89-99`）而不是散落在注释里：`raw` 只许出现在**布尔开关**字段上（`Query.AllowRawTerms` / `RetrieveRequest.AllowRawTerms` / `ContentAsk` 方向没有原文开关），`text` 只许出现在不参与本扫描的 `FakeDocument` 上（理由记在 `fakeStructReason`，`leak_test.go:101-107`）。
2. **扫描器的反向对照**：`TestBodyFieldWouldBeCaught` 用一个人造的 `badCitation`（含 `Body`/`Snippet`/`APIKey`/`Payload`/`Excerpt`/`Verbatim`）证明扫描器真的会拒绝它们，同时证明布尔 `AllowRawTerms` 不被误判。少了这条，前面的绿灯可能只是扫描器本身写错了。
3. **运行时序列化兜底**：`TestPopulatedFixturesSerializeWithoutContent` 用填满值的样本逐个 `json.Marshal` + `assertNoLeak`（标记串是 `secretBody` / `secretTitle` / `rivalBody` / `"正文-"` / `"标题-"` / `"报销流程说明"` / `"项目预算表"`，`leak_test.go:19-27`），并覆盖 `Citation.Display()` 与 `AuditEvent.String()`；`TestFakeNeverPutsPlaintextOnTheWire` 覆盖知识源响应 JSON、引用集合、审计 JSON、丢弃记录 JSON。
4. **持久形状不可达**（正文通道独有）：`TestContentCarrierIsUnreachableFromPersistedShapes` 从每一个会被落库、落日志、回客户端的形状出发沿 JSON 字段图走，断言走不到 `Passage.Verbatim` —— 这就是「不入库」在开关打开之后的可执行形式。清零义务另有 `TestDroppedPassageContentIsZeroed`：被兜底丢弃的篇目字节必须在返回前清零，而不是等 GC。
5. **序列化点再挡一层 PII**：`AuditEvent.MarshalJSON`（`audit.go:130`）与 `String()`（`audit.go:146`）在输出前按 `looksLikePII`（`@` 或 11 位以上纯数字，`audit.go:180`）把 `subject` 换成 12 位截断摘要 `subject_ref`，原文消失。这里在 `Validate` 之外再兜一层，是因为手构事件可以绕过校验、而日志是最容易把个人信息永久留在别人能读到的地方的一条路径。测试：`TestMarshalRedactsPIISubject`；`validateSubjectID`（`reason.go:176`）在入口就拒邮箱/手机号形态。
6. **凭证字段单独复查**：`TestReflectionSeesNoCredentialFields` 用凭证词表（`secret/password/api_key/token/private_key/authorization …`）扫一遍——本包结构里根本不存密钥，认证属于注入的 transport。

`AuditEvent.Validate`（`audit.go:80`）本身会拒：未注册的 `result_code` / `dropped_reasons`、空 `chain`、缺 `purpose`、非法 `query_digest`、负计数或负耗时、缺 `policy_version`、`finished_at` 早于 `started_at`、非法 `citation_digests`。原因码一旦发布就进审计表：只能追加，禁止重命名或用旧值表达新语义（`reason.go:22-23`）。

Sink 侧：`AuditSink`（`audit.go:210`，实现必须可并发调用）、`AuditFunc`（`audit.go:215`）、`NopAudit`（`audit.go:227`，默认丢弃而不是默认落库：接线阶段先保证不写坏别人的表）、`AuditRecorder`（`audit.go:232`，内存环形缓冲，`Record` 先跑 `Validate`，不合格的事件只加 `rejected` 计数不进缓冲——测试里出现构造错误应表现为「事件缺失 + Rejected 非零」，而不是一条半成品混进断言）。**`Resolve` 不主动写 sink**，它只把事件放进 `Outcome.Audit`，由调用方决定投递（并发写入用例：`TestResolveIsReusableUnderConcurrency`，断言 `Rejected()==0`）。

## 8. 跨组织隔离与范围校验

规则（`filter.go:189-216` `coversOwner`；对外同义实现 `scope.go:153` `KnowledgeScope.CoversOwner`）：

| 文档声明的归属 | 判定 | 不满足时的码 |
|---|---|---|
| `system` | 跳过本项检查（分级与知识库白名单仍生效；它不属于任何组织） | — |
| `user` | 必须**等于**本次 `subject` | `document_subject_mismatch` |
| `organization` / `project` | 必须**精确**存在于本次 `chain` | `cross_organization_denied` |
| 归属形态非法（`Validate` 失败） | 丢弃 | `document_subject_mismatch` |

**本包不猜「项目属于组织」的层级**：层级由各适配器（B/G）展开成完整 `ScopeChain` 传进来，与 `policy` 包约定一致（`filter.go:192-194`，playbook §2.7 与 A 包 §5）。

「范围不匹配要报错，而不是静默 deny」是本层的一个专门设计（对应任务书 §8）：

- `Filter` 进门先 `req.Validate()`（`filter.go:82`）——空 `chain`、非法 `chain`、缺 `user:<subject>` 都返回 `ErrProtocol`，**整次判定失败**；如果放任空 chain 走下去，表现会是「所有归属都不在集合内 ⇒ 所有文档被兜底丢弃」，症状和「知识源坏了」一模一样，难查且掩盖了真正的接线漏传（`scope.go:63-68`）。
- `NewKnowledgeScope` / `Validate` / `AdmitKnowledgeBases` 三个入口同样把空 chain 当错误（`scope.go:46-50`、`scope.go:192-195`）。
- `Resolve` 再兜一次 `len(rc.Chain) == 0`（`resolve.go:75-76`）。
- A 包的口径被原样照抄：漏传范围不能被解释成「不限范围」（`docs/3.0-policy-domain.md` §3 第 4 条）。

跨组织隔离用例（端到端）：

- `TestFilterDropsCrossOrganizationDocuments` —— 邻组织文档、别的项目文档、他人 `user` 文档各留自己的码，本组织 + `system` 归属两篇留下，且邻组织文档的**摘要**不出现在引用里；
- `TestResolveKeepsCrossOrganizationDataApart` —— alice（`example-org`）与 mallory（`example-rival-org`）共用同一个 fake 知识源，各自的引用摘要集合**完全不相交**，且每次过线的白名单只是各自准入的子集；
- `TestAdmitKnowledgeBasesRespectsScope` —— 规则只发给邻组织范围时，alice 连知识库级准入都拿不到；
- `TestHTTPRetrieverEndToEndStaysFailClosed` —— 真实 HTTP 形态的「源侧实现不完整」（邻组织文档 + 白名单外库 + 正文形状字段一起返回），端到端只留 1 篇，且引用/审计一行/审计 JSON 全部 `assertNoLeak`；
- `TestResolveHappyPath` —— 跨分级的 `doc-2` 被 `knowledge_level_exceeded` 兜掉，而不是采信源侧结论。

## 9. 与相邻包的边界

- 本包唯一的仓库内依赖是 `internal/policy`（`scope.go:9`、`context.go:9`、`delegation.go:10`、`filter.go:8`、`resolve.go:9`、`citation.go:11`、`audit.go:11`、`fake.go:11`）。**不 import** `internal/config`、`internal/store`、`internal/server`、`internal/router`（`doc.go:28-29`）；其余依赖全是标准库（`context`、`net/http`、`encoding/json`、`crypto/sha256`、`mime`、`net/url`、`sort`、`sync` 等）。
- 不 import `internal/dialer`：出网策略通过 `DoFunc` / `TransportDo` 注入（`http.go:29-35`、`http.go:83-109`），本包不自建 client，避免绕过出网控制。
- 不接分类器：`detected_level` 在 `EffectiveLevelFor` 里恒为 `LevelPublic`（`filter.go:277-282`），检测归 E，路由归 D。**§4.8 之后这条仍然成立**：本包拿到正文也不判定它——`DeliverContents` 采信**源侧申报级**并用本次 `scope.MaxDataLevel` 做上限兜底，对交付字节不做任何内容检测（`sha256` 只用于一致性锚定）。要不要对注入内容再跑一次分类器（§0 第 1 条「取较高者」那个子口径）是 E/接线的决定，见 docs/3.0-decision-packages.md §8.1「仍然要如实标出来的五件」第 2 条。
- 时钟一律显式传 `now`：`NewKnowledgeScope` 之外的所有判定入口 `AdmitKnowledgeBases(..., now)`、`NewRequestContext(..., now)`、`Validate(now)`、`BuildRequest(..., now)`、`Filter(..., now)`、`Resolve(..., now)` 都吃注入时钟（`doc.go:30-31`）。唯一读墙钟的两处：`http.go:253`（`time.Until(req.Deadline)` 计算实际可用超时——超时本身只能吃墙钟）与 `resolve.go:112-118` 的耗时测量（观测值，不参与任何判定，且对负值夹零）。
- 本包不注册 HTTP handler、不写数据库、不接指标：`AdmitKnowledgeBases` → `NewKnowledgeScope` → `NewRequestContext` → `Resolve` → sink 的串联在**接线层** `internal/server/knowledge30.go`（§3.C 运行期接线）。接线层只做「组装上下文 + 落审计 + 出网来源」，任何权限判断仍然只发生在策略内核与本包的兜底 Filter 里；把这条边界写死，是为了以后换执行路径时不必重新证明「谁有权读哪篇」。

5. 无 `AllowedTargets` 结构：本包不校验目标主机名/网段是否在该源被授权的集合内（§4.4）。管理员把端点改到别的主机时，本包只会拒绝非 http(s)/带凭证/带 query 的形态，不会拒绝「主机不对」。
6. `RetrieveRequest.Validate()`（`delegation.go:256-301`）**不校验** `policy_version`、`issued_at`、`budget_ms`、`allow_raw_terms`。`policy_version` 与 `issued_at` 由 `RequestContext.Validate` 保证（`context.go:170-176`、`context.go:191-193`），但**源侧直接用 `req.Validate()` 自检时不会拒缺 `policy_version` 的请求**。
7. 不处理 `Content-Encoding`（gzip 响应会在 JSON 解码处判 `retrieval_protocol_invalid`）；不请求也不校验 `Content-Length` 与实际长度的关系（体积只由 `io.LimitReader` 约束）。
8. `RetrieveResponse.DecisionReason`（整次层面，`delegation.go:127-128`）网关侧既不校验也不读取；`ReturnedDocument.DecisionReason` 只做字形校验、不校验是否注册、且不会传播到 `Citation` / `AuditEvent`。也就是说这两个「补充说明码」目前只在协议里存在、在结果里消失。
9. 响应体不回传 `policy_version`：网关无法校验「源侧判定用的是哪一版策略」，只能靠 `request_id` + 审计里的请求版本做间接关联（源侧若有自己的策略世代，用 `acl_version` 承载）。
10. `Outcome.Dropped` 的逐条记录**不进审计**（`AuditEvent` 只有 `dropped_count` 与 `dropped_reasons`）；要看「哪一篇被丢」必须持有 `Outcome` 本身。`DropRecord.Validate()`（`filter.go:324`）在包内没有调用点。
11. `HTTPRetriever` 的字段（`Endpoint` / `Do` / `MaxResponseBytes` / `FallbackBudget` / `Name`）全是导出的、可并发修改。「实现必须可并发复用」的前提是**构造后不再改字段**（测试里 `client.MaxResponseBytes = 512` 这类改法只能出现在并发用例之前）。没有不可变构造路径。

**判定与观测细节（含与注释的偏差）**

12. `protocolViolation` 对 `rule_id` 的必填检查发生在 `allowed` 检查之前（`filter.go:119` 先于 `filter.go:123`）：`allowed:false` 且缺 `rule_id` 的文档报 `document_acl_evidence_missing`，而不是 `document_not_readable_at_source`。**这是实现的选择而非偏差**——缺依据的丢弃篇同样要进审计，不能因为结论是 false 就免掉形态检查；`delegation.go:402-407` 的注释已按这个口径写清。对接方要按码分布理解这一点：`document_acl_evidence_missing` 计数非零说明源侧字段实现不完整，与「有多少篇被拒」无关。
13. 前置校验失败（`retriever` 为 nil、`rc`/`scope` 不合法、上下文过期）返回 `(nil, err)`，**不产出 `Outcome`、不产出审计事件**——这些 fail_closed 事件目前只能靠调用方自己打日志留痕（`resolve.go:65-76`）。
14. `ReasonContextExpired`（`reason.go:30`）已注册但**没有任何代码路径产生它**：过期上下文走 `resolve.go:68` 的普通错误分支。同理要注意 `no_knowledge_base_allowed` / `retrieval_no_hits` / `retrieval_ok` 是结果档位而不是失败码。
15. `HTTPRetriever` 的部分失败不带 `KB` 字段：`ReasonResponseTooLarge`（`http.go:215-219`）、JSON 解码失败（`http.go:222-225`）、`ReasonProtocolInvalid` 的两个装配分支（`http.go:151`、`http.go:168`）与 `ReasonUnavailable`（`http.go:182`）只带 `Reason`/`Detail`。审计归因到「哪一路」时这几条形同缺失。
16. `HTTPRetriever.Validate` 用 `ErrEndpoint` 报「响应体上限必须为正」（`http.go:127-129`），语义上更像 `ErrRetriever`/`ErrProtocol`；不影响判定方向（仍然是拒）。
17. `Query.Terms` 无长度上限（`AuditEvent`/`RetrieveRequest` 的摘要长度由 `ValidateDigest` 约束，明文检索词只在 `allow_raw_terms=true` 时出现且仍受请求体上限约束）。检索词摘要与标题摘要同为**域分隔**摘要（`citation.go:36-72`：`llmproxy-kb-query-v1` / `llmproxy-kb-title-v1`，长度前缀拼接），跨用途不会撞出同一个值，所以审计里「搜过这个词」不能拿去离线命中「存在这么一份文档」（测试 `TestFakeNeverPutsPlaintextOnTheWire`、`TestDigestAndTitleDigest`）。**同一域内的字典攻击已关掉**（2026-10-05 裁决，决策包 §0.1 第 18′ 行；此前这条写的是「真正的兜底是接线阶段给审计摘要加 HMAC 密钥，本包不做」）：`Query.Digest` 在 `Pepper` 非空时产出 HMAC-SHA256 的域分隔摘要，密钥是接线侧从 `master.key` 派生的 `kb-query-digest` 子密钥（`secrets.Cipher.Derive`，与 `pii-mask` 假名那把互不相干）。本包**仍然不持有也不管理主密钥**，只多收一个 `Query.Pepper` 字段 —— 这是「不持有正文」那条口径在密钥面的同构说法：包负责形状与判定，密钥归接线侧。`Pepper` 为空时如实退回无密钥摘要（生产形态下只剩一种情况能到这里：`master.key` 不可读也不可写 —— `main.go:333` 是无条件 `LoadOrCreate`，所以单用户实例同样拿得到派生密钥；库里已有用户却拿不到密钥时是拒绝启动，不走到这一步），接线侧必须在装配期打一行 WARN 说清代价与出路（`knowledge30.go`），不能静默当成配好了。摘要算法变更没有协议版本位可记（本包协议无 schema version 字段），但源侧从不消费 `query_digest`（`fake.go:370-377` 只用 `search_terms` 做全文匹配），而当前无任何生产审计行，因此这次改口径无需迁移；**要迁移的是运维-side 的认知**：换主密钥等于换掉全部历史检索摘要的口径，旧行不能再拿去和新行逐位比（代价写在 README「假名与检索摘要的密钥位」一节）。
18. `KnowledgeScope.CoversOwner`（`scope.go:153`）与 `filter.go:195` 的 `coversOwner` 是同一规则的两份实现，包内调用方只有测试；同类「导出但包内未使用」的还有 `LevelAllows`、`Projects`、`SortCitations`、`IsFailClosed`、`Remaining`、`UserScope`、`ScopeDisplay`、`WithBudget`。它们都是给接线方的；§3.C 接线后**只有 `SortCitations` 有生产调用点**（`knowledge30.go:499` 的合并后全局截断），其余（`LevelAllows`、`Projects`、`IsFailClosed`、`Remaining`、`UserScope`、`ScopeDisplay`、`WithBudget`）仍只有测试覆盖，规则改动存在两处漂移风险。
19. `DurationMS` 是本包唯一的耗时观测字段；无指标埋点、无 `logx` 接入（playbook §3.I 的观测由主线补）。
20. 本包不做 `Identity.ValidAt(now)`（身份过期归 A 的 `Resolver.Evaluate`），也不展开组织/项目层级（归 B/G）；`AdmitKnowledgeBases` 只透传 `policy.PolicyContext` 与 `policy.ScopeChain`。

**正文通道（§4.8）遗留**

21. **没有正文交付的源侧实现**：只有客户端 `HTTPRetriever.DeliverContent` 与 `FakeRetriever` 那条腿。`llmproxy-knowledge-content-v1` 目前**没有任何对端**——这条要如实读成「协议与网关侧齐了，能对接的对端还没有」，不能当成「注入能力已在真实知识库上跑通」。
22. 第 5 条那个目标约束缺口对**两个入口都成立**：`DeliveryEndpoint` 同样只被 `knowledge.ValidateEndpoint` 管形态（协议、无凭证、无 fragment/query），不校验主机/网段是否在该源被授权的集合内。缓解在 E 侧：每次请求用 `KnowledgeContentEndpoints()` 枚举两个入口逐个复查 `allowed_endpoints`（`processor/content.go:367-385`），配置漂移即拒绝出网——但白名单本身仍是管理员手写的集合。
23. `DeliverContents` 的多源扇出同样不在本包：一次只对一个源交付；接线层按源分组逐路调用、失败按声明里的 `fail_closed` 决定拒或原样放行，**绝不合并部分结果**（`knowledgecontent30.go` 文件头第 3 条）。
24. `Passage.DataLevel` 是**源侧申报级**，本包不检测（§9）。因此 §0 第 1 条第三个子口径（与 `detected_level` 取较高者）在本包侧只落地了「不超过本次上限」这一半，合级那一半待主线定（§8.1 五件第 2 条）。
25. 交付请求里的 `expected_digest` 依赖准入检索返回的摘要；如果同一批文档在检索响应里被源侧换了摘要（同一 `source_id` 两次不同 `digest`），交付会整批 `content_digest_mismatch` 丢弃。这是刻意的（宁可什么都不注入，也不注入一份对不上依据的内容），但意味着**源侧摘要不稳定会表现为「注入永远不生效」**，排查时要先看 `dropped_reasons` 而不是先看权限。
