### 3.1 本次交付：§3.F 执行记录与生产接线测试 —— 「委托跑过了」要能回答用了什么时限（任务 #32、#33）

**打通的是哪一段。** §3.F 的接线在上一包里已经让非流式交换真的换了承载者，但那次交付
留下的证据只到三样：响应头 `X-Llmproxy-Executor`（只有承载者）、`/metrics` 的累计数
（只有次数与稳定码）、以及请求记录里的 `policy_version`。排障要问的下一句 ——
**「这一发到底用了什么时限、多大上限、失败类型是什么」** —— 三样都答不了。本包补的就是
这一句，外加把「生产接线」从单元测试口径提升到真实请求口径。

**改了什么。**

- `internal/server/forwarder.go`：委托分支加一条结构化执行记录
  `event=executor_exchange`，一行承载六项事实 —— `executor` / `provider` / `model` /
  `upstream_model` / `protocol` / `timeout_ms` / `max_response_bytes` / `status` / `reason`。
  字段是**逐个点名**从 `Attempt` 取的，不是把它整个打出来：`Attempt` 里带着 `APIKey`

1. **导出走原始字节**：`res.text()` 之后直接喂 Blob，不做「解析再拼回去」。字段顺序与数字

3. **被拒的提交要把服务端口径盖回输入框**：400 意味着窗口一个字都没动，留着那串确定无效

取证事实（接线时照用，未来改这段别再重新发明）：

- 委托链的四个构造调用是 `AdmitKnowledgeBases(r, ctx, chain, candidates, now)` →
  `NewKnowledgeScope(chain, maxLevel, kbs)` → `NewRequestContext(requestID, subject, chain,
  purpose, effective, policyVersion, now)`（可再 `WithBudget`/`WithMaxResults`/`WithDeadline`）→
  `Resolve(ctx, retriever, rc, scope, q, now)`。
- `Outcome` 的不变量：**`Failure` 非空 ⇒ `Citations` 必空**。接线侧不写「失败了就用已有部分结果」
  这种分支，那正是 fail_open 的入口。
- 没有任何库被准入时 `Resolve` 直接短路，**一次委托请求都不发**。
- `RequestContext` 硬性要求 chain 含 `user:<subject>`，且 subject 禁 `§`/`+`（PII 形态）。
- `coversOwner`（`filter.go:195`）在按 kind 分流之前先 `owner.Validate()`，因此 `system` 归属的
  文档也必须带非空 `owner_id`，否则报 `document_subject_mismatch`。这条形状约束在 C 包单测里
  不显眼看得到（接线夹具 `kbDoc` 就是在这里第一次踩中）。

五条接线边界（实现照此落地，逐条有测试）：

1. **准入判定只有 A 包一个真值源**。本层不写第二套权限规则；客户端传来的库名只能**收窄**
   候选集，永远不能扩展；声明段里没有的库即使策略放行也不发委托（回话里单列
   `undeclared_knowledge_bases`，不混进 policy 拒绝码，避免污染原因码注册表）。
2. **静态 key 直接 403**。它落不出 `user:<subject>`，因此构造不出合法 `RequestContext` ——
   不退化成「按 system 范围检索」，那等于把网关主人的身份借给一把共享钥匙。
3. **legacy（没有策略内核）返回 501**。没有内核就没法判准入，而「没有策略所以全都给」
   是 §3.C 明令禁止的失败模式。shadow 与 enforce 都可用：检索本身对 2.x 没有副作用，
   准入判定在两种模式下都由同一个内核给出。
4. **检索词一律只传摘要**。§2.9 规则 4 要求原文授权只能由管理员策略授予，而本版没有
   「原文检索词」这个授权位，所以接口**不接受**客户端声明 `allow_raw_terms`。
   这是有意的功能缺口，写在 §4 与 `docs/3.0-verification.md` §9.5 里，而不是靠一个布尔字段糊过去。
5. **审计按源逐条落**。多个知识源 ⇒ 多条 `AuditEvent`（target = 源名），因为「哪个库被谁
   查到、哪一家失败」是不同事实，合成一条就没法统计源侧可用性。

三类路径已验证（`internal/server/knowledge30_test.go`，14 条，逐条清单见

```bash
llmproxy replay run -records ~/Downloads/llmproxy-replay-records.json -now "$(date -u +%FT%TZ)"
```

本轮实测：`cmp` 相同（sha256 `959756ec…`），`replay run` 报「记录 1 条：通过 1，差异 0，
拒绝回放 0」。

§3.2 那一包的演练口径是「先出产物，再让产物自己跑」：

```bash
./scripts/release-check.sh                                    # 出 dist/ 四个 tar.gz + SHA256SUMS
./scripts/drill-release-artifact.sh                           # ✓ 五项留痕：sha256/版本/启动/优雅退出/重开
tar -xzf dist/llmproxy-v2.5.0-dirty-darwin-arm64.tar.gz -C /tmp/drill
export ART=/tmp/drill/llmproxy-v2.5.0-dirty-darwin-arm64/llmproxy
LLMPROXY_BIN=$ART bash scripts/e2e-multiuser.sh                # ✓ 同一套 189 项，跑在发行件上（amd64 那个架构同样 0 失败）
LLMPROXY_BIN=$ART KEEP=1 bash scripts/e2e-multiuser.sh          # 留住运行时目录，拿 records.json
# 同一份记录，每次只变一样：二进制、policy.mode、时钟、目录
LLMPROXY_HOME=<留住的目录> $ART replay run -records <目录>/records.json -now "$(date -u -v+2d +%FT%TZ)"
```

实测四段都是「记录 3 条：通过 3，差异 0，拒绝回放 0」，并且报告照实附一行「只做解释性回放，
不比对首选顺序」；两条失败对照（配置缺 providers、策略包内容文件被挪走）都是点名拒因，
不是「0 条差异」。
