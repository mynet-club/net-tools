### 3.1 本次交付：回放证据链的管理台面板 —— §4 第 15 条的面板那一半（任务 #29）

提交：`cda4d5f`（本地，未推送）。复现入口：`./scripts/check-ui-refs.sh`
（admin 面 129 个字面量 id 全对得上）；浏览器那一段是手工路径，见下面「已知限制」。

**这一包不新增任何接口**：`GET /v1/_admin/replay`、`POST …/sampling`、`GET …/export`、
`POST …/clear` 四个端点与它们的 OpenAPI 条目都是 §2.8 那一包交付的，此前只有 API 与 CLI
两个面。补的是第三个面：证据链的运维口径写得很明白 ——「要证据时打开 → 跑一批流量 →
导出取走 → 关掉或清空」，而这四步在只有 CLI 的情况下意味着登服务器。

面板上每一格都是服务端报出来的原值，界面不复算判定、不复算费用、也不自己跑回放：

| 区 | 内容 | 为什么这么摆 |
|---|---|---|
| 顶部横幅 | 非 enforce 时的「窗口不会采集任何记录」 | 「开关是开的、窗口是空的」是这一屏最容易误读的状态，必须比统计更显眼 |
| 计数 | 窗口内判定/选路、累计收到/丢弃/失败 | 丢弃与失败非零本身就是待查项，不能只报「收了多少」 |
| 计数 | 回放缺省抽样器 + 首选顺序是否逐位复现 | 后者是「否」是当前事实不是缺陷，界面照实写，不等人来问 |
| 开关 | 复框 + 千分率 + 范围过滤 + 上限 | 指针语义：留空的字段不动；**只有过滤框例外**（清空就是清掉过滤） |
| 导出 | 下载 `llmproxy-replay-records.json` | 拿的是记录文件**本身**那串字节，不重序列化 |
| 清空 | 清记录与计数，开关与过滤保留 | 与服务端 `clear` 的语义一致：这批证据拿走了，配置没变 |

三条方向性决定：

1. **导出走原始字节**：`res.text()` 之后直接喂 Blob，不做「解析再拼回去」。字段顺序与数字
   格式一旦变，那份文件就不再是 §2.8 契约里「另一个进程能逐字段重跑」的那一份。实测对账：
   同一个窗口，浏览器下载的那份与 `llmproxy replay collect -out` 的那份 **sha256 相同**，
   且浏览器那份交给独立进程 `llmproxy replay run -records … -now …` 报
   「记录 1 条：通过 1，差异 0，拒绝回放 0」。
2. **模式联动**：策略屏每次刷新（含改 mode）都带着回放屏重读一次。窗口收不收得到记录完全
   由 `policy.mode` 决定，两屏各自独立就会各说各话。
3. **被拒的提交要把服务端口径盖回输入框**：400 意味着窗口一个字都没动，留着那串确定无效
   的值会出现「框里 2000、横幅 500」这种没人说得清的状态；连不上网关则保留人已打的内容。

浏览器实测（Chromium，真进程网关）抓到并修掉两个真缺陷：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 无效值被静默丢掉 | 千分率填 `abc` 点保存：不报错、不改配置，人以为改过了 | `rpInt` 只管「是不是整数」这一件格式事，非整数直接说破「本次没有提交」；取值域（0~1000、1~上限）仍只由服务端判 |
| 四个字段各占一行 | 用了 `type="number"`，撞上 `app.css` 的 `input[type=text\|number] { width: 100% }` | 沿用本页既有行的写法（不带 `type`、`class="mono"`），实测四个控件与按钮回到同一行 |

**已知限制（不伪装）**：面板没有自动化入口 —— 本仓库对 UI 只有一道静态门禁
（`check-ui-refs.sh` 查 id 引用），本轮的开关保存、非法值拒绝、导出逐字节对账、清空、
模式联动五件事全部是浏览器手工路径 + 命令行对账，重跑要人再点一遍。
§4 第 15 条的另一半（导出过滤只认 `user:<名>`）原样成立：窗口按 2.x 的路由作用域记账，
组织/项目范围进不了这个键，那是存储裁决不是界面活。

  `Resolve(ctx, retriever, rc, scope, q, now)`。
- `Outcome` 的不变量：**`Failure` 非空 ⇒ `Citations` 必空**。接线侧不写「失败了就用已有部分结果」
  这种分支，那正是 fail_open 的入口。
- 没有任何库被准入时 `Resolve` 直接短路，**一次委托请求都不发**。
- `RequestContext` 硬性要求 chain 含 `user:<subject>`，且 subject 禁 `§`/`+`（PII 形态）。
- `coversOwner`（`filter.go:195`）在按 kind 分流之前先 `owner.Validate()`，因此 `system` 归属的
  文档也必须带非空 `owner_id`，否则报 `document_subject_mismatch`。这条形状约束在 C 包单测里
  不显眼看得到（接线夹具 `kbDoc` 就是在这里第一次踩中）。

五条接线边界（实现照此落地，逐条有测试）：

1. **准入判定只有 A 包一个真值源**。本层不写第二套权限规则；客户端传来的库名只能**收窄**
   候选集，永远不能扩展；声明段里没有的库即使策略放行也不发委托（回话里单列
   `undeclared_knowledge_bases`，不混进 policy 拒绝码，避免污染原因码注册表）。
2. **静态 key 直接 403**。它落不出 `user:<subject>`，因此构造不出合法 `RequestContext` ——
   不退化成「按 system 范围检索」，那等于把网关主人的身份借给一把共享钥匙。
3. **legacy（没有策略内核）返回 501**。没有内核就没法判准入，而「没有策略所以全都给」
   是 §3.C 明令禁止的失败模式。shadow 与 enforce 都可用：检索本身对 2.x 没有副作用，
   准入判定在两种模式下都由同一个内核给出。
4. **检索词一律只传摘要**。§2.9 规则 4 要求原文授权只能由管理员策略授予，而本版没有
   「原文检索词」这个授权位，所以接口**不接受**客户端声明 `allow_raw_terms`。
   这是有意的功能缺口，写在 §4 与 `docs/3.0-verification.md` §9.5 里，而不是靠一个布尔字段糊过去。
5. **审计按源逐条落**。多个知识源 ⇒ 多条 `AuditEvent`（target = 源名），因为「哪个库被谁
   查到、哪一家失败」是不同事实，合成一条就没法统计源侧可用性。

三类路径已验证（`internal/server/knowledge30_test.go`，14 条，逐条清单见
`docs/3.0-verification.md` §9.4）：

- **正常**：出网库集合=被点名且被准入的那一个；purpose/策略版本/分级上限按判定现场传出；
  回话只有 `source_id` + 摘要，标题与正文不出现；准入清单不回端点地址；检索词只以摘要出网
  并同样以摘要落审计（逐源一条，target=源名）。
- **拒绝**：被策略拒掉与未声明的库**零委托发出**且留一条 `delegation: "not_sent"` 审计；
  客户端不能扩大候选集；`allow_raw_terms` 被 400 指认；静态 key 403；legacy 两条路径都 501；
  空/超长检索词、显式 `max_results: 0`、超上限、未知子路径 404、GET search 405 各归各位。
- **失败**：源侧 5xx ⇒ 502 且零引用（`retrieval_upstream_status`）；`request_id` 串号 ⇒
  `retrieval_protocol_invalid`；`timeout_ms` 真的是兜底预算（`retrieval_timeout`）；
  超上限文档逐条丢弃为 `knowledge_level_exceeded` 而请求仍成功；transport 装不起来时错误指名到源。

**两类证据必须分开读**：以上全部跑在进程内 `httptest` 桩源（`kbStub`，按 §4.2/§4.3 协议
应答但没有真实 ACL 数据）之上，`examples/university` 的演示同样只用假依赖。两者证明的是
**领域装配走得通**，不是真实登录、真实知识库、真实模型可用。后者属于「端到端验证」层，
仍未完成（§4 第 1 条）。

契约冲突：本次未发现需要主线裁决的接口冲突。唯一新增到全局词汇表的是 `purpose` 取值
`knowledge-search`（`kbPurpose`），已同时写进 `docs/3.0-policy-domain.md` §4 与
`internal/server/policy30.go:policyPurposeFor` 的注释，理由是模型调用与检索的合规口径不同，
共用一个值会让按 purpose 写的 deny 条件在其中一侧静默失配。

## 4. 明确还没做（不伪装）

1. **§3.C 的端到端验证**：接线与三类测试已完成，且测试本身就是本机端到端（配置真实加载、
   真实 SQLite 审计、双向真实 HTTP）。缺的是真实世界那三样：真实源侧服务端实现（本仓库只有
   客户端 `HTTPRetriever` 与 `FakeRetriever`）、跨主机网络与 TLS 路径、源侧真实 ACL 数据。
2. **检索结果不参与模型请求**：`/v1/chat/completions` 的提示词里不会自动带任何引用。
   注入增强需要先定「谁授权这次增强、注入多少篇、`knowledge_level` 与 `detected_level`
   怎么合并」，口径没定之前自动注入等于静默扩大正文访问面（§2.9 规则 3）。
3. **流式上游交换仍走 2.x 传输**：F 的 `Attempt` 强制正时限与正字节上限，而现网流式刻意
   两者都没有（§2.9 规则 7 + idle.go 的「无总时限」）。要委托流式，先得让 F 能表达
   「以调用方 ctx 为准、不缓存」的通道 —— 那是接口裁决（§3.5 契约冲突第 2 条），不在接线里
   偷偷补，也不在文档里把它算成已完成。
4. **`executor.Registry` 没有生产调用点**：它假设「名字→单实例」，而生产按
   （名字 × 归属 × 代理）分通道要多实例。接线自行装配、没有把 `Registry` 塞进请求路径，
   该接口冲突已在 §3.5 登记待主线裁决。
5. **执行明细不落库**：承载者只在响应头 `X-Llmproxy-Executor`、日志与**内存计数**里；
   按执行器/按原因码的调用与失败维度已由 §3.2 补上，落库仍缺（一张表 = `store` 三方言
   各一遍迁移，与第 12 条同一条裁决）。同样仍缺的是按执行器的耗时分位：现网只有请求级
   `llmproxy_latency_ms`，按承载者再拆一套要先定「两条链路是否共用同一个环形样本」。
6. **只注册了一个执行器名**（`http-openai`）。Ollama/vLLM 方言适配器存在于 F 包里，
   但注册它们需要配置面新增语义（§2.7 规则 4：新语义要带版本与迁移说明），不在接线包里顺手加。
7. **处理器执行明细不落库**：逐条结果只进日志，装配失败只有日志与回话两个面，管理台没有
   「这条声明装不起来」的红灯位。落库需要 `store` 三方言各加一张表并过 `test-matrix.sh`，
   是一次独立的存储变更。
8. **跨请求稳定的假名不支持**：`PseudonymKey` 是密钥，不接受文件注入（§8.1 同一条理由），
   所以 `pii-mask` 今天只能用每请求随机 salt。检索侧同源的缺口是 `query_digest` 没有
   HMAC 密钥位，低熵检索词在审计表里可被字典命中（`docs/3.0-knowledge-delegation.md` §10 第 17 条）。
9. **原文检索词的授权位缺失**（见 §3.6 边界 4）。
10. **处理器拒收的响应不记 usage**：与既有 502/超时路径同口径，要不要照计属于计费决策。
11. **知识源只有计数没有分位**：按源/按原因码的失败维度与累计毫秒已由 §3.2 补上，
   仍缺 p95 一类的分布（只有 `measured` 与累计毫秒，只能算均值），以及按范围的检索耗时。
12. **回放记录不落库**：采集窗口只在进程内存里，**重启即空**、溢出丢最旧。为什么：补一张表
    意味着 §2.7 三方言各一遍迁移并过 `test-matrix.sh`，而记录里的 subject 是用户名 ——
    长期留存「谁在什么时候被授权用了哪个模型」是一份独立的合规决定（§2.9 要求这类数据
    只在需要时存在）。今天的运维口径写在 `replayUsage` 里：要证据时打开 → 跑一批流量 →
    collect 取走 → off 或 clear。
13. **首选顺序不逐位复现**：线上是 `routing-seeded-splitmix64-v1`，回放缺省抽样器是
    `replay-sampling-v1`，因此记录一律只做解释性回放。逐位复现需要 D 的
    `routing.PlanFromReplay/Replay(ReplayInput)`，而冻结的 `replay.File` v1 携带不了那组输入
    （§3.4 契约冲突第 1 条）。这是接口裁决，不由接线侧拍板。
14. **拒绝证据与原文出网授权的冲突**（§3.4 契约冲突第 2 条）：同版本回放对「带原文授权的
    范围里的一次真实拒绝」必然且只报 `external_plaintext_allowed` 这一位差异。已钉成
    `TestReplay30DenyEvidenceAndRawBodyGrantConflict`，等主线给出口径。
15. **回放导出过滤只认 `user:<名>`**：管理台面板已由 §3.1 补上（四个端点现在有三个面），
    剩下的是过滤键本身 —— 窗口按 2.x 的路由作用域（用户名）记账，组织/项目范围今天进不了
    这个键，因此 `?scope=organization:…` 直接 400 而不是静默导出空文件。放开它要先定
    「窗口按什么键记账」，那是存储与路由作用域的裁决（与第 12 条同源）。
16. **回放面板没有自动化入口**：本仓库对 UI 只有 `check-ui-refs.sh` 这一道静态门禁（查 id
    引用），§3.1 那五件事（保存、非法值拒绝、导出逐字节对账、清空、模式联动）是浏览器手工
    路径 + 命令行对账。要把它变成可重跑的门，先得有 UI 层的驱动夹具 —— 那是新工具链，
    不在接线包里顺手搭。
17. MySQL/PG 侧门禁只在有 DSN 时才真跑；本机 `test-matrix.sh` 目前只覆盖 SQLite 基线。

## 6. 交接规则（本仓库当前生效）

- 每个工作包**只在本地提交**，不推送；推送由用户决定。
