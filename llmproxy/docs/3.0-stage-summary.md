### 3.1 本次交付：§3.F 执行器接线（任务 #25）

提交：本次交付的本地提交（未推送）。复现入口：
`go test ./internal/server/ -run TestExecutor30 -count=1`。

**打通的是哪一段**：配置修订 → 执行器声明表 → 按出网通道惰性构造实例 → 计划候选的
执行器名解析 → `Attempt` 构造（目标/凭证/正文/超时/上限全显式）→ 一次上游交换 →
既有 `relay`。此前 `internal/server/` 里没有一处 import `internal/executor`，
线上请求一律不经过它。

实际接入点（逐条可在代码里查到）：

| 接入点 | 位置 |
|---|---|
| 声明表 | `buildExecutorRuntime()`：今天只有一个名字 `policyExecutorOpenAI`（`http-openai`），协议形态 `executor.ProtocolOpenAIChat`；与 `policy30.go:544` 构造候选时写进 `RouteCandidate.Executor` 的值同源，另起字面量就是第二个事实源 |
| 运行态生命周期 | `policyRuntime.exec`（`policy30.go`），与 `rt.proc`/`rt.kb` 同一条修订生命周期一起换 |
| 通道装配 | `newUpstreamExecutor`：`executor.NewHTTPExecutor(Options{Transport: tr, UserAgent: "llmproxy/"+config.Version, ...})`，`tr` 只取 `s.transportFor(systemPaid, proxyURL)` 且拿到 nil 即报错 |
| 缓存键 | `executorChannel{executor, protocol, systemPaid, proxyURL}`；失败也缓存（坏代理 URL 是配置事实）；64 条上限，越界后每请求现构造 |
| 委托判定 | `executorCallFor(rt, shot, ask)` 三结论：`(nil,nil)` 不委托 / `(nil,err)` 拒候选 / `(call,nil)` 委托 |
| 形状适配 | `(*executorCall).roundTrip`：`Outcome` → `*http.Response`（状态码、过滤后的头、体积声明、未改写字节流） |
| 归因映射 | `upstreamFailMessage`：`ReasonTimeout`/`ReasonCallerCanceled` → 那句「供应商 X 请求超时」，2.x 侧仍按文本判 |
| 观测 | 响应头 `X-Llmproxy-Executor=<执行器名>`；漂移 WARN `event=executor_plan_drift` |

三条边界（实现照此落地，逐条有测试；完整论证见 `docs/3.0-verification.md` §10.3）：

1. **计量语义一个字不改**（playbook §3.F 禁止项）。执行器的回报只被拼成 `relay`
   能消费的结构，usage/TTFT/计价/熔断/粘性全走原路；`MaxResponseBytes` 与 relay 的
   `maxUpstreamResponseBytes` 同值，两条上限不同值时「谁先拦住超大响应」变成运气。
2. **只有 `policy.mode=enforce` 且 `shot.Applied` 才委托**。legacy/shadow 下 2.x 传输
   原样跑；影子一旦能换传输层，差异报告里就掺进了被观测者自己的改动。
3. **流式不委托**。F 的 `Attempt.Validate` 强制 `Timeout`/`MaxResponseBytes` 为正，
   而现网流式刻意「无总时限」且「边收边转发、不缓存、无字节上限」（§2.9 规则 7）；
   补进去是功能回退，打通它需要 F 先能表达「以调用方 ctx 为准、不缓存」的通道 ——
   接口裁决，不在接线里偷偷做。

失败方向（这一包最容易伪装成完成的两处）：

- 计划声明的执行器本网关注册不上 ⇒ **拒掉这个候选**，不出网也不回落到 2.x。
  回落等于把「计划说用哪个执行器」降级成注释，正是 §8 点名的绕过出网控制的快捷路径。
  测试直接断言缓存里零通道、桩上游零请求。
- 计划与这一跳真正要发的上游模型名不一致 ⇒ 不委托 + WARN（`event=executor_plan_drift`）。
  拿计划里的名字去覆盖真实目标，等于让审计描述一次没发生的交换。

三类路径已验证（`internal/server/executor30_test.go`，10 条 + 判定分支表 10 格，
逐条清单见 `docs/3.0-verification.md` §10.5）：

- **正常**：委托头在场且桩上游逐字收到的正文里 `model` 是上游真名、没有被注入
  `stream_options`；`Authorization`/`User-Agent`/`Content-Type` 与 2.x 同形；
  两条链路下 usage/状态/归属/尝试数逐字段一致且**冻结成本一致且非零**；
  委托侧策略版本仍在、legacy 侧没有。
- **拒绝**：legacy 与 shadow 下委托头缺席且上游只收到一次；流式不委托且照常出
  `text/event-stream`+`[DONE]`+usage；未注册名 ⇒ 拒候选（错误指名该名并列出已注册名、
  不出网、不含密钥）；八条「不委托」理由各自归位且不被误当成「拒候选」。
- **失败**：通道装不起来时错误指名环节、失败原因进缓存、不出网；一次正常超时在两条
  链路下同形归因且记录里不含正文；上游 400 原样透传不重试、不回 `executor_*` 内部码；
  持续 503 最终透出上游状态码。

**两类证据必须分开读**：以上全部跑在进程内 `httptest` 桩上游之上，它按 OpenAI 兼容形态
应答但不是任何真实供应商。真实代理/TLS/限流路径、真实方言适配器、真实 usage 回报的边角
形态属于「端到端验证」层，仍未完成（§4 第 3、6 条）。

契约冲突（需主线裁决，接线侧没有擅自改 F 的冻结代码）：

1. **`executor.Registry` 假设「名字→单实例」，生产需要「名字 × 出网通道→多实例」**。
   `HTTPExecutor` 把 transport 绑在实例上，而同一家的请求可能来自系统池通道或某个用户
   自有代理通道。接线因此自行按通道装配（`executorRuntime.channel`），
   `Registry.ResolvePlanPrimary` 目前**没有生产调用点**。要么 F 的 `Registry` 改成按通道
   索引，要么 `Attempt` 携带 transport —— 两者都是接口变更，留给主线。
2. **`Attempt` 无法表达「无总时限 + 不缓存」**，导致流式不可委托（边界 3）。
   这是 F 契约与 §2.9 规则 7 的真实冲突，不是接线偷懒。

### 3.2 上一包交付：§3.C 检索委托接线（任务 #24）

提交：`d76be6e`（本地，未推送）。复现入口：
`go test ./internal/server/ -run TestKnowledge -count=1`。

**打通的是哪一段**：`knowledge_sources` 声明 → 出网 transport → 策略准入 → C 包委托 →
`Filter` 兜底 → 按源审计落库 → 用户面回话。此前这一段只在领域面与测试里存在，
`internal/server/` 没有任何一处 import `internal/knowledge`。

实际接入点（逐条可在代码里查到）：

| 接入点 | 位置 |
|---|---|
| 装配委托入口 | `buildKnowledgeRuntime`：`knowledge.NewHTTPRetriever(endpoint, knowledge.TransportDo(tr, timeout_ms))`，`tr` 只取 `s.Transports().Get("")` |
| 运行态生命周期 | `policyRuntime.kb`（`policy30.go`），与 `rt.proc` 同一条修订生命周期一起换，配置热加载不会留下与策略对不上的旧装配 |
| 准入判定 | `knowledge.AdmitKnowledgeBases(rt.resolverFor(scope), ctx, chain, declared, now)` —— 唯一真值源，资源 `knowledge:<id>` + 动作 `read` |
| 委托上下文 | `NewRequestContext(..., kbPurpose, ...)` + `WithMaxResults` + 逐源 `WithDeadline`（只收窄）→ `NewKnowledgeScope` → `Resolve` |
| 审计 | `s.db.AuditScope(scope, actor, "knowledge.search", <源名>, <AuditEvent JSON>)`，**凡被问到的源恰好一条**；失败发生在网关这一侧（transport 装不起来 / 预算用尽 / 范围不合法 / `Resolve` 前置校验失败）时由 `minKBAudit` 补一条最小留痕 |
| 端点 | `GET /v1/_me/knowledge`（准入清单，只读不落审计）、`POST /v1/_me/knowledge/search`（严格 JSON 体），分发在 `users.go:handleMe` |
| 契约 | `ui/openapi.yaml` 两条路径 + `operationId: meKnowledgeSearch` + 动作名 `knowledge.search`，由 `TestOpenAPISpec` 钉住 |

取证事实（接线时照用，未来改这段别再重新发明）：

- 委托链的四个构造调用是 `AdmitKnowledgeBases(r, ctx, chain, candidates, now)` →
  `NewKnowledgeScope(chain, maxLevel, kbs)` → `NewRequestContext(requestID, subject, chain,
  purpose, effective, policyVersion, now)`（可再 `WithBudget`/`WithMaxResults`/`WithDeadline`）→
  `Resolve(ctx, retriever, rc, scope, q, now)`。
- `Outcome` 的不变量：**`Failure` 非空 ⇒ `Citations` 必空**。接线侧不写「失败了就用已有部分结果」
  这种分支，那正是 fail_open 的入口。
- 没有任何库被准入时 `Resolve` 直接短路，**一次委托请求都不发**。
- `RequestContext` 硬性要求 chain 含 `user:<subject>`，且 subject 禁 `@`/`+`（PII 形态）。
- `coversOwner`（`filter.go:195`）在按 kind 分流之前先 `owner.Validate()`，因此 `system` 归属的
  文档也必须带非空 `owner_id`，否则报 `document_subject_mismatch`。这条形状约束在 C 包单测里
  不显眼看得到（接线夹具 `kbDoc` 就是在这里第一次踩中）。

五条接线边界（实现照此落地，逐条有测试）：

1. **准入判定只有 A 包一个真值源**。本层不写第二套权限规则；客户端传来的库名只能**收窄**
   候选集，永远不能扩展；声明段里没有的库即使策略放行也不发委托（回话里单列
   `undeclared_knowledge_bases`，不混进 policy 拒绝码，避免污染原因码注册表）。
2. **静态 key 直接 403**。它落不出 `user:<subject>`，因此构造不出合法 `RequestContext` ——
   不退化成「按 system 范围检索」，那等于把网关主人的身份借给一把共享钥匙。
3. **legacy（没有策略内核）返回 501**。没有内核就没法判准入，而「没有策略所以全都给」
   是 §3.C 明令禁止的失败模式。shadow 与 enforce 都可用：检索本身对 2.x 没有副作用，
   准入判定在两种模式下都由同一个内核给出。
4. **检索词一律只传摘要**。§2.9 规则 4 要求原文授权只能由管理员策略授予，而本版没有
   「原文检索词」这个授权位，所以接口**不接受**客户端声明 `allow_raw_terms`。
   这是有意的功能缺口，写在 §4 与 `docs/3.0-verification.md` §9.5 里，而不是靠一个布尔字段糊过去。
5. **审计按源逐条落**。多个知识源 ⇒ 多条 `AuditEvent`（target = 源名），因为「哪个库被谁
   查到、哪一家失败」是不同事实，合成一条就没法统计源侧可用性。

三类路径已验证（`internal/server/knowledge30_test.go`，14 条，逐条清单见
`docs/3.0-verification.md` §9.4）：

- **正常**：出网库集合=被点名且被准入的那一个；purpose/策略版本/分级上限按判定现场传出；
  回话只有 `source_id` + 摘要，标题与正文不出现；准入清单不回端点地址；检索词只以摘要出网
  并同样以摘要落审计（逐源一条，target=源名）。
- **拒绝**：被策略拒掉与未声明的库**零委托发出**且留一条 `delegation: "not_sent"` 审计；
  客户端不能扩大候选集；`allow_raw_terms` 被 400 指认；静态 key 403；legacy 两条路径都 501；
  空/超长检索词、显式 `max_results: 0`、超上限、未知子路径 404、GET search 405 各归各位。
- **失败**：源侧 5xx ⇒ 502 且零引用（`retrieval_upstream_status`）；`request_id` 串号 ⇒
  `retrieval_protocol_invalid`；`timeout_ms` 真的是兜底预算（`retrieval_timeout`）；
  超上限文档逐条丢弃为 `knowledge_level_exceeded` 而请求仍成功；transport 装不起来时错误指名到源。

**两类证据必须分开读**：以上全部跑在进程内 `httptest` 桩源（`kbStub`，按 §4.2/§4.3 协议
应答但没有真实 ACL 数据）之上，`examples/university` 的演示同样只用假依赖。两者证明的是
**领域装配走得通**，不是真实登录、真实知识库、真实模型可用。后者属于「端到端验证」层，
仍未完成（§4 第 1 条）。

契约冲突：本次未发现需要主线裁决的接口冲突。唯一新增到全局词汇表的是 `purpose` 取值
`knowledge-search`（`kbPurpose`），已同时写进 `docs/3.0-policy-domain.md` §4 与
`internal/server/policy30.go:policyPurposeFor` 的注释，理由是模型调用与检索的合规口径不同，
共用一个值会让按 purpose 写的 deny 条件在其中一侧静默失配。

   客户端 `HTTPRetriever` 与 `FakeRetriever`）、跨主机网络与 TLS 路径、源侧真实 ACL 数据。
2. **检索结果不参与模型请求**：`/v1/chat/completions` 的提示词里不会自动带任何引用。
   注入增强需要先定「谁授权这次增强、注入多少篇、`knowledge_level` 与 `detected_level`
   怎么合并」，口径没定之前自动注入等于静默扩大正文访问面（§2.9 规则 3）。
3. **流式上游交换仍走 2.x 传输**：F 的 `Attempt` 强制正时限与正字节上限，而现网流式刻意
   两者都没有（§2.9 规则 7 + idle.go 的「无总时限」）。要委托流式，先得让 F 能表达
   「以调用方 ctx 为准、不缓存」的通道 —— 那是接口裁决（§3.1 契约冲突第 2 条），不在接线里
   偷偷补，也不在文档里把它算成已完成。
4. **`executor.Registry` 没有生产调用点**：它假设「名字→单实例」，而生产按
   （名字 × 归属 × 代理）分通道要多实例。接线自行装配、没有把 `Registry` 塞进请求路径，
   该接口冲突已在 §3.1 登记待主线裁决。
5. **执行明细不落库、不指标化**：承载者只在响应头 `X-Llmproxy-Executor` 与日志里；
   `/metrics` 上没有按执行器/按原因码的调用与失败维度（playbook §3.I 的观测面仍待补）。
6. **只注册了一个执行器名**（`http-openai`）。Ollama/vLLM 方言适配器存在于 F 包里，
   但注册它们需要配置面新增语义（§2.7 规则 4：新语义要带版本与迁移说明），不在接线包里顺手加。
7. **处理器执行明细不落库**：逐条结果只进日志，装配失败只有日志与回话两个面，管理台没有
   「这条声明装不起来」的红灯位。落库需要 `store` 三方言各加一张表并过 `test-matrix.sh`，
   是一次独立的存储变更。
8. **跨请求稳定的假名不支持**：`PseudonymKey` 是密钥，不接受文件注入（§8.1 同一条理由），
   所以 `pii-mask` 今天只能用每请求随机 salt。检索侧同源的缺口是 `query_digest` 没有
   HMAC 密钥位，低熵检索词在审计表里可被字典命中（`docs/3.0-knowledge-delegation.md` §10 第 17 条）。
9. **原文检索词的授权位缺失**（见 §3.2 边界 4）。
10. **处理器拒收的响应不记 usage**：与既有 502/超时路径同口径，要不要照计属于计费决策。
11. **知识源没有指标埋点**：耗时只在 `AuditEvent.DurationMS`，`/metrics` 上没有按原因码的
   检索失败率维度（playbook §3.I 的观测面仍待补）。
12. **线上决策记录导出与跨进程回放**仍未闭合（`docs/3.0-verification.md` §7 第 1 条）：
   它就是任务队列里的 #26，本轮不并入 #24/#25 的交付口径。
13. MySQL/PG 侧门禁只在有 DSN 时才真跑；本机 `test-matrix.sh` 目前只覆盖 SQLite 基线。
