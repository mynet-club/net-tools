# 3.0 验证手册（工作包 I）

本手册是手册 §8「Definition of Done」的可执行化：一条命令跑什么、每一步证明了哪条约束、
哪些东西**还没做**（不伪装）。凡"未实现"一律显式写出并给出判定入口。

## 1. 怎么跑

在 `llmproxy/` 目录下：

```bash
./scripts/release-check.sh --3p0        # 3.0 领域门禁：gofmt / 测试覆盖 / OWNED 包 vet+test+race
./scripts/test-matrix.sh   --3p0        # 3.0 领域包按包 go test -race -count=1
./scripts/release-check.sh --pkg=./internal/replay/...   # 定向到某个包（可重复给多个）
./scripts/release-check.sh              # 完整发布门禁（原有步骤与用法保持不变）
./scripts/test-matrix.sh                # 完整测试矩阵：同一套 store 断言跑 SQLite/MySQL/PostgreSQL
```

三个新开关（`--3p0`、`--pkg=`）都是**加法式**的：不带参数时行为与改动前一致，
构建产物与发布流程不受影响。`bash -n` 已覆盖两个脚本的语法。

## 2. OWNED / INFLIGHT：并行期口径已收掉

包分两类，清单就在两个脚本顶部（`DOMAIN_OWNED` / `DOMAIN_INFLIGHT`，
`release-check.sh:23-24`、`test-matrix.sh:20-21`）：

| 类别 | 当前成员 | 红了的后果 |
|---|---|---|
| OWNED（已合并并冻结） | `internal/policy`、`internal/replay`、`internal/identity`、`internal/knowledge`、`internal/processor`、`internal/routing`、`internal/executor`、`examples/university` | 门禁**失败并非 0 退出** |
| INFLIGHT（并行在途） | 空 | —— |

两类拆分这套机制**保留但不启用**。它的由来：并行期「别人的包编译不过」既不能被伪装成通过
（所以错误原文必须可见），也不能算成本包的发布失败（所以不能非 0 退出）。七个领域包与高校
示例都按 §8 合并之后，这个口径必须收掉 —— 否则门禁等于对半数代码失效。
`gate_gofmt` 在名单为空时显式打印「无在途包」，就是为了不在输出里留下「还有包在途」的误读。

**迁移规则**（将来新包仍然适用）：一个包按 §8 复核合并后，主线要把包名从两个脚本各自的
`DOMAIN_INFLIGHT` 移到 `DOMAIN_OWNED`，并更新本表。脚本里**不单独硬编码包名**：
`--3p0` 的 OWNED 全量 vet+test 目标由 `DOMAIN_OWNED` 派生，两个脚本的 `domain_tag`
都按同一份名单归类 —— 漏改的后果是该包从此享受"红也不拦"的待遇，
门禁静默失效比没有门禁更危险。

缺席的包（目录不存在）跳过并提示"该工作包还没派"；有源文件却没测试文件的包按类别判
OWNED 失败 / INFLIGHT 警告（`gate_tests_present`）。

## 3. 每一步证明了什么（对齐 §6 / §8）

| 门禁步骤 | 证明的约束 |
|---|---|
| `gofmt -l` 领域包 | §5 代码规范可机器核查，不靠自觉 |
| 测试覆盖检查 | §8.2「正常/拒绝/失败路径有测试」的必要条件（有源必须有测） |
| 按包 `go vet` | 类型与常见错误用法，按包跑是为了在并行期定位到归属 |
| `--3p0` 的 OWNED 全量 vet + test（非 `--quick` 时带 `-race`） | §8.3、§8.4；目标从 `DOMAIN_OWNED` 派生，`-count=1` 禁测试缓存，避免"其实没跑" |
| `--3p0` 对 INFLIGHT 的探测 | 只 `go test -count=1` 并把错误原文打出来，保证在途失败可见但不伪装成通过 |
| 完整门禁的 `go vet ./...` + `go test ./...` | 领域包不会把主程序与其它包拖到编译/测试不过（`--3p0` 不做全量，是为了并行期能秒级自查） |
| 三数据库矩阵 | store 层方言一致性（沿用原有 test-matrix 语义） |

## 4. 回放记录的数据契约（`internal/replay`）

### 4.1 记录里有什么

`DecisionRecord`（`record.go:174`）：`request_id`、`recorded_at`、`policy_version`、
`scope_chain`、`subject`（`SubjectSnapshot`：subject/source/roles/groups/projects/
auth_methods/issued_at/expires_at）、`context`（`ContextSnapshot`：purpose/organization/
project/data_level/allowed_regions/wiring_mode）、`resource`、`action`、
`effect`、`reason`、`reasons`、`winner`/`matched`（`RuleRef`，只存规则标识与 `sort_key`）、
`expires_at`、`external_plaintext_allowed`。

`RoutingRecord`（`record.go:396`）：`request_id`、`recorded_at`、`policy_version`、
`routing_seed`、`routing_epoch`、`sampling_algo`、`candidates_digest`、`candidates`
（按 `policy.SortCandidates` 稳定顺序写入）、`plan`、`rejections`。

`File`（`codec.go:51`）刻意**没有** `generated_at`：文件级时间戳会让同一批记录两次导出
产生不同字节，而 §2.8 要的是同一输入同一输出；时刻信息由每条记录的 `recorded_at` 承担。

### 4.2 为什么不含正文（以及怎么把它变成会失败的断言）

§2.8 明确"不需要记录请求正文"，§2.9 限定正文访问，§5 禁止落真实密钥与个人信息。
本包不依赖自觉，而是用四层断言钉住：

1. `TestRecordStructsCarryNoBodyOrCredentials` —— 反射扫描记录结构体的全部字段名；
2. `TestEncodedRecordsHaveNoForbiddenKeys` —— 扫描**序列化后的 JSON 键**（结构体可以藏，
    map 键藏不住）；
3. `TestDecodeRejectsForbiddenKeysEvenWhenNested` —— 解码时拒掉嵌套任意深度出现的被禁键，
   所以"手工改过的记录文件"也进不来；
4. `TestRecordOmitsDisplayName` / `TestRecordOmitsConditionValues` —— 结论性输出里
   不带显示名（PII）与 conditions 取值（可能含数据内容）。

被禁词表 `ForbiddenFieldWords()`（`codec.go:26`）：`body`、`payload`、`content`、`prompt`、
`messages`、`message`、`apikey`、`api_key`、`secret`、`token`、`password`、`credential`、
`baseurl`、`base_url`、`cookie`、`authorization`、`raw`、`email`、`phone`、`idcard`、`id_card`。
连 `raw` 与 `content` 都禁，是因为 `raw_body` 这类命名会诱导实现方往记录里塞正文片段。
A 包 `internal/policy/leak_test.go` 用同一口径，两包必须一致 —— 改一处就要改两处。

注意 `external_plaintext_allowed` 是布尔：它记录"是否允许未脱敏文本出网给 sidecar"这个**结论**
（§2.9 规则 3、4），正文本身从不入库。

### 4.3 回放的 fail_closed 清单（每条都有对应测试）

回放一律 fail_closed，绝不退化成"随机选一个"或"按 deny 收"：

| 拒绝条件 | 哨兵 | 测试 |
|---|---|---|
| 策略集为空 | `ErrEmptyBundleSet` | `TestNewFailClosed` |
| 未显式给定时钟 | `ErrClockRequired` | `TestReplayNeedsFixedClock` |
| 路由记录缺 `routing_seed` | `ErrSeedMissing` | `TestReplayRoutingRequiresSeed` |
| seed 与 `(request_id, policy_version, routing_epoch)` 推导值不符 | —— | `TestReplayRoutingDetectsWrongSeedDerivation` |
| 记录结构自相矛盾 | `ErrRecordInvalid` | `TestReplayRejectsBrokenRecord`、`TestRecordStructs...` |
| 候选摘要与候选池对不上 | —— | `TestReplayRoutingDetectsCandidateDigestChange` |
| 排除原因未在闭集注册 | —— | `TestReplayRoutingRejectsUnregisteredRejectionReason` |
| 记录文件结构版本不受支持 | `ErrSchemaVersion` | `TestDecodeRejectsUnknownFieldsAndBadSchema` |
| 含被禁字段 | `ErrForbiddenField` | 见 4.2 |

**"喂错策略包"必须是 rejected 而不是 deny**：跨组织回放（拿 hospital-a 的记录只喂 university
的包）落在 `StatusRejected`，因为"没有资格参与这次判定"和"没有授权"是完全不同的运维结论。
测试：`TestReplayCrossOrganizationIsNotSilentDeny`。

### 4.4 回放结果的三态与结构化差异

`Status`（`report.go:34`）：`passed` / `mismatch` / `rejected`。
`mismatch` 是 §3.0 影响面报告要的东西（记录能回放，但当前策略集给了不同结论）；
`rejected` 是不可信回放。差异以 `FieldDiff{field, expected, actual}` 输出（`report.go:46`）——
只返回 bool 的回放在影子运行对不上时毫无价值，运维必须一眼看出是策略版本变了还是某条规则 TTL 到期。

`Options.StrictReasonChain`（`replayer.go:25`）默认关闭，只比结论与决定性规则：
`Reasons` 里带 `condition_unmet` 这类中间过程项，规则文案微调就可能让它抖动，
把它设成默认会让门禁天天报假红。要审计完整原因链时显式打开
（`TestReplayStrictReasonChain`）。

### 4.5 确定性的三处保障

- **稳定排序**：范围链、候选 provider、命中规则、差异项全部显式排序，绝不依赖 map 遍历顺序。
  `TestReplayDigestIgnoresInputOrder` 断言乱序输入产出同一报告。
- **golden fixture**：`testdata/replay-baseline.json` + 摘要常量
  `61dd8998…3a78be`（`fixture_test.go:14-18`）。`TestGoldenFixtureEqualsInMemoryBuild`
  把"文件里的基线"与"内存里现算的记录"逐字节对齐，因此 A 包契约的**非预期变更**会立刻撞红。
  重新生成：`go test ./internal/replay/ -run TestWriteGoldenFixture`（改基线必须与策略变更同一次提交）。
- **注入式抽样器**：`Sampler` 接口 + 默认 `replay-sampling-v1`（`sampler.go`）。
  只有记录声明的算法与本实现一致时才逐位比对首选/尝试顺序；其它算法标识降级为
  **解释性回放**，不声称逐位相同（`TestReplayRoutingExplanatoryModeOnUnknownAlgo`、
  `TestReplayRoutingUsesInjectedSampler`）。这是 §2.8 的分工：在线权重随机不受影响，
  回放必须显式取 seed。D 包合并后主线可注入其抽样器实现，使在线与回放逐位一致。
- **fallback 不绕权限**：`TestReplayRoutingDetectsFallbackBypassingPolicy`。
- **并发安全**：`TestReplayerIsConcurrencySafe`（配合 `-race`）。
- **策略版本来源**：`TestReplayRoutingVersionSourceUsesFilter` 断言版本串必须来自
  `BundleSet.Filter(chain)` 的实际加载结果（§3.0 要求 `RoutingPlan.PolicyVersion` 不得凭空调用方声明）。

## 5. §3.0 三类必需测试：落地位置

§3.0 要求接线过程必须能用三类测试证明。数据结构与判定口径在 `internal/replay`
（`WiringMode` 三态 `ModeShadow`/`ModeEnforce`/`ModeLegacy`、`StatusMismatch` 计数、
`Report` 汇总），**测试本体在接线方**（`internal/server/policy30_test.go`），因为三条都要
在同一请求上同时跑两条链路：

| 必需测试 | 证明的约束 | 落地位置 |
|---|---|---|
| shadow vs legacy 差异报告 | 影子「只看不动」：产出策略版本与差异计数，不改选路、不拒请求、不写回放输入 | `TestPolicy30ShadowObservesWithoutChangingRouting`、`TestClassifyShadowDiffSeparatesNoConclusionFromDisagreement` |
| enforce 影响面 | 被拒模型短路 403（不碰上游、不产影子计数）；分级门逐家收窄候选池；回落不允许压过 deny | `TestPolicy30EnforceBlocksDeniedModel`、`TestPolicy30EnforceNarrowsPoolByDataLevel`、`TestPolicy30FinishPolicyFallbackCannotOverrideDeny` |
| per-scope 回滚还原 | 回退到 legacy 后行为与回退前一致，且按 scope 回滚不覆盖别人的策略包 | `TestPolicy30RollbackToLegacyRestoresBehavior`、`TestPolicy30RollbackPerScopeWithoutCoveringBundle` |

差异报告的数字面同时出现在 `/healthz`，因此**管理台的模拟入口不许掺影子计数**
（`TestAdminPolicySimulateAllowAndDeny` 断言模拟前后 `evaluated` 不变）：
管理员点一次「模拟」就改一次一致性指标，差异报告从此不可信。

判定入口照旧：`replay.New(set, Options{Now: 固定时刻})` + `Run(File)` 对两次导出的
记录做 diff，不需要新写比较逻辑。

处理器链的执行接线（§3.0 线 2）另有一套同类三分类，落在
`internal/server/procexec_test.go`：正常路径（脱敏真的到达上游 / 流式逐段过滤 /
计划里的链与装配同源）、拒绝路径（400/413/403/503 与影子、legacy 的零影响）、
失败路径（`fail_closed` 与 `fail_open`、响应侧失败的归因、`WriteHeader` 之前的改判）。
断言全部盯「越界」而不是「功能」—— 功能 E 包自己测过，接线会犯的是另一类错，
逐条见 §8.9 的表。

## 6. 发布与回滚演练清单

合并顺序（§9）：A → B/C/E → D → F → G → H。每次合并后：

1. `./scripts/release-check.sh --3p0` 必须全绿（八个 OWNED 成员一个都不能红）；
2. `./scripts/test-matrix.sh` 全量（含三数据库）；
3. 影响并发代码时 `go test -race ./...`；
4. 回放基线：`go test ./internal/replay/ -run Golden`；
5. 涉及 store 结构变更时，按 §2.7 在演练库执行"备份 → 迁移 → 行数/主键/金额/scope 映射校验 →
   回滚"四步，并保留校验输出作为合并证据；
6. 检查 §5 表格里的"尚未实现"是否有变化，有则同步本手册。

## 7. 已知限制

- 本包**不做**记录导出：线上请求怎么产出 `DecisionRecord`（在 server 侧采样、落库、导出文件）
  仍未实现；`DecisionRecordFrom`/`RoutingRecordFrom` 只是从 A 包对象构造记录的纯函数。
  因此三类测试目前跑在进程内装配的场景上，跨进程的证据链（导出文件 → `replay.Run`）还没闭合。
- 策略包（`BundleSet`）的加载已落地：`internal/config/policybundle.go` 读
  `policy.bundles_dir`，`internal/server/policy30.go:62` 持有按范围过滤前的全集。
  管理侧的只读视图在 `internal/server/policyadmin.go`，**写入（发布/回滚）仍不在门禁范围内**。
- `internal/executor` 与 `examples/university` 已合并进 OWNED 名单，任何一步红都拦停。
- INFLIGHT 名单已清空（并行期口径收掉，见 §2）。机制保留：将来新包仍从 INFLIGHT 起步。

### 7.1 §2.7 规则 8：2.x 兼容层的现存面（只剩两处，都在 store）

价目、审计、熔断、用量四块的旧字符串读写 API 已全部删除（`InsertUserPrice` /
`UserPriceAt` / `UserPricesEffective` / `ListUserPrices` / `HasEffectiveUserPrices` /
`ScopeDefault` / `ScopeUser` / 无范围的 `Audit`·`AuditRecent` / `ProviderStatus` 三件套 /
按 `user_name` 读 `usage_user_daily` 的那五条），接口里不再留着「以后再说」的分支。
仍然存在的两处**不是**兼容读路径，而是迁移与历史数据本身要求的：

1. `scope_migration.go` 里读 2.x 的 `user_prices.scope` 串与 `usage_user_daily` 整表 ——
   一次性升级的镜像源，跑完就不再经过（`DecodeLegacyPriceScope` 只有它调）。
   结构已是 3.0 但 `usage_scope_daily` 为空时也会补一次镜像（`mirrorUsageScopeDailyIfEmpty`）：
   否则老账单会因为「表形状对了」而被跳过，读出来一律是 0。
2. `resolveRequestScope` 里 `UserName` → `(user, <用户名>)`（规则 3）——
   只服务旁路写进来的历史记录。在线主线在 `forwarder.go` 就把 `rec.Scope` 定实了。
   静态 key 与匿名本机请求**不**套这个映射：熔断桶是 `system:global`，但那只代表
   「用的是全局池」，不等于这笔账记在系统头上（规则 5：没有归属就留空，不猜）。

### 7.2 录价口径的行为变化（升级后必须知道）

- `llmproxy price set user` 与 `PUT /v1/_admin/prices/user` 的 scope 参数从
  `default` / `user:<名>` 换成精确选择器 `kind:id`，全局兜底价写 `system:global`。
  旧的 `default` 串现在直接 400，不再静默当成全局默认 —— 组织级、项目级价目
  （`organization:*` / `project:*`）从此才有地方放。
- 响应与 CSV 一律给 `scope_kind` + `scope_id` 两列，不给折叠成一个串的 scope（规则 1）。
- 取价链条是「最具体的范围优先」，固定次序 user > project > organization > system，
  与链条的传入顺序无关。这次修掉的实现：`sortBySpecificity` 的比较符写反，
  结果是全局兜底价压过个人专属价 —— 那是静默算错钱。回归测试是
  `TestScopePriceChainIsOrderIndependent`（三种传入顺序 + 逐层回落）。
- 读价与判 `priced` 时，范围链条末端的系统全局兜底由调用方**显式**给出
  （`internal/server/prices.go:priceScopeChain`），不再藏在某个旧 helper 里。
  少给这一腿会让「只有全局兜底价」的库被判成「没价目」，报表退回估算段。


## 8. §3.H 声明面：处理器与知识库（配置 → 管理 API → 管理台）

本节头四段交付**声明的读写面**：`config.yaml` 里多了 `processors` 与 `knowledge_sources`
两段，各自有加载校验、编辑层、管理 API、OpenAPI 与管理台面板。§8.7 起是**执行面** ——
声明怎么在请求生命周期里真的跑起来，以及跑到哪一步为止。

### 8.1 边界：这一段声明约束，不声明运行参数

| 在配置文件里 | 不在配置文件里 | 为什么 |
|---|---|---|
| 阶段、正文档位、范围、超时与体积上限、`fail_closed`、出网白名单、`version` | 脱敏类型子集、字段替换规则、JSON Schema、过滤词表、sidecar 的端点与请求头（在 `processor_params/<声明名>.json`，见 §8.7）、sidecar 的 HTTP 客户端与原文授权判定器、pseudonym key | E 包规定 `Config` 在**注册期**绑定（`Register` 的 cfg 参数），把运行参数塞进配置文件等于让配置成为第二个真值来源，而且密钥会跟着进文件；HTTP 客户端与判定器只能由 server 侧注入 —— 前者给进文件就绕过了 dialer 的出网白名单，后者给进文件等于让「谁被授权看原文」不再只有策略包一个业务源 |
| 知识源的委托端点、服务的知识库 ID 列表、预算与响应体积上限 | 检索服务的凭证、transport | C 包要求 transport 由接线方从出网策略注入；凭证进 URL 会被委托协议拒（`ValidateEndpoint` 禁 userinfo） |

判据一条都不在 H 层重抄：每条声明由所属领域包判 —— 处理器走
`config.ProcessorDef.Spec()`（内部调 `processor.Spec.Validate()` + `policy.ParseBodyAccess`
+ `processor.ParsePhase`），知识源走 `knowledge.ValidateEndpoint` / `ValidateKnowledgeBaseID`。
`Spec()` 比 `Spec.Validate()` 更严三处（`body_access` / `fail_closed` / `scope` 必须显式写、
`timeout_ms > 0`）：这些字段决定「正文会不会离开网关」「失败时放行还是拒」，
缺省值在这类字段上不是便利，是把一次漏配变成一次静默的宽松放行。

### 8.2 一条落盘通道，三段配置

`policy` / `processors` / `knowledge_sources` 的写侧共用 `Server.commitSectionConfig`
（`internal/server/policypublish.go`）：临时文件宽松+严格两次试读 → 按引用加载策略包（policy 段的
`sectionGuard`）→ 备份（留 5 份）→ 原子改名 → `chmod 0600` → 带范围的审计 → 等热加载并回报。
`policyAudit` 是这个通道的**必填**参数，不是各调用点自觉加的可选字段 —— 于是
「新增一个写接口却忘了记审计」在编译期就不成立。失败路径整笔还原（含内容文件的 undo），
磁盘与审计都不留痕。

### 8.3 三条不可绕过的接口规则

1. **整段提交**：改一条也要把整个数组发回来。段是整体替换的，做成增量写会让
   「谁最后写」决定线上形态，而 diff 里看不出中间态。
2. **缺字段 ≠ 空段**：请求体必须带本段那个键（`{"processors": […]}` /
   `{"knowledge_sources": […]}`），清空要显式传 `[]`。否则一个漏带键的请求就删掉整段声明。
   带错段的键、多带字段都在读磁盘之前拒掉。
3. **未知键直接拒**：`readJSONBodyStrict` 用 `DisallowUnknownFields`，与配置加载的
   `KnownFields(true)` 同一条规则。`condition` 写成 `conditions`、`expires_at` 写成
   `expire_at`，宽松解码会得到一条「没有条件、没有期限」的声明并把它发布出去。

读侧一律从**文件原文**构建（`config.RawProcessors` / `RawKnowledgeSources`），不是加载后的
`Config`：加载后的形态有些值已被展开或清洗，把那份发给界面会让「界面上看到的」和
「磁盘上写的」分开。空段回 `[]` 而不是 `null`；磁盘那一版读不回来时 GET **仍然 200** 并给
`baseline_error`（列表退回显示服务当前加载着的那一份）—— 连读都被 500 会让人以为服务挂了，
而修好它的正当路径正是整段保存一份合法声明。

### 8.4 界面拿到的是服务端的事实，不是自己抄的表

`config.Vocabulary()` 下发阶段闭集、内置类型（取 `processor.NewRegistry().KnownTypes()`，
部署 `RegisterType` 注入的自定义类型自动跟上）、三档正文访问、范围种类与全部领域上限；
管理台只回显它，并且只做两件检查：JSON 语法、顶层是不是数组。§9「H 只能调用服务端策略接口，
不能在前端重新计算权限」在这里的落法是不在前端重抄任何一条领域规则。

每次读与写都带 `mode` + `applies`：`applies` 为真当且仅当 `policy.mode = enforce`（§3.0 规则 2）。
「保存成功」与「正在生效」是两件事 —— 不把这一层写在最上面，脱敏就会在 legacy 下被当成已经上线。
管理台「处理器与知识库」卡片因此把 `policy.mode → 参与/暂不参与` 放在第一个统计格。

### 8.5 审计的非放大原则

动作是 `processor.config.write` / `knowledge.config.write`，归属固定在 `system:global`
（§2.7 规则 2：全局开关这类动作「关于」系统范围，actor 那一列才记谁按的）。
detail 只写条数、名字与范围（`处理器声明：0 条 → 1 条（pii-request@*)`、
`知识源委托入口：1 条 → 0 条（已清空）`），**不含端点与阈值数值**：基线读不回来时领域错误信息
里可能带着含凭证的 URL，把它抄进审计库等于把别人写错的凭证搬进另一个持久化位置。
被拒的写不落审计（`TestAdminProcessorsBadDeclarationLeavesFileUntouched` 数过条数）。

### 8.6 本轮顺手修掉的两个真实缺陷

1. **空段渲染出重复顶层键**（`internal/config/editproc.go`）：清空处理器时正文里又写了一遍
   `processors: []`，而 `spliceSection` 已经输出了 `processors:` 那行 —— YAML 直接拒，
   于是「在界面上点清空」会把配置文件写成加载不了的状态。现在空列表只留 key 行与说明注释，
   读侧用 `sectionIsNull` 把「key 挂着、值为空」与 `[]` 视为同义。
2. **`configEqual` 漏比两段声明**（`internal/config/store.go`）：只改处理器或知识源声明会被判成
   「配置没变」→ `revision` 不推进 → 重载回调直接 return → 管理台一直报「还在等热加载」。
   这与 §policyEqual 那段注释记的是同一类事故（回滚开关按下去没反应，比没有开关更糟）。
   新增 `processorsEqual` / `knowledgeSourcesEqual`，比的是 **normalize 之后的领域形态**：
   `ProcessorDef.FailClosed` 是 `*bool`，两次 Parse 各分配一个指针，直接 `!=` 会恒不等 ——
   那会让每次保存都白丢一次上游连接池（同 `databaseEqual` 的坑）。
   回归测试：`TestConfigEqualIdenticalDeclarationsReparses`（含「`kb-course ` 与 `kb-course`
   是同一个库 ID」）与 `TestConfigEqualDetectsDeclarationChanges`（换类型/阶段/范围/超时/版本/
   白名单/加知识源，8 个方向都判「变了」且比较对称）。

### 8.7 执行期接线（§3.0 线 2：声明现在真的会跑）

上一节那句「`ProcessorChain` 恒为空」已经过时。三块新代码，边界各自清楚：

| 文件 | 只负责 | 为什么切在这里 |
|---|---|---|
| `internal/server/procruntime.go` | 按声明装配：`Registry.Register` + 运行参数文件 + sidecar 客户端与原文授权判定器的注入 | 声明仍是唯一真值源；客户端与判定器只能由 server 侧给（E 包拒绝自己造连接，那会绕过 dialer 的出网白名单） |
| `internal/server/procexec.go` | 一次请求的处理器调用：请求阶段、响应阶段（缓冲/流式）、审计阶段、失败→HTTP 回话的归类 | 装配失败**不在这里回话**，只记在 `procRuntime` 上；影子模式完全不受影响 |
| `internal/server/forwarder.go` | 插入点：策略判定与配额之后、重试循环之前跑请求阶段；`relay` 里跑响应阶段 | 「before-route」的实际边界是**真正选定供应商的那一刻**，不是计划算出来那一刻 —— `policyJudge` 被无副作用的路由模拟复用，插在计划处会让模拟跑处理器 |

三个决定值得单独记下，因为它们都是「不做也没人报错」的那类：

1. **只有 `policy.mode = enforce` 参与**。影子读正文 = 用合规成本换一个不改变行为的数字，
   §3.0 线 1 明令禁止；legacy 则连装配都不该发生（回滚开关必须真的一刀切）。
2. **装不起来就拒**。命中本范围链的声明若装配失败，请求得到 503
   （`processor_unavailable`），而不是「处理器没跑、正文原样发出去」。这是 §2.9 规则 5
   「敏感策略默认 fail_closed」的接线形态 —— 同一条坏声明在影子下必须零影响，两侧都有测试钉住。
3. **处理器的失败不算供应商的失败**。响应侧拒收把 `rec.ErrorType` 写成 `processor`、
   `outcome` 记成 `relayAmbiguous`，因此一家正常返回 200 的上游不会因为我们的链子起不来而进冷却。

§2.9 规则 7/8 的可观测面：`X-Llmproxy-Body-Pipeline` 声明头按**事实累加**，不互相覆盖 ——
请求正文被整段读过并改写过就写 `buffered`（同时 `Content-Length` 跟着新长度重算），
响应逐段包装就追加 `stream`，两侧都参与时是 `buffered,stream`。之所以不能覆盖：
`buffered` 恰恰是 `max_input_bytes` 与 `timeout_ms` 生效的那一段，只剩一个 `stream`
就等于把唯一有信息量的事实丢掉。`metadata-only` 档位既不缓冲也不改写，因此**不**出现这个头。
审计阶段拿到的是 `procAuditMetadata` 那份结论元数据（request id / 类型 / 模型 / 供应商 /
状态 / 是否流式 / 尝试次数 / 策略版本），不含 `rec.ErrorMsg` —— 错误原文可能带着上游回包片段。

启动期新增 `server.CheckProcessorParams(cfg)`（`cmd/llmproxy/main.go` 里紧跟
`CheckPolicyRuntime`）：声明了处理器却没有运行参数文件、文件不是合法 JSON、或文件里写了
别的类型的键，一律拒绝启动。留到第一个真实请求才暴露的话，表现是「界面说这条声明存在而
运行时没人跑它」，与策略包缺文件是同一类事故。

### 8.8 仍然没做（不伪装）

1. **处理器执行明细不落库**。逐条结果（哪个处理器、什么原因码、改写计数、耗时）只进日志
   （`event=processor_*`），装配失败也只有日志（启动/热加载的 ERROR）与拒绝回话两个面 ——
   管理台还没有「这条声明装不起来」的红灯位。落库要 `store` 三方言各加一张表并过
   `test-matrix.sh`，那是一次独立的存储变更，不该塞进接线这一包顺手做。
2. **`internal/executor` 与 `internal/knowledge` 仍未接入请求路径**：`internal/server/` 里
   没有一处 import 这两个包。也就是说工具调用执行与检索增强还只存在于领域面和测试里，
   线上请求不经过它们。
3. **跨请求稳定的假名不支持**。`PseudonymKey` 是密钥，按 §8.1 的同一条理由不接受文件注入，
   于是 `pii-mask` 今天只能用每请求随机 salt —— 占位符哈希在不同请求之间对不上。
4. **`knowledge_sources` 声明没有 transport 注入方**。C 包要求委托客户端由接线方从出网策略
   构造（与 sidecar 同一个形态），这一段还没写，因此知识源目前只做加载校验与管理面。
5. **处理器拒收的响应不记 usage**。上游回包里的 `usage` 在改判错误时**不**进记录 ——
   与既有的 502/超时路径同口径（那次花钱没换来一次成功应答）。要不要照计是计费口径问题，
   留给单独的决策，不在这里静默选边。
