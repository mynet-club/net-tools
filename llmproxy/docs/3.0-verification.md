# 3.0 验证手册（工作包 I）

本手册是手册 §8「Definition of Done」的可执行化：一条命令跑什么、每一步证明了哪条约束、
哪些东西**还没做**（不伪装）。凡"未实现"一律显式写出并给出判定入口。

## 1. 怎么跑

在 `llmproxy/` 目录下：

```bash
./scripts/release-check.sh --3p0        # 3.0 领域门禁：gofmt / 测试覆盖 / OWNED 包 vet+test+race
./scripts/test-matrix.sh   --3p0        # 3.0 领域包按包 go test -race -count=1
./scripts/release-check.sh --pkg=./internal/replay/...   # 定向到某个包（可重复给多个）
./scripts/release-check.sh              # 完整发布门禁（原有步骤与用法保持不变）
./scripts/test-matrix.sh                # 完整测试矩阵：同一套 store 断言跑 SQLite/MySQL/PostgreSQL
```

三个新开关（`--3p0`、`--pkg=`）都是**加法式**的：不带参数时行为与改动前一致，
构建产物与发布流程不受影响。`bash -n` 已覆盖两个脚本的语法。

## 2. OWNED / INFLIGHT：并行期口径已收掉

包分两类，清单就在两个脚本顶部（`DOMAIN_OWNED` / `DOMAIN_INFLIGHT`，
`release-check.sh:23-24`、`test-matrix.sh:20-21`）：

| 类别 | 当前成员 | 红了的后果 |
|---|---|---|
| OWNED（已合并并冻结） | `internal/policy`、`internal/replay`、`internal/identity`、`internal/knowledge`、`internal/processor`、`internal/routing`、`internal/executor`、`examples/university` | 门禁**失败并非 0 退出** |
| INFLIGHT（并行在途） | 空 | —— |

两类拆分这套机制**保留但不启用**。它的由来：并行期「别人的包编译不过」既不能被伪装成通过
（所以错误原文必须可见），也不能算成本包的发布失败（所以不能非 0 退出）。七个领域包与高校
示例都按 §8 合并之后，这个口径必须收掉 —— 否则门禁等于对半数代码失效。
`gate_gofmt` 在名单为空时显式打印「无在途包」，就是为了不在输出里留下「还有包在途」的误读。

**迁移规则**（将来新包仍然适用）：一个包按 §8 复核合并后，主线要把包名从两个脚本各自的
`DOMAIN_INFLIGHT` 移到 `DOMAIN_OWNED`，并更新本表。脚本里**不单独硬编码包名**：
`--3p0` 的 OWNED 全量 vet+test 目标由 `DOMAIN_OWNED` 派生，两个脚本的 `domain_tag`
都按同一份名单归类 —— 漏改的后果是该包从此享受"红也不拦"的待遇，
门禁静默失效比没有门禁更危险。

缺席的包（目录不存在）跳过并提示"该工作包还没派"；有源文件却没测试文件的包按类别判
OWNED 失败 / INFLIGHT 警告（`gate_tests_present`）。

## 3. 每一步证明了什么（对齐 §6 / §8）

| 门禁步骤 | 证明的约束 |
|---|---|
| `gofmt -l` 领域包 | §5 代码规范可机器核查，不靠自觉 |
| 测试覆盖检查 | §8.2「正常/拒绝/失败路径有测试」的必要条件（有源必须有测） |
| 按包 `go vet` | 类型与常见错误用法，按包跑是为了在并行期定位到归属 |

| `--3p0` 对 INFLIGHT 的探测 | 只 `go test -count=1` 并把错误原文打出来，保证在途失败可见但不伪装成通过 |

## 4. 回放记录的数据契约（`internal/replay`）

### 4.1 记录里有什么

`DecisionRecord`（`record.go:174`）：`request_id`、`recorded_at`、`policy_version`、
`scope_chain`、`subject`（`SubjectSnapshot`：subject/source/roles/groups/projects/
auth_methods/issued_at/expires_at）、`context`（`ContextSnapshot`：purpose/organization/
project/data_level/allowed_regions/wiring_mode）、`resource`、`action`、
`effect`、`reason`、`reasons`、`winner`/`matched`（`RuleRef`，只存规则标识与 `sort_key`）、
`expires_at`、`external_plaintext_allowed`。

`RoutingRecord`（`record.go:396`）：`request_id`、`recorded_at`、`policy_version`、
`routing_seed`、`routing_epoch`、`sampling_algo`、`candidates_digest`、`candidates`
（按 `policy.SortCandidates` 稳定顺序写入）、`plan`、`rejections`。

`File`（`codec.go:51`）刻意**没有** `generated_at`：文件级时间戳会让同一批记录两次导出
产生不同字节，而 §2.8 要的是同一输入同一输出；时刻信息由每条记录的 `recorded_at` 承担。

### 4.2 为什么不含正文（以及怎么把它变成会失败的断言）

§2.8 明确"不需要记录请求正文"，§2.9 限定正文访问，§5 禁止落真实密钥与个人信息。
本包不依赖自觉，而是用四层断言钉住：

1. `TestRecordStructsCarryNoBodyOrCredentials` —— 反射扫描记录结构体的全部字段名；
2. `TestEncodedRecordsHaveNoForbiddenKeys` —— 扫描**序列化后的 JSON 键**（结构体可以藏，
    map 键藏不住）；
3. `TestDecodeRejectsForbiddenKeysEvenWhenNested` —— 解码时拒掉嵌套任意深度出现的被禁键，
   所以"手工改过的记录文件"也进不来；
4. `TestRecordOmitsDisplayName` / `TestRecordOmitsConditionValues` —— 结论性输出里
   不带显示名（PII）与 conditions 取值（可能含数据内容）。

被禁词表 `ForbiddenFieldWords()`（`codec.go:26`）：`body`、`payload`、`content`、`prompt`、
`messages`、`message`、`apikey`、`api_key`、`secret`、`token`、`password`、`credential`、
`baseurl`、`base_url`、`cookie`、`authorization`、`raw`、`email`、`phone`、`idcard`、`id_card`。
连 `raw` 与 `content` 都禁，是因为 `raw_body` 这类命名会诱导实现方往记录里塞正文片段。
A 包 `internal/policy/leak_test.go` 用同一口径，两包必须一致 —— 改一处就要改两处。

注意 `external_plaintext_allowed` 是布尔：它记录"是否允许未脱敏文本出网给 sidecar"这个**结论**
（§2.9 规则 3、4），正文本身从不入库。

### 4.3 回放的 fail_closed 清单（每条都有对应测试）

回放一律 fail_closed，绝不退化成"随机选一个"或"按 deny 收"：

| 拒绝条件 | 哨兵 | 测试 |
|---|---|---|
| 策略集为空 | `ErrEmptyBundleSet` | `TestNewFailClosed` |
| 未显式给定时钟 | `ErrClockRequired` | `TestReplayNeedsFixedClock` |
| 路由记录缺 `routing_seed` | `ErrSeedMissing` | `TestReplayRoutingRequiresSeed` |
| seed 与 `(request_id, policy_version, routing_epoch)` 推导值不符 | —— | `TestReplayRoutingDetectsWrongSeedDerivation` |
| 记录结构自相矛盾 | `ErrRecordInvalid` | `TestReplayRejectsBrokenRecord`、`TestRecordStructs...` |
| 候选摘要与候选池对不上 | —— | `TestReplayRoutingDetectsCandidateDigestChange` |
| 排除原因未在闭集注册 | —— | `TestReplayRoutingRejectsUnregisteredRejectionReason` |
| 记录文件结构版本不受支持 | `ErrSchemaVersion` | `TestDecodeRejectsUnknownFieldsAndBadSchema` |
| 含被禁字段 | `ErrForbiddenField` | 见 4.2 |

**"喂错策略包"必须是 rejected 而不是 deny**：跨组织回放（拿 hospital-a 的记录只喂 university
的包）落在 `StatusRejected`，因为"没有资格参与这次判定"和"没有授权"是完全不同的运维结论。
测试：`TestReplayCrossOrganizationIsNotSilentDeny`。

### 4.4 回放结果的三态与结构化差异

`Status`（`report.go:34`）：`passed` / `mismatch` / `rejected`。
`mismatch` 是 §3.0 影响面报告要的东西（记录能回放，但当前策略集给了不同结论）；
`rejected` 是不可信回放。差异以 `FieldDiff{field, expected, actual}` 输出（`report.go:46`）——
只返回 bool 的回放在影子运行对不上时毫无价值，运维必须一眼看出是策略版本变了还是某条规则 TTL 到期。

`Options.StrictReasonChain`（`replayer.go:25`）默认关闭，只比结论与决定性规则：
`Reasons` 里带 `condition_unmet` 这类中间过程项，规则文案微调就可能让它抖动，
把它设成默认会让门禁天天报假红。要审计完整原因链时显式打开
（`TestReplayStrictReasonChain`）。

### 4.5 确定性的三处保障

- **稳定排序**：范围链、候选 provider、命中规则、差异项全部显式排序，绝不依赖 map 遍历顺序。
  `TestReplayDigestIgnoresInputOrder` 断言乱序输入产出同一报告。
- **golden fixture**：`testdata/replay-baseline.json` + 摘要常量
  `61dd8998…3a78be`（`fixture_test.go:14-18`）。`TestGoldenFixtureEqualsInMemoryBuild`
  把"文件里的基线"与"内存里现算的记录"逐字节对齐，因此 A 包契约的**非预期变更**会立刻撞红。
  重新生成：`go test ./internal/replay/ -run TestWriteGoldenFixture`（改基线必须与策略变更同一次提交）。
- **注入式抽样器**：`Sampler` 接口 + 默认 `replay-sampling-v1`（`sampler.go`）。
  只有记录声明的算法与本实现一致时才逐位比对首选/尝试顺序；其它算法标识降级为
  **解释性回放**，不声称逐位相同（`TestReplayRoutingExplanatoryModeOnUnknownAlgo`、
  `TestReplayRoutingUsesInjectedSampler`）。这是 §2.8 的分工：在线权重随机不受影响，
  回放必须显式取 seed。
  接线侧（§2.8 记录导出，见 §11）已把线上算法如实声明为 `routing-seeded-splitmix64-v1`
  （`internal/server/replay30.go:replaySamplingAlgoOnline`），因此今天的线上记录进回放器
  **一律走解释性回放**，首选顺序不参与比对。要让两者逐位一致，需要主线把 D 的抽样器
  注入 `replay.Options.Sampler` —— 而 `replay.File` 的冻结 schema 只能携带 seed 与候选池，
  携带不了 `routing.PlanFromReplay` 需要的 `ReplayInput` 结构，那是一次接口裁决（§11.5）。
- **fallback 不绕权限**：`TestReplayRoutingDetectsFallbackBypassingPolicy`。
- **并发安全**：`TestReplayerIsConcurrencySafe`（配合 `-race`）。
- **策略版本来源**：`TestReplayRoutingVersionSourceUsesFilter` 断言版本串必须来自
  `BundleSet.Filter(chain)` 的实际加载结果（§3.0 要求 `RoutingPlan.PolicyVersion` 不得凭空调用方声明）。

## 5. §3.0 三类必需测试：落地位置

§3.0 要求接线过程必须能用三类测试证明。数据结构与判定口径在 `internal/replay`
（`WiringMode` 三态 `ModeShadow`/`ModeEnforce`/`ModeLegacy`、`StatusMismatch` 计数、
`Report` 汇总），**测试本体在接线方**（`internal/server/policy30_test.go`），因为三条都要
在同一请求上同时跑两条链路：

| 必需测试 | 证明的约束 | 落地位置 |
|---|---|---|
| shadow vs legacy 差异报告 | 影子「只看不动」：产出策略版本与差异计数，不改选路、不拒请求、不写回放输入 | `TestPolicy30ShadowObservesWithoutChangingRouting`、`TestClassifyShadowDiffSeparatesNoConclusionFromDisagreement` |
| enforce 影响面 | 被拒模型短路 403（不碰上游、不产影子计数）；分级门逐家收窄候选池；回落不允许压过 deny | `TestPolicy30EnforceBlocksDeniedModel`、`TestPolicy30EnforceNarrowsPoolByDataLevel`、`TestPolicy30FinishPolicyFallbackCannotOverrideDeny` |
| per-scope 回滚还原 | 回退到 legacy 后行为与回退前一致，且按 scope 回滚不覆盖别人的策略包 | `TestPolicy30RollbackToLegacyRestoresBehavior`、`TestPolicy30RollbackPerScopeWithoutCoveringBundle` |

差异报告的数字面同时出现在 `/healthz`，因此**管理台的模拟入口不许掺影子计数**
（`TestAdminPolicySimulateAllowAndDeny` 断言模拟前后 `evaluated` 不变）：
管理员点一次「模拟」就改一次一致性指标，差异报告从此不可信。

判定入口照旧：`replay.New(set, Options{Now: 固定时刻})` + `Run(File)` 对两次导出的
记录做 diff，不需要新写比较逻辑。记录本身由接线侧在判定现场产出并可导出（§11）。

处理器链的执行接线（§3.0 线 2）另有一套同类三分类，落在
`internal/server/procexec_test.go`：正常路径（脱敏真的到达上游 / 流式逐段过滤 /
计划里的链与装配同源）、拒绝路径（400/413/403/503 与影子、legacy 的零影响）、
失败路径（`fail_closed` 与 `fail_open`、响应侧失败的归因、`WriteHeader` 之前的改判）。
断言全部盯「越界」而不是「功能」—— 功能 E 包自己测过，接线会犯的是另一类错，
逐条见 §8.9 的表。

执行器接线（§3.F）同样是这套三分类，落在 `internal/server/executor30_test.go`：
正常路径（委托确实承载交换且上游收到的装配同形 / 两条链路的账与冻结成本逐字段一致 /
流式照常逐段）、拒绝路径（legacy 与 shadow 零委托、未注册执行器名拒候选且零出网、
八条不委托理由各自归位）、失败路径（通道装不起来指名原因且不含密钥、超时归因两条路同形、
上游 4xx/5xx 的状态与错误体原样透传）。逐条见 §10.5 的表。

## 6. 发布与回滚演练清单

6. 检查 §5 表格里的"尚未实现"是否有变化，有则同步本手册。

### 7.1 §2.7 规则 8：2.x 兼容层的现存面（只剩两处，都在 store）

价目、审计、熔断、用量四块的旧字符串读写 API 已全部删除（`InsertUserPrice` /
`UserPriceAt` / `UserPricesEffective` / `ListUserPrices` / `HasEffectiveUserPrices` /
`ScopeDefault` / `ScopeUser` / 无范围的 `Audit`·`AuditRecent` / `ProviderStatus` 三件套 /
按 `user_name` 读 `usage_user_daily` 的那五条），接口里不再留着「以后再说」的分支。
仍然存在的两处**不是**兼容读路径，而是迁移与历史数据本身要求的：

1. `scope_migration.go` 里读 2.x 的 `user_prices.scope` 串与 `usage_user_daily` 整表 ——
   一次性升级的镜像源，跑完就不再经过（`DecodeLegacyPriceScope` 只有它调）。
   结构已是 3.0 但 `usage_scope_daily` 为空时也会补一次镜像（`mirrorUsageScopeDailyIfEmpty`）：
   否则老账单会因为「表形状对了」而被跳过，读出来一律是 0。
2. `resolveRequestScope` 里 `UserName` → `(user, <用户名>)`（规则 3）——
   只服务旁路写进来的历史记录。在线主线在 `forwarder.go` 就把 `rec.Scope` 定实了。
   静态 key 与匿名本机请求**不**套这个映射：熔断桶是 `system:global`，但那只代表
   「用的是全局池」，不等于这笔账记在系统头上（规则 5：没有归属就留空，不猜）。

### 7.2 录价口径的行为变化（升级后必须知道）

- `llmproxy price set user` 与 `PUT /v1/_admin/prices/user` 的 scope 参数从
  `default` / `user:<名>` 换成精确选择器 `kind:id`，全局兜底价写 `system:global`。
  旧的 `default` 串现在直接 400，不再静默当成全局默认 —— 组织级、项目级价目
  （`organization:*` / `project:*`）从此才有地方放。
- 响应与 CSV 一律给 `scope_kind` + `scope_id` 两列，不给折叠成一个串的 scope（规则 1）。
- 取价链条是「最具体的范围优先」，固定次序 user > project > organization > system，
  与链条的传入顺序无关。这次修掉的实现：`sortBySpecificity` 的比较符写反，
  结果是全局兜底价压过个人专属价 —— 那是静默算错钱。回归测试是
  `TestScopePriceChainIsOrderIndependent`（三种传入顺序 + 逐层回落）。
- 读价与判 `priced` 时，范围链条末端的系统全局兜底由调用方**显式**给出
  （`internal/server/prices.go:priceScopeChain`），不再藏在某个旧 helper 里。
  少给这一腿会让「只有全局兜底价」的库被判成「没价目」，报表退回估算段。


## 8. §3.H 声明面：处理器与知识库（配置 → 管理 API → 管理台）

本节头四段交付**声明的读写面**：`config.yaml` 里多了 `processors` 与 `knowledge_sources`
两段，各自有加载校验、编辑层、管理 API、OpenAPI 与管理台面板。§8.7 起是**执行面** ——
声明怎么在请求生命周期里真的跑起来，以及跑到哪一步为止。

### 8.1 边界：这一段声明约束，不声明运行参数

| 在配置文件里 | 不在配置文件里 | 为什么 |
|---|---|---|
| 阶段、正文档位、范围、超时与体积上限、`fail_closed`、出网白名单、`version` | 脱敏类型子集、字段替换规则、JSON Schema、过滤词表、sidecar 的端点与请求头（在 `processor_params/<声明名>.json`，见 §8.7）、sidecar 的 HTTP 客户端与原文授权判定器、pseudonym key | E 包规定 `Config` 在**注册期**绑定（`Register` 的 cfg 参数），把运行参数塞进配置文件等于让配置成为第二个真值来源，而且密钥会跟着进文件；HTTP 客户端与判定器只能由 server 侧注入 —— 前者给进文件就绕过了 dialer 的出网白名单，后者给进文件等于让「谁被授权看原文」不再只有策略包一个业务源 |
| 知识源的委托端点、服务的知识库 ID 列表、预算与响应体积上限 | 检索服务的凭证、transport | C 包要求 transport 由接线方从出网策略注入；凭证进 URL 会被委托协议拒（`ValidateEndpoint` 禁 userinfo） |

判据一条都不在 H 层重抄：每条声明由所属领域包判 —— 处理器走
`config.ProcessorDef.Spec()`（内部调 `processor.Spec.Validate()` + `policy.ParseBodyAccess`
+ `processor.ParsePhase`），知识源走 `knowledge.ValidateEndpoint` / `ValidateKnowledgeBaseID`。
`Spec()` 比 `Spec.Validate()` 更严三处（`body_access` / `fail_closed` / `scope` 必须显式写、
`timeout_ms > 0`）：这些字段决定「正文会不会离开网关」「失败时放行还是拒」，
缺省值在这类字段上不是便利，是把一次漏配变成一次静默的宽松放行。

### 8.2 一条落盘通道，三段配置

`policy` / `processors` / `knowledge_sources` 的写侧共用 `Server.commitSectionConfig`
（`internal/server/policypublish.go`）：临时文件宽松+严格两次试读 → 按引用加载策略包（policy 段的
`sectionGuard`）→ 备份（留 5 份）→ 原子改名 → `chmod 0600` → 带范围的审计 → 等热加载并回报。
`policyAudit` 是这个通道的**必填**参数，不是各调用点自觉加的可选字段 —— 于是
「新增一个写接口却忘了记审计」在编译期就不成立。失败路径整笔还原（含内容文件的 undo），
磁盘与审计都不留痕。

### 8.3 三条不可绕过的接口规则

1. **整段提交**：改一条也要把整个数组发回来。段是整体替换的，做成增量写会让
   「谁最后写」决定线上形态，而 diff 里看不出中间态。
2. **缺字段 ≠ 空段**：请求体必须带本段那个键（`{"processors": […]}` /
   `{"knowledge_sources": […]}`），清空要显式传 `[]`。否则一个漏带键的请求就删掉整段声明。
   带错段的键、多带字段都在读磁盘之前拒掉。
3. **未知键直接拒**：`readJSONBodyStrict` 用 `DisallowUnknownFields`，与配置加载的
   `KnownFields(true)` 同一条规则。`condition` 写成 `conditions`、`expires_at` 写成
   `expire_at`，宽松解码会得到一条「没有条件、没有期限」的声明并把它发布出去。

读侧一律从**文件原文**构建（`config.RawProcessors` / `RawKnowledgeSources`），不是加载后的
`Config`：加载后的形态有些值已被展开或清洗，把那份发给界面会让「界面上看到的」和
「磁盘上写的」分开。空段回 `[]` 而不是 `null`；磁盘那一版读不回来时 GET **仍然 200** 并给
`baseline_error`（列表退回显示服务当前加载着的那一份）—— 连读都被 500 会让人以为服务挂了，
而修好它的正当路径正是整段保存一份合法声明。

### 8.4 界面拿到的是服务端的事实，不是自己抄的表

`config.Vocabulary()` 下发阶段闭集、内置类型（取 `processor.NewRegistry().KnownTypes()`，
部署 `RegisterType` 注入的自定义类型自动跟上）、三档正文访问、范围种类与全部领域上限；
管理台只回显它，并且只做两件检查：JSON 语法、顶层是不是数组。§9「H 只能调用服务端策略接口，
不能在前端重新计算权限」在这里的落法是不在前端重抄任何一条领域规则。

每次读与写都带 `mode` + `applies`：`applies` 为真当且仅当 `policy.mode = enforce`（§3.0 规则 2）。
「保存成功」与「正在生效」是两件事 —— 不把这一层写在最上面，脱敏就会在 legacy 下被当成已经上线。
管理台「处理器与知识库」卡片因此把 `policy.mode → 参与/暂不参与` 放在第一个统计格。

### 8.5 审计的非放大原则

动作是 `processor.config.write` / `knowledge.config.write`，归属固定在 `system:global`
（§2.7 规则 2：全局开关这类动作「关于」系统范围，actor 那一列才记谁按的）。
detail 只写条数、名字与范围（`处理器声明：0 条 → 1 条（pii-request@*)`、
`知识源委托入口：1 条 → 0 条（已清空）`），**不含端点与阈值数值**：基线读不回来时领域错误信息
里可能带着含凭证的 URL，把它抄进审计库等于把别人写错的凭证搬进另一个持久化位置。
被拒的写不落审计（`TestAdminProcessorsBadDeclarationLeavesFileUntouched` 数过条数）。

### 8.6 本轮顺手修掉的两个真实缺陷

1. **空段渲染出重复顶层键**（`internal/config/editproc.go`）：清空处理器时正文里又写了一遍
   `processors: []`，而 `spliceSection` 已经输出了 `processors:` 那行 —— YAML 直接拒，
   于是「在界面上点清空」会把配置文件写成加载不了的状态。现在空列表只留 key 行与说明注释，
   读侧用 `sectionIsNull` 把「key 挂着、值为空」与 `[]` 视为同义。
2. **`configEqual` 漏比两段声明**（`internal/config/store.go`）：只改处理器或知识源声明会被判成
   「配置没变」→ `revision` 不推进 → 重载回调直接 return → 管理台一直报「还在等热加载」。
   这与 §policyEqual 那段注释记的是同一类事故（回滚开关按下去没反应，比没有开关更糟）。
   新增 `processorsEqual` / `knowledgeSourcesEqual`，比的是 **normalize 之后的领域形态**：
   `ProcessorDef.FailClosed` 是 `*bool`，两次 Parse 各分配一个指针，直接 `!=` 会恒不等 ——
   那会让每次保存都白丢一次上游连接池（同 `databaseEqual` 的坑）。
   回归测试：`TestConfigEqualIdenticalDeclarationsReparses`（含「`kb-course ` 与 `kb-course`
   是同一个库 ID」）与 `TestConfigEqualDetectsDeclarationChanges`（换类型/阶段/范围/超时/版本/
   白名单/加知识源，8 个方向都判「变了」且比较对称）。

### 8.7 执行期接线（§3.0 线 2：声明现在真的会跑）

上一节那句「`ProcessorChain` 恒为空」已经过时。三块新代码，边界各自清楚：

| 文件 | 只负责 | 为什么切在这里 |
|---|---|---|
| `internal/server/procruntime.go` | 按声明装配：`Registry.Register` + 运行参数文件 + sidecar 客户端与原文授权判定器的注入 | 声明仍是唯一真值源；客户端与判定器只能由 server 侧给（E 包拒绝自己造连接，那会绕过 dialer 的出网白名单） |
| `internal/server/procexec.go` | 一次请求的处理器调用：请求阶段、响应阶段（缓冲/流式）、审计阶段、失败→HTTP 回话的归类 | 装配失败**不在这里回话**，只记在 `procRuntime` 上；影子模式完全不受影响 |
| `internal/server/forwarder.go` | 插入点：策略判定与配额之后、重试循环之前跑请求阶段；`relay` 里跑响应阶段 | 「before-route」的实际边界是**真正选定供应商的那一刻**，不是计划算出来那一刻 —— `policyJudge` 被无副作用的路由模拟复用，插在计划处会让模拟跑处理器 |

三个决定值得单独记下，因为它们都是「不做也没人报错」的那类：

1. **只有 `policy.mode = enforce` 参与**。影子读正文 = 用合规成本换一个不改变行为的数字，
   §3.0 线 1 明令禁止；legacy 则连装配都不该发生（回滚开关必须真的一刀切）。
2. **装不起来就拒**。命中本范围链的声明若装配失败，请求得到 503
   （`processor_unavailable`），而不是「处理器没跑、正文原样发出去」。这是 §2.9 规则 5
   「敏感策略默认 fail_closed」的接线形态 —— 同一条坏声明在影子下必须零影响，两侧都有测试钉住。
3. **处理器的失败不算供应商的失败**。响应侧拒收把 `rec.ErrorType` 写成 `processor`、
   `outcome` 记成 `relayAmbiguous`，因此一家正常返回 200 的上游不会因为我们的链子起不来而进冷却。

§2.9 规则 7/8 的可观测面：`X-Llmproxy-Body-Pipeline` 声明头按**事实累加**，不互相覆盖 ——
请求正文被整段读过并改写过就写 `buffered`（同时 `Content-Length` 跟着新长度重算），
响应逐段包装就追加 `stream`，两侧都参与时是 `buffered,stream`。之所以不能覆盖：
`buffered` 恰恰是 `max_input_bytes` 与 `timeout_ms` 生效的那一段，只剩一个 `stream`
就等于把唯一有信息量的事实丢掉。`metadata-only` 档位既不缓冲也不改写，因此**不**出现这个头。
审计阶段拿到的是 `procAuditMetadata` 那份结论元数据（request id / 类型 / 模型 / 供应商 /
状态 / 是否流式 / 尝试次数 / 策略版本），不含 `rec.ErrorMsg` —— 错误原文可能带着上游回包片段。

启动期新增 `server.CheckProcessorParams(cfg)`（`cmd/llmproxy/main.go` 里紧跟
`CheckPolicyRuntime`）：声明了处理器却没有运行参数文件、文件不是合法 JSON、或文件里写了
别的类型的键，一律拒绝启动。留到第一个真实请求才暴露的话，表现是「界面说这条声明存在而
运行时没人跑它」，与策略包缺文件是同一类事故。

### 8.8 仍然没做（不伪装）

1. **处理器执行明细不落库**。逐条结果（哪个处理器、什么原因码、改写计数、耗时）只进日志
   （`event=processor_*`），装配失败也只有日志（启动/热加载的 ERROR）与拒绝回话两个面 ——
   管理台还没有「这条声明装不起来」的红灯位。落库要 `store` 三方言各加一张表并过
   `test-matrix.sh`，那是一次独立的存储变更，不该塞进接线这一包顺手做。
2. **执行器只接了非流式那一段**。`internal/executor` 现在确实在请求路径上（§10），
   但**流式交换仍然走 2.x 的传输**：F 的 `Attempt.Validate` 强制 `Timeout` 与
   `MaxResponseBytes` 为正，而现网流式刻意「无总时限」（idle.go：长回答会被总时限
   正常掐断）且「边收边转发、不缓存全文、无字节上限」（§2.9 规则 7）。
   要打通它得先让 F 能表达「以调用方 ctx 为准、不缓存」的通道 —— 那是接口裁决，
   不在接线里偷偷做（详见 §10.3 边界 3）。
   （`internal/knowledge` 已在 §3.C 接线，见 §9。）
3. **跨请求稳定的假名不支持**。`PseudonymKey` 是密钥，按 §8.1 的同一条理由不接受文件注入，
   于是 `pii-mask` 今天只能用每请求随机 salt —— 占位符哈希在不同请求之间对不上。
4. **检索结果不参与模型请求**。§9 打开的是 `POST /v1/_me/knowledge/search` 这一段自助检索；
   `/v1/chat/completions` 的提示词里**不会**自动带上任何引用。把引用注入提示词是另一件事：
   它要求先定「谁授权这次增强、注入多少篇、分级怎么和 `detected_level` 合并」，
   那些口径没定之前自动注入等于静默扩大正文访问面（§2.9 规则 3）。
5. **处理器拒收的响应不记 usage**。上游回包里的 `usage` 在改判错误时**不**进记录 ——
   与既有的 502/超时路径同口径（那次花钱没换来一次成功应答）。要不要照计是计费口径问题，
   留给单独的决策，不在这里静默选边。

### 9.3 这五个决定各自挡住了一条静默失败

1. **模式口径与处理器不同**：检索在 `shadow` 与 `enforce` 下都可用，`legacy` 一律 501。
   处理器只在 enforce 参与是因为读正文有合规成本；检索不改变任何 2.x 行为，而准入判定
   在两种模式下都由同一个内核给出。**legacy 是 501 而不是 200 空结果**，因为「没有策略
   所以全都给」正是 §3.C 明令禁止的失败模式。静态 key 一律 403：C 包要求范围集合含
   `user:<subject>`（`context.go` 的 `validateFields`），共享钥匙没有主体，退化成
   「按 `system` 范围检索」等于把网关主人的授权借给每一个拿钥匙的人。
2. **候选集的唯一来源是配置声明**，客户端递来的库名只能收窄。声明段里没有的库单列成
   `undeclared_knowledge_bases` 而不是混进策略拒绝码 —— 原因码注册表只能记真实判定，
   「这个库压根没有委托入口」是接线事实，把它写成 `policy_denied` 会让权限大盘统计失真。
3. **委托客户端只从出网策略构造**：`s.Transports().Get("")` 拿不到就让这个源装配失败，
   请求期指名报错（`retrieval_transport_not_configured`），绝不回落 `http.DefaultTransport`。
   与 sidecar 同一条理由：默认 transport 不受出网白名单管，而审计看不出差别。
4. **502 与「200 零命中」的分界是计数而不是结果**：`allFailed()` 比的是
   `len(Failures) == Queried`（被问到的源数，含装配失败的那些）。用「citations 为空」
   判空的话，「三个源全超时」会被写成「知识库里没有答案」—— 那是把故障伪装成结论。
5. **审计先落库再交付**：`Resolve` 一返回就投递事件，落不进去直接返回 500 且不带任何引用。
   **凡被问到的源都恰好留下一条审计**，包括失败发生在网关这一侧的四条路径（transport 装不起来、
   剩余预算用尽、知识范围不合法、`Resolve` 前置校验失败）—— 它们不产出 `Outcome`，
   由 `minKBAudit` 补一条最小留痕，只填能确定属实的字段。假造的分级与耗时会让「装配从来没通过」
   被统计成「一次真实的零命中检索」。零准入的检索同样留痕（`delegation: "not_sent"`），
   否则「有人试过且被全量拒绝」在审计上等于「没人查过」。

预算与合并的口径：总预算 = 被问到的源的 `timeout_ms` 之和、以 `knowledge.MaxBudget` 为顶，
每个源再按「此刻还剩多少」用 `WithDeadline` 收窄（只允许收窄不允许放宽，否则一个慢源会替
整条链路续期）。请求按配置声明顺序发出，合并后 `SortCitations` 再全局截断到 `max_results` ——
**截断只改回话，各源审计里的 `hit_count` 保持源侧事实**。

内容面：委托请求只带检索词的域分隔摘要（`llmproxy-kb-query-v1`），本版没有「原文检索词」
这个授权位，所以请求体不接受 `allow_raw_terms`，未知键在严格解码那一关就被 400 指认；
回话与审计只有 `source_id` + 内容摘要 + 标题摘要，标题与正文一个字节都不出现。
委托端点地址既不进用户面回话也不进审计，`AuditEvent.Retriever` 与审计 target 用源名。

### 10.3 三条边界，各自挡住一条静默失败

1. **计量语义一个字不改**（playbook §3.F 的禁止项）。`Outcome` 只被拼成 `relay`
   能直接消费的 `*http.Response`：状态码、过滤掉逐跳头之后的响应头、体积声明、
   **未经改写的字节流**。usage 扫描、TTFT、计价冻结、熔断计数、会话粘性全部仍在
   `relay` 与调用方那一段里。`Attempt.MaxResponseBytes` 直接取 `maxUpstreamResponseBytes`
   那个常量 —— 两条上限不同值时，「谁先拦住超大响应」变成运气，报出来的归因跟着变。
   证据：`TestExecutor30MeteringMatchesLegacyPath` 把同一条请求在两条链路下的请求行字段
   逐个比（`meterView` 一次 `==`）并比 `usage_daily` 里的**冻结成本**，同时断言这个数
   确实非零 —— 一致但都是 0 的比较等于没比。`meterView` 里刻意没有 TTFT：那是两次
   独立请求各自的墙钟读数，不是账 —— 把它塞进等价比较，就等于拿一个必然会抖的毫秒差
   去断言「计量语义没变」，`-race` 下必然偶发红。测试改成断言两侧都**记录了** TTFT
   （可以为 0，不能为 nil），字段存在性归测试，数值等价归台账。
2. **只有 `policy.mode=enforce` 且本次判定真的生效（`shot.Applied`）才委托**。
   legacy/shadow 下 2.x 传输原样跑（§3.0 线 2）。影子一旦能换传输层，差异报告里就掺进了
   被观测者自己的改动，两条链路的对比不再是「同一件事的两种判法」。
   证据：`TestExecutor30DoesNotDelegateOutsideEnforce`（含「上游只收到一次请求」）与
   判定分支表里的「计划没生效」「shadow 模式」两格。
3. **流式不委托**。`Attempt.Validate` 要求 `Timeout` 与 `MaxResponseBytes` 为正，
   而现网流式刻意两者都没有：无总时限（长回答会被总时限正常掐断，见 idle.go）、
   边收边转发不缓存全文（§2.9 规则 7）。把这两样补进流式是一次功能回退；
   要打通得先让 F 能表达「以调用方 ctx 为准、不缓存」的通道 —— 那是接口裁决，
   不在接线里偷偷做。证据：`TestExecutor30StreamingStaysOnLegacyTransport` 同时断言
   「没有委托头」「响应仍是 `text/event-stream` 且 `[DONE]` 完整」「usage 照常扫到 33」。

### 10.4 判定与装配上的几个决定

- **计划声明的执行器注册不上 ⇒ 拒掉这个候选**，不出网也不回落到 2.x 通道。
  回落等于把「计划说用哪个执行器」降级成一句注释，而那正是 §8 点名的
  「绕过出网控制的快捷路径」。拒候选时连 transport 都不装配 —— 测试直接断言
  缓存里零通道、上游零请求。
- **计划与真实目标漂移 ⇒ 不委托并留 WARN**（`event=executor_plan_drift`）。
  拿计划里的上游模型名去覆盖这一跳真正要发的目标，等于让审计描述一次没发生的交换。
- **transport 只从 `s.transportFor` 拿，且拿到 nil 就报错**。回落到
  `http.DefaultTransport` 是一条不受出网策略约束的暗通道；自有上游走带拨号层
  IP 校验的 `GetChecked`，系统池走 `Get`，两套不共用条目。
  因此 `Attempt.EgressCheck` 刻意留空 —— 出网判定已经在 dialer 里绑进 transport，
  再填一份就是两个校验点，两个校验点必然漂移。
- **实例按 (执行器名, 归属, 代理) 分通道缓存，上限 64 条**。`HTTPExecutor` 把 transport
  绑在实例上，所以一个名字在生产里对应多个实例。这与 `executor.Registry`
  「名字→单实例」的假设冲突，已登记为待裁决项（`docs/3.0-stage-summary.md` §4），
  而不是靠改 F 的冻结代码「顺手修好」。越界后不再缓存、每请求现构造：宁可少复用连接池
  （底层 transport 仍由 `dialer.TransportCache` 复用），也不留一个无界结构。
- **装配失败按通道缓存**。代理 URL 写坏是配置事实，每请求重撞只会把日志刷满，
  而报错点仍然是「命中这条通道的那次请求」，且错误文本指名环节而不带密钥。
- **一次正常超时不认成「客户端走了」**。委托时执行器把同一个 deadline 又包了一层，
  到点时先动的是哪个 ctx 没有保证，于是「我们的时限到了」在执行器侧可能报成
  `executor_caller_canceled`。归因次序保证了走到映射这一步时真实客户端上下文还活着，
  所以 `ReasonTimeout` 与 `ReasonCallerCanceled` 都折算成那句「供应商 X 请求超时」。
  反过来若把它当客户端断开，一次正常超时会变成不给这家记失败的 499，熔断口径跟着抖。
  证据：`TestExecutor30TimeoutAttributionMatchesLegacy`（两条链路的超时文案同形、
  记录里不含正文）。
- **观测面**：新增响应头 `X-Llmproxy-Executor`，值为承载这次交换的执行器名。
  与 `X-Llmproxy-Affinity`/`X-Llmproxy-Body-Pipeline` 同一类用途 —— 上线验证要一眼看出
  「委托生效了」，而不是翻日志；头里只有名字，不含正文与密钥。

### 11.3 六条边界，各自挡住一条静默失败

1. **只采 enforce、且判定出了版本**。`shot.Version == ""` 意味着这个范围没被任何策略包
   覆盖、请求按旧路由走，记一条空版本的选路证据既过不了 §2.8 的自校验，又会把
   「这个范围退出了 3.0」误报成「3.0 判了它」。影子与 legacy 一律零采集
   （`TestReplay30ShadowAndLegacyCaptureNothing`，空窗口的导出还要能过 `File.Validate`）。
2. **拒绝也是证据，但只到判定这一层**。真实 403 留 `DecisionRecord`，**不留** `RoutingRecord`
   —— 请求根本没进选路（`TestReplay30DeniedRequestLeavesDenyEvidenceOnly`）。半个痕迹
   比没痕迹更坏：一条带着计划的拒绝记录会让回放去比对一次没有发生的抽样。
3. **抽样算法如实声明，不冒充逐位复现**。线上算法声明为 `routing-seeded-splitmix64-v1`
   （`replaySamplingAlgoOnline`），回放缺省抽样器是 `replay-sampling-v1`，两者不同名 ⇒
   `ReplayRouting` 走**解释性回放**：仍复核候选摘要、排除原因与授权，但不比对首选顺序，
   并把这句写进报告备注。状态口同时回 `sampling_algo_declared`、
   `sampling_algo_replay_default` 和 `bit_exact_primary_order: false`。把两个标识合并成一个
   就能让回放「看起来」比对了顺序 —— 所以这条由 `TestReplay30ExportReplaysClosedLoop`
   与 `TestReplay30AdminSurfaceAuthArgsAndAudit` 同时看着。
4. **候选按有效权重写**。`routing.Offer.Candidate.Weight` 是配置原值（未配置 = 0），
   计划里的权重是 `candidateForPlan()` 折算后的有效权重。直接抄原值的话，记录顶层的
   `candidates_digest` 与 `requests.candidates_digest` 那一列、与计划内候选三者对不上，
   「导出的记录能和线上落库痕迹对上」这条最基本的证据就断了。
   测试是拿记录与 `traceOf(...)` 的 seed/epoch/version/digest **四列逐字段相等**来钉的。
5. **暴露面按用途分级**（§2.9 规则 6）。状态口只有计数与配置，不含任何 subject；
   导出面就是记录文件本身，没有额外字段可泄漏；审计 detail 只写条数与计数；
   采集失败的 WARN 只带 request_id；CLI 落盘权限 0600。
   「窗口里谁被采到了」只在导出那一份里出现，两个面的暴露程度不同，所以断言也不同：
    populated 窗口的状态响应里出现 `mallory` 或记录级 `subject` 键就判失败。
6. **采集失败绝不影响请求，但必须数得出来**。`DecisionRecordFrom`/`RoutingRecordFrom`
   出错只 WARN 并 `failed++`，状态口与导出说明都把这一位摊开。静默失败的窗口会让运维
   看到「比线上少几条」而没人说为什么（`TestReplay30StatusReportsAsOfAndCounters` 用一次
   真实失败路径——空 subject——把这一位跑出来）。

窗口的有界性与清零语义另有两条断言：容量缩小会挤掉记录并计入 `dropped`
（`TestReplay30WindowEvictsOldestAndCountsDrops`），`clear` 只清记录与计数、不动开关与
过滤条件 —— 拿走这批证据不该顺手关掉观测面。抽样按 `request_id` 的 FNV-1a 散列决定，
同一 id 重复判定结果不变（`TestReplay30SamplingIsDeterministicPerRequestID`）。

### 11.4 CLI 的 fail-closed 判据

`llmproxy replay run` 在这一包里的角色是「门禁能自动跑的那条命令」，所以它的失败方向
比功能更重要，逐条有测试（`cmd/llmproxy/replay_test.go`）：

| 输入 | 结果 |
|---|---|
| 缺 `-records` / 缺 `-now` / `-now` 不是 RFC3339 | 报错，**不**用 `time.Now()` 兜底（策略与身份的过期语义只有钉住时钟才能复现） |
| 记录文件读不到 / 不是记录文件（含 `"body"` 这类被禁键） | 报错，不当成「空记录」放过 |
| 记录合法但为空 | 报错「没有任何可回放的条目」—— 空报告永远不算通过 |
| 配置是 legacy 或没引用任何策略包 | 报错「没有可回放的策略包」，而不是「跑了一遍、0 条差异」 |
| `server.admin_token` 缺失或还是 `${ENV}` 形态 | 报错并给出处置方向，不拿半成品凭证去发请求 |
| 回放结果有任何 mismatch / rejected | 非 0 退出，报告与报告摘要照打 |

### 11.5 §2.8 仍然没做（不伪装）

1. **记录不落库**。窗口只在进程内存里，重启即空、溢出丢最旧。为什么不落一张表：
   §2.7 的存储变更要三方言各写一遍迁移并过 `test-matrix.sh`，而记录里的 subject 是用户名 ——
   长期留存一份「谁在什么时候被授权用了哪个模型」的表是一个独立的合规决定（§2.9 要求
   这类数据只在需要时存在）。今天的口径是「要证据时打开 → 跑一批流量 → collect 取走 →
   off 或 clear」，运维流程写在 `replayUsage` 里。**这是一条已知限制，不是完成项。**
2. **首选顺序不逐位复现，且这一条需要接口裁决**。要逐位复现得用 D 包的
   `routing.PlanFromReplay/Replay(ReplayInput)`，而 `replay.File` 的冻结 schema（v1）
   只能携带 seed、候选池与计划，携带不了 `ReplayInput` 那组输入结构。可选出路两条，
   都属于主线裁决而不是接线侧可以自便的：给 `replay.File` 升 schema 携带重放输入，
   或把 D 的抽样器注入 `replay.Options.Sampler`（§4.5 的注入点就是为此留的）。
3. **拒绝证据与原文出网授权天然冲突**（已钉成测试，待裁决）。
   `DecisionRecord.Validate` 钉死「拒绝 ⇒ 不可能授予原文出网」，所以采集侧对一次 deny
   只能写 `external_plaintext_allowed=false`；而 `ReplayDecision` 无条件重跑
   `AllowsRawBody`，它判的是 `body.raw/read` 这个**另一个资源**，与本次结论无关。
   于是在「带原文授权的范围里发生的一次真实拒绝」上，同版本回放必然报**且只报**这一位差异 ——
   那是 schema 的产物，既不是策略变了也不是记录坏了。
   `TestReplay30DenyEvidenceAndRawBodyGrantConflict` 锁住今天这个形态；改任何一侧都要动
   冻结接口（放宽 A 的不变量等于松 §2.9 的隐私闸门，跳过比对要动回放核），
   所以留给主线，不在接线里偷偷选边。
4. **管理台没有回放面板**。四个端点只有 API 与 CLI 两个面。§9「界面不重算权限与费用」
   在这里的落法是：面板要做的是「开个窗、下个文件」，而导出那份文件是聚合了 subject 的
   敏感记录，CLI 那条路径已经有 0600 与 fail-closed 校验；把它做成一个按钮不会减少任何
   摩擦，只多一个泄漏面。等 §11.5 第 1 条的留存口径定了再谈面板。
5. **窗口过滤只认 `user:<名>`**。窗口按 2.x 的路由作用域名（用户名）记账，
   组织/项目范围今天进不了这个键，所以 `?scope=organization:university` 直接 400 指认，
   而不是静默导出一份空文件。等 D 的按范围路由落库后这一条才有放宽的余地。

### 11.6 本包顺手修掉的既有测试缺陷（不属于 §2.8，但要留痕）

`TestExecutor30MeteringMatchesLegacyPath`（§3.F / §10.5）的 `meterView` 注释写着
「不含时延」，字段里却带着 `ttft`。这条断言拿两次独立请求各自的墙钟读数做等价比较，
`-race` 下 1ms 抖动就报「计量语义变了」—— 一个必然会红、红了又难复现的门禁项。
本包跑门禁时撞上，改法是拆成两件各自断得动的事：等价比较只留「账」上的字段，
TTFT 改为断言两侧都非 nil 且 ≥ 0（记了就好，数值不进比较）。

为什么不在 §3.F 那一包里修：当时 `-race` 单次通过就提交了，而抖动需要重复跑与
高负载才现形。这类「注释与字段不一致」的断言是伪装完成的另一种形态 —— 它看起来
在比更多，实际把一条不稳定的读数焊进了等价判据。

### 12.3 抓到的真缺口：分级声明不在 providers 的管理编辑层，3.0 从接口上开不起来

第一版第 23 节跑出 11 红，其中一条不是脚本写错：`POST /v1/_admin/policy/mode
{"mode":"shadow","data_level":"public"}` 回 400
「`policy.mode=shadow` 时已启用的供应商必须逐家声明 `max_data_level`……未声明不能按最宽松处理」。
按提示去 `PUT /v1/_admin/config/providers` 补声明，接口回 `written:true`，
**文件里却一行 `max_data_level` 都没多** —— 于是那条「必须逐家声明」的规则在管理接口上
是个死循环：它要求一个接口本身给不了的字段。后果按严重度排：

- 想启用 3.0 只能手改 `config.yaml`。§3.0 的启用路径与 §3.H 声明面「配置段 + 管理 API + 管理台」
  这条承诺，在 providers 这一段上少了一个字段就整段不成立。
- 界面读不到当前声明，也就无从核对：运营看到的「这家上游能承接哪一等数据」只能是猜。

漏在三处，且三处**必须一起补**（补一处都只是把字段搬到另一个方向上丢）：

| 位置 | 原来 | 现在 |
|---|---|---|
| `internal/server/configedit.go` 请求结构 | 无 `max_data_level` | 有；非空先过 `policy.ParseDataLevel` 词表，拼错直接 400 并点名是哪个供应商的哪个字段 |
| 同文件 `configProviderView`（下发视图） | 无 | 回显磁盘原文里那一版（空串 = 没写），与 `api_key` 一样「留空 = 沿用原值」 |
| `internal/config/edit.go` `renderProviders` | 字段清单里没有 | 写在 `timeout_ms` 之后、`models` 之前，函数头那句字段顺序注释同步改掉 |

另外三个决定值得留痕：

- **留空沿用而不是清空**：与 `api_key` 同一条规矩，理由同样硬 —— 界面拿到的是当前值，
  一次只改权重的保存不该顺手抹掉一条**收紧**声明。
- **反向（已声明 → 未声明）在 API 上做不到**，且不是遗漏：留空的语义已经被「沿用」占住，
  不能同时表示「清空」；放松一条分级声明只能由直接编辑文件的人做，那是一次可归责的手工动作。
  这条方向性差别写进了 OpenAPI 与代码注释，免得后来人当 bug「修平」。
- **拼错的值必须在接口层就拒**：加载期对 `max_data_level` 是硬失败（拼错不会降级成「当作没配」），
  所以让它落进文件等于把「这份配置起不来」延后到下一次热加载 —— 那时候已经没有人知道是谁改的。

控制台侧同步补了编辑位：`ui/admin.js` 读 `max_data_level`、在供应商行里给一个四值下拉
（第一项是「留空 = 不改」，与服务端语义一致），保存时随 `cfgPayload()` 一起发；
`ui/app.css` 的 `.prow-grid` 从 5 轨加到 6 轨。OpenAPI 在
`GET /v1/_admin/config` 与 `PUT /v1/_admin/config/providers` 两处把口径写全。

测试位置：`internal/server/configedit_test.go` 的 `TestAdminConfigProviderDataLevelRoundTrip`
（写得进 / 留空沿用 / 拼错拒且文件字节不变）与 `TestAdminConfigDataLevelUnblocksShadowMode`
（先只落段与包，让「切不动」只剩分级这一件事；接口补声明后再切才应通过，
并核 providers 段的保存不吃掉 `policy` 段）。

### 12.4 两处口径失真：一处写在文档里，一处写在测试里

- **`X-Llmproxy-Policy-*` 从来没存在过**。§3.0 判定痕迹的真实落法是
  `requests` 表那四列（`policy_version/routing_epoch/routing_seed/candidates_digest`）
  加上 `GET /v1/_admin/policy/trace?request_id=` 的读回面；响应头那三个
  （`X-Llmproxy-Executor` / `-Affinity` / `-Body-Pipeline`）说的是**执行与管道的事实**，
  不是授权结论。把结论挂到响应头上等于把它交给下游缓存、日志采集与客户端任意转发去处置，
  而 §2.9 要求这类痕迹只在网关一侧可读。
- **e2e 第 9 节在断一张已经不写的表**：`SELECT … FROM usage_user_daily WHERE user_name='dave'
  AND system_paid=1`。§2.7 规则 8 之后写侧只剩 `usage_daily` + `usage_scope_daily`
  （`internal/store/store.go` 里那句「这里不再写 `usage_user_daily`」），
  运行时读用量也一律走按范围那张表 —— 于是这条断言永远红，而红的含义是「脚本没跟上迁移」，
  不是「计量坏了」。改法是按 3.0 的口径断两件事：`(user,dave)` 那一行确实标了 `system_paid`，
  **并且**老表没有新行（双写没退干净就该由这一条抓到）。

### 12.5 `exactly_replayable` 必须两面都断，只断一面会把口径带偏

痕迹里这个字段是 `tr.RoutingSeed != ""`。第一版脚本拿**被策略拒掉**那条请求去断「可逐字段回放」，
于是红了 —— 而红的是脚本：一条 403 根本没进选路，没有计划也就没有 seed，
给它写 seed 等于引导别人去逐位复现一次**没发生**的决策（§11.3 第 2 条同源）。
现在两条都留在场上：拒绝那条断 `policy_version` 读得回（失败路径也要有证据）、
断 `exactly_replayable=False` 且带「只能解释性回放」那句 `note`；
放行那条才断 `True`，并顺手核归属落成 `user:alice`。

### 12.6 两个 `system` 范围 id：今天不打架只靠一条不变量

判定链用 `system:gateway`（`policySystemScope`，静态 key 那一格），而策略写侧的审计归属与
store 侧默认范围用 `system:global`（`policy.SystemScope`）。它们能同时成立，
唯一原因是 `PolicyBundle.Covers` 对**任意** `Kind==system` 的包按 Kind 放行、不看 ID。
这条如果被改窄成按 id 精确匹配，失败方向是「策略静默不生效」—— 审计照常写着发布成功，
判定却退回旧链路，是整条链上最难查的分叉。`internal/server/policy30_test.go`
的 `TestSystemBundleCoversGatewayChainRegardlessOfID` 把两面都钉住：
`system:global` 的包必须覆盖 `system:gateway` 的链，而 `project:*` 的包**不许**
顺手覆盖（放宽只留给 `Kind==system` 那一格）。这个用例还先断两个 id 的字面量没被改，
否则前置条件变了会让「覆盖成立」变成一次巧合。

### 12.7 §3.I 仍然没做（不伪装）

1. 流式那一段的执行器承载仍未接线（§4 第 3 条），e2e 的假上游也不支持流式，
   所以第 23 节对此一个字都不声称。
2. 判定记录仍不落库、不跨进程留存（§11.5 第 1 条）。这一节把「导出 → 另一进程重跑」
   在同机闭合了，但没改变「重启即空」这个事实。
3. 管理台没有回放面板（§11.5 第 4 条原样成立）；这一节只核了面板**读**到的字段口径。
4. 首选项的逐位复现仍未闭合（§11.5 第 2 条）：`bit_exact_primary_order` 依旧是 `false`，
   第 23 节断的是「报告里差异 0」，不是「顺序逐位一致」。
5. 真实多机现场（拷走 `policy-bundles/` 与记录文件、在另一台机器/另一天重跑）仍未做过。

## 13. §3.I 指标埋点：执行器与检索委托两个面真的长出维度

§12 那一包核的是「3.0 在真进程上跑不跑得通」，它同时在 §12.7 与 §4 第 5、11 条留了
一句：观测面**只有字段没有维度** —— 委托成没成只能翻日志或看那一发的响应头，
检索失败率只能靠逐条审计数。这一包补的就是那两个维度，不新增能力面。

### 13.1 三层完成口径，逐层给证据

| 层 | 状态 | 可复现的证据 |
|---|---|---|
| 指标面完成 | 已完成 | `internal/server/metrics.go` 的 `observeExecutorExchange` / `noteExecutorRejection` / `noteExecutorSkip` / `noteKnowledgeQuery` / `noteKnowledgeFailure` / `observeKnowledgeResult`，加 `/healthz` 的 `metrics.executor`、`metrics.knowledge` 两段与 `/metrics` 的 8 个 `llmproxy_executor_*` / `llmproxy_knowledge_*` 序列名 |
| 运行期接线完成 | 已完成 | 埋点位置只有三处真实调用点：`forwarder.go` 委托分支交换之后、`executor30.go` 的三个拒/跳分支、`knowledge30.go` 的 `kbSearch` 逐源循环。断言在 `TestExecutor30MetricsRecordDelegationOutcomes`、`TestKnowledge30MetricsCountQueriesAndFailures` —— 都从真请求路径读回快照，不是直接喂计数器。另有两条落在**真进程**上（`scripts/e2e-multiuser.sh` 第 23 节）：enforce 下委托发生过 → 同一个数同时出现在 `/metrics` 与 `/healthz`；切回 legacy 后新请求不再让那个计数器长 |
| 明细落库 | **未完成** | 计数只在进程内存里，重启即空（§4 第 12 条同一条理由：一张表要 `store` 三方言各一遍迁移）。这一包刻意不碰存储：playbook §3.I 要求的是「指标维度稳定」，落库是另一件事的裁决 |

### 13.2 补出来的维度

| 面 | 序列 | 标签 | 这一维回答的问题 |
|---|---|---|---|
| 执行器 | `llmproxy_executor_exchanges_total` | `executor`（注册表内的名字） | 计划声明的承载者**真的**换过人吗 |
| 执行器 | `llmproxy_executor_failures_total` | `executor` + `reason` | 换过人之后失败成什么形态 |
| 执行器 | `llmproxy_executor_rejected_total` | `stage`（接线侧常量） | 有多少候选一次都没出网就被拒 |
| 执行器 | `llmproxy_executor_skipped_total` | `reason`（仅 `plan_upstream_mismatch`） | 有没有「本该走执行器却静默回到 2.x」 |
| 检索 | `llmproxy_knowledge_searches_total` | `source`（配置声明的源名） | 分母：这个源被问到过几次 |
| 检索 | `llmproxy_knowledge_failures_total` / `..._failure_reasons_total` | `source`+`reason` / `reason` | 按源与跨源两个粒度看失败原因码 |
| 检索 | `..._duration_ms_total` / `..._measured_total` / `..._citations_total` / `..._truncated_total` | 无 | 慢不慢、样本够不够、有没有被截断 |

### 13.3 四条口径决定

1. **标签取值空间必须封闭**。`executor` 只可能是注册表里的名字，`reason` 只可能是
   `internal/executor` 或 `internal/knowledge` 的注册码，`stage` 是接线侧常量。唯一来自
   配置的是知识源名（基数由运维声明几个源决定，与 provider 名同级）。
2. **计划里那个注册不上的执行器名不进标签**（`TestExecutor30MetricsRecordDelegationOutcomes`
   第 3 步专门断标签里没有 `ollama-native`）。它本身就是被拒原因，让被观测的东西决定
   观测的基数，一个错配的策略包就能把 `/metrics` 的序列数打爆 —— 而这两个端点都不鉴权。
3. **未注册的值不冒充注册值**。`ReasonCode.String()` 对表外的码会拼出
   `executor_unregistered(<原样>)`，那串文本不受控，所以执行器侧统一折到
   `wiring_unclassified`（`TestExecutorExchangeReasonStaysInClosedSets` 把注册码、未注册码、
   空码、非 `ExecutionError` 四类各断一次，并断凡注册码都 `Valid()`）；知识侧未注册码
   直接不建序列（`TestKnowledgeFailureMetricIgnoresUnregisteredReason`），口径与审计写入侧
   的 `Validate()` 一致。
4. **上游 4xx/5xx 算进执行器失败维度是有意的**，取值用 `executor` 包里**已导出的**那两个
   常量而不是字符串字面量（包内那个 `reasonForStatus` 非导出，这里按同一阈值分派）。
   看板要区分「执行器自己故障」与「对方明确说不行」靠的是 `reason` 标签，不是靠这里少记一笔。
   同一条不变量在测试里是可数的：**每条委托交换要么没有失败码，要么有且仅有一个**
   （503 那一发断 `failures == exchanges`）。

### 13.4 分子分母与坏样本

- 检索侧 `queries_by_source` 在**被问到**那一刻就记，包含委托根本没发出去的路径；
  失败按原因码另记。只记失败会得到「1 次失败 = 100% 挂」，而实际可能是 1/50。
- 耗时/命中/截断只在源侧真跑过的那条上记（`observeKnowledgeResult`）。网关侧失败连耗时
  都不能假造 —— 口径同 §12 里那条 `minKBAudit`：编出来的数字会被算成一次真实的零命中检索。
- 负耗时直接丢弃而不是夹到 0：那是「这条事件本身不对」，不是一个很快的检索。
- legacy / shadow 下执行器两段恒为空表，但**字段一定在场**（`TestRuntimeMetricsExecutorAndKnowledgeDimensions`
  末段专断空快照也带 `executor`/`knowledge` 两段）。抓取端靠「字段在不在」判断版本会抖，
  靠「值为 0」判断没委托才稳。
- **计数器是累计的，不是状态的**：第 23 节里那条「切回 legacy 后委托计数不涨」的第一版拿
  切换**之前**的快照当基线，于是把切换前那几发合法委托也算成了违规增长（2 → 4，其中两跳是
  enforce 期间正常发生的）。基线改为回滚之后现取，断言才只回答它想回答的那件事 ——
  legacy 下的**新**请求不产生委托。这条实测同时确认了一个此前只在推演里的事实：
  legacy 没有计划，也就没有「计划声明的执行器」，所以委托面在紧急开关按下后必然静止。

### 13.5 仍然没做（不伪装）

1. **执行明细不落库**：逐次交换的承载者、耗时、上游状态只进日志与内存计数（§4 第 5 条的
   存储那一半原样成立）。
2. **没有分位/直方图**：检索侧只有累计毫秒 + 样本数（可算均值），没有 p95；执行器侧连累计
   耗时都没记 —— 现网已有 `llmproxy_latency_ms` 的请求级分位，按执行器再拆一套需要先定
   「委托与否要不要共用同一个环形样本」。
3. **处理器链没有自己的维度**：`X-Llmproxy-Body-Pipeline` 是逐请求事实头，
   `/metrics` 上没有按处理器名的运行/失败计数（§4 第 7 条同一段）。
4. **影子模式不进这些计数器**：`policy.mode=shadow` 下不委托，所以委托面恒空，一致率仍在
   `metrics.policy_shadow` 那一格里 —— 两边不许互相冒充（§12.1 口径）。

这一包补管理台那一个面，**不新增接口、不改字段语义、不落库**。

### 14.2 浏览器实测抓到并修掉的两个真缺陷

静态检查看不见这两条，只有真点一次才现形：

1. **非法值被静默丢掉**：千分率填 `abc` 点保存，界面既不报错也不改配置，人以为改过了。
   修法是 `rpInt` 只判「是不是整数」这一件**格式**事，非整数直接说破「本次没有提交」；
   取值域（0~1000、1~上限）仍然只由服务端判 —— 界面复算业务规则就会和注册表版本赛跑。
2. **四个字段各占一行**：`type="number"` 撞上 `app.css:62` 的
   `input[type=text|number] { width: 100% }`，控件被挤成四行。本页既有行的写法是**不带
   `type`**（默认 text 不匹配那条属性选择器）+ `class="mono"`，改完实测四个控件与按钮回到
   同一行（x 138 / 218 / 384 / 551 / 717，同一 y）。

另外一条是自纠：被服务端 400 拒掉之后，输入框里还留着那串确定无效的值（2000），而横幅报的是
服务端口径（500）—— 两个数字互相矛盾，等于让界面同时说两件真事。现在 400 之后强制回显
服务端值；连不上网关则保留人已打的内容（值是对的，只是没送出去）。

### 14.3 为什么导出必须是原始字节

`replay.File` 那份文件的全部价值在于**另一个进程能拿它逐字段重跑判定**。客户端如果
「解析成对象再拼回去」，字段顺序、数字格式、空值写法都可能变，而变化的那一份看起来仍然
是合法 JSON —— 于是差异会以「回放复现不了」的形态在很晚之后才暴露，且没人会怀疑到导出这一步。
所以 `rpExport` 走 `res.text()` → `new Blob([text])` → `<a download>`，一次序列化都不做。
§14.1 第二行那条 sha256 相同就是这条决定的验收，不是顺手做的对比。

顺带把这条路的边界钉住：CSP 是 `default-src 'self'`，同源 `blob:` 在 `'self'` 范围内，
所以浏览器实测能拿到文件（Safari 上 `object-src` 的历史行为不同，本轮未在 Safari 复测）。

### 14.4 界面没有碰的东西

- **不复算判定**：面板上没有任何「这条会不会被拒」的推断；模式与结论都来自
  `/v1/_admin/policy` 与 `/v1/_admin/replay` 的字段。
- **不碰计量与审计**：写侧仍是 `replay.sampling.set` / `replay.export` / `replay.clear`
  三条既有审计动作，归属 `system:global`，detail 只有计数没有正文。
- **不暴露 subject**：状态端点本来就不含用户名（§2.9 规则 6），面板因此也拿不到
  「谁被采到了」—— 那只在导出的文件里，取件这个动作本身留审计痕。
- **导出过滤仍只认 `user:<名>`**：这是 §4 第 15 条剩下的那一半，界面照实把服务端的 400
  原样报出来，不做「前端先挡一层」的粉饰。

## 15. §3.I 发布与回滚演练：练的那个文件就是发出去的那个文件

§3.I 的清单最后一条是「发布和回滚演练」。在这一包之前，它只在 `go build` 出来的本地产物
上验过。本地产物与发行件的差别不是形式：发行件带 `-trimpath`、`-ldflags` 注入的版本号、
`CGO_ENABLED=0`，而管理台是 `go:embed` 编进二进制的 —— 于是「练的」和「发的」根本不是同一个
文件。这一包把演练搬到发行件上，并顺手把 e2e 的入口打开：`LLMPROXY_BIN` 指哪儿就用哪儿的
二进制当网关（假上游仍从源码编译，它是被测对象之外的夹具）。

| 步骤 | 命令 | 结果 |

### 15.3 演练里必须主动试的两条失败

只跑成功路径的演练等于没演练，这两条是刻意做出来的对照：

- 全新 home 里只放记录与策略包、配置里没有 providers →
  `错误: providers 需要至少包含一个供应商`。回放走的是**完整配置校验**，不提供「只读记录文件」
  的捷径（§8 DoD 6：不能有绕过校验的快捷路径）。这不是缺陷，是 fail-closed 在 CLI 上的表现，
  也意味着换机器时配置要一起带。
- 把 `policy-bundles/e2e-base.yaml` 挪走再跑 → 明确拒绝并点名缺哪个文件
  （「`policy.bundles` 里的每个引用都要有对应文件；文件名必须是 `<id>.yaml`」），
  **而不是报「0 条差异」**。「看起来跑过了」与「真的跑过了」的差别就在这句拒因里。

### 15.4 演练当场抓到的一处自身缺陷

第一次带 `LLMPROXY_BIN` 的运行在 `scripts/e2e-multiuser.sh:49` 就中止：
`line 49: BIN\xef\xbc\x88: unbound variable`。写回显时 `$BIN` 紧跟一个全角括号，`set -u` 下
那三个字节被当成了变量名的一部分。改成 `${BIN}` 后同一行才是它本来的作用。全脚本扫过一遍，
没有第二处这种写法。这类缺陷只有「换一种调用方式」才会露头 —— 它正好说明演练该被跑。

## 16. §3.F 执行记录与生产接线测试：一次委托的六项事实落在同一行

§10 交付的是「委托进了请求路径」，那一节的证据到此为止能回答三件事：承载者是谁（响应头）、
委托发生过没有（指标累计数）、当时判用的是哪版策略（请求记录的 `policy_version`）。排障的
下一句 ——「这一发用了什么时限、多大响应上限、失败类型是什么」—— 三样都答不了，因为
`Attempt` 上的那几位在委托完成后就被丢掉了。另一半缺口是口径：§10.5 那张表里的用例打交道的
是 `executorCallFor` 与桩执行器，属于「接线组件正确」，还没有一条用例从**配置声明**一路走到
**真出网**再回到**记录**。本包补这两件，行为没有扩大。

### 16.1 执行记录落在哪个面，以及只有那一个面的原因

委托分支现在写一行结构化记录（`internal/server/forwarder.go`）。行首时间戳与级别由
`internal/logx` 加（下面这行的时间部分是示意），`event=` 起的字段序列就是格式串的实际输出，
取值与 §16.2 第一条用例断言的那一行一致：

```
2026-10-04 09:12:03.481 [INFO] event=executor_exchange request_id=req-wire-rec executor=http-openai provider=vendorA model=gpt-4o upstream_model=gpt-4o protocol=openai_chat timeout_ms=3000 max_response_bytes=33554432 status=200 reason=-
```

三处口径决定：

- **字段逐个点名取，不是把 `Attempt` 整体打出来**。`Attempt` 里带着 `APIKey` 与 `Body`，
  日志面是会被采集、滚窗、外发的，这两位在记录里出现就是 §2.9 的破口。测试因此除了断言字段
  齐全，还单独断言一次「密钥明文不在记录行里」（`executorwiring_test.go`、e2e 第 23 节各一条）。
- **`reason=-` 而不是空串**。空串在 `key=value` 形式里会塌成一个看不见的字段，而 `reason=`
  这一位的用途正是区分「这次交换没有失败码」与「没记上」。成功也留行 —— 5xx 同样是一次
  完成了的交换，记录必须在，否则「有记录」读起来像「有失败」。
- **只在日志面，不落库**。落库要新增表 = sqlite/mysql/postgres 各一遍迁移，那是存储裁决，
  已整理成 `docs/3.0-decision-packages.md` 第 4 条，接线侧不自行拍板。同理，执行记录今天
  不进 `/v1/_admin/replay/export` 那份记录文件、也不进跨进程回放 —— 决策记录里没有这一位。

拒候选那条留痕也从自由文本改成同词汇的结构化行
（`event=executor_rejected request_id=… provider=… 候选被拒不出网: …`）：与成功行共用 `event=`
词汇，「被拒」和「跑过」可以一起 grep。只看 200 数量分不出「真的没出网」与「出网了但没记录」。

第 23 节里新加的 8 条（§16.3）在两个架构上都给绿：真实进程的日志面留下了
`event=executor_exchange`，六个字段各一条，另有一条断言记录里不含上游密钥明文。

上表两行是当时手敲序列的那一遍。脚本收进仓库之后（§17.8），它自己打印的那条
`LLMPROXY_BIN=<解包件>/llmproxy bash scripts/e2e-multiuser.sh` 在两个 darwin 架构上**各自再跑
一遍**，仍是 `通过 189 项，失败 0 项`、exit 0 —— 也就是说这个复现入口现在不依赖任何 `/tmp` 里
的一次性脚本，`git clone` 之后就能重跑。

### 17.6 分类小结（失败三类分开，不混记）

| 类 | 本轮计数 | 具体 |
|---|---|---|
| 代码缺陷 | **0** | 门禁、两套 e2e、生命周期全绿 |
| 环境 / 缺外部条件 | 2 项 | 两个 linux 产物在本机 `cannot execute binary file: Exec format error`；真·跨物理机仍未做（本机只有一个文件系统、一台机器，Rosetta 换的是 ISA 不是机器） |
| 演练脚本自身口径 | **2 项，均已修** | ① `init` 模板带 `${OPENAI_API_KEY}` 占位符时直接 `start` 必然被拒，补合成密钥而非放宽校验（§17.3）；② 移植进仓库的第一版脚本漏 `export LLMPROXY_HOME`，把演练跑到了真实 `~/.config/llmproxy` 上，已复原并加了自证隔离门（§17.8） |

一条旧口径同时被校正：§15.5 记的「本机没有 Rosetta」在本轮实测中不成立（`oahd` 在跑、
`arch -x86_64` 返回 0、amd64 产物可执行），所以跨架构验证从「只有本架构」推进到
「两个 darwin 架构都跑过整套 e2e」；仍然缺的是 **Linux 上执行**与**另一台物理机**。

### 17.7 演练没覆盖到的（不伪装）

- 生命周期那一段（§17.4）走的是**示例配置的默认形态**：`policy.mode` 没配，所以它证明的是
  「发行件能起、能优雅退、能重开、观测面字段在」，不是「3.0 在发行件上跑过委托」—— 后者由
  §15 与 §16.3 那两遍第 23 节承担。
- linux 产物只到「构建 + 校验和 + 内层二进制 sha256 + `file`/`go version -m` 读头」这一层。
- 真实上游交换没在生命周期演练里发生（刻意不带真密钥），因此那一段没有 `executor_exchange`。
- mysql / postgres 两种方言的迁移与重开仍未演练（要实例，见 §1 矩阵与决策包「缺外部条件」）。

### 17.8 演练收进仓库的那一刻，它先把用户的线上配置改了

上面五节最初是在 `/tmp` 里手敲着跑的。本轮把序列固化成 `scripts/drill-release-artifact.sh`
（用法：`./scripts/build.sh` 或 `./scripts/release-check.sh` 之后 `OUT=/tmp/x ./scripts/drill-release-artifact.sh`；
末尾会打印接着跑第 23 节的那条 `LLMPROXY_BIN=…` 命令），而**移植的第一次运行是一次事故**：

- 漏了 `export LLMPROXY_HOME="$D/home"` 这一行，于是脚本里的 `init` / `config set server.port` /
  `user add drill-user` / `stats` 全部落在真实的 `~/.config/llmproxy` 上。
- 实际后果：`server.port` 从 `8787` 被写成 `57551` 那个一次性随机端口；库里多了一行
  `drill-user`（以及它那条 `scope_quota`）。没有服务在跑，所以没有中断；凭证没有被写进仓库。
- 已复原：端口改回 `8787`（与工具自动留的 `config.yaml.bak-…` 逐行 diff 后确认只差那一行）、
  `DELETE` 掉 `drill-user` 及其配额行，195 条真实请求记录一条没动。库外那份
  `llmproxy.db.pre-scope-….bak` 保留不动 —— 它是 `user add` 触发一次性 scope 迁移时产品自己
  留的备份，删它才是多事。
- 修法不是「下次记得」：脚本现在在 `mkdir` 之后立刻 `export LLMPROXY_HOME` 并**自证一次**
  （解析出的路径必须等于 `$D/home`，且不得等于 `$HOME/.config/llmproxy`，否则直接
  `DRILL_FAIL(环境)` 退出），第 0 节把「隔离出来的 home」和真实 home 一起打出来留痕。
  第三节 §17.6 的「演练脚本自身口径」计数因此从 1 项变 2 项 —— 两项都已修。

这条要写在文档里而不是悄悄修掉，理由和 §17.3 同源：演练脚本本身也是一个会犯的错的件。
它没有隔离门的时候，"在发行件上演练"这句话的真实含义是"在用户那份真实配置上演练"。
