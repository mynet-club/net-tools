# llmproxy 优化计划与技术锁定

> 文档状态：**v2.5.0 已落地阶段一/二及阶段三热点**；当前评估和下一轮优化见文末
>
> 适用版本：v2.5.0（2026-09）

## 1. 项目现状

llmproxy 是一个 Go 单二进制 LLM 转发网关。它负责下游 OpenAI 兼容协议接入、上游供应商路由、失败重试、熔断、SSE 透传、用户隔离、费用计量、SQLite 记账和网页控制台。

当前架构已经具备较完整的生产基础：

- `server` 负责鉴权、请求解析、限流、计量和 HTTP 接口；
- `router` 负责模型候选筛选、权重选择、会话粘性和熔断；
- `forwarder` 负责上游请求、响应读取、SSE 处理和 usage 提取；
- `dialer` 负责直连、HTTP CONNECT 和 SOCKS5，**用户上游带拨号层出网校验**；
- `store` 负责 SQLite 数据、用户、价格、统计和**统一金额算法**（`RowCharge`）；
- `config` 负责 YAML 配置、校验和热加载（含 `CheckResolvedIP`）；
- `secrets` 负责用户上游密钥加密；
- `logx` 负责日志和轮转。

当前验证结果（v2.5.0）：

- `go test ./...` 与 `go test -race` 通过；
- `go vet ./...` 通过；
- 阶段一（安全）与阶段二（账本）验收项已关闭，见下方实施记录。

本轮更新后的评估结论：核心安全、账本、指标、告警、主动探活和多数据库能力已经落地；剩余优先级集中在发布门禁、压测覆盖、优雅退出演练和资源缓存的一致性。此次还修复了两个低风险但真实存在的边界问题：粘性 TTL 热加载下的并发访问，以及用量报表缓存满时更新已有条目会整表清空。

变更记录与回滚流程见 [CHANGELOG.md](./CHANGELOG.md)。

## 2. 优化目标

优化工作的目标按以下顺序排列：

1. 关闭用户可控上游带来的网络安全边界缺口；
2. 保证费用、配额和历史账本口径一致；
3. 保证重启、并发写入和故障恢复行为可验证；
4. 在行为稳定后提升高并发下的内存、数据库和粘性路由性能；
5. 建立可重复的构建、测试、发布和运行观测流程。

不改变项目的产品边界：不引入支付系统、不扩展为通用多租户平台、不引入非 OpenAI 协议适配层。

## 3. 技术锁定

以下决定作为实施基线。除非出现明确的性能或安全证据，不在迭代中反复改变。

### 3.1 运行时与依赖

**锁定：继续使用 Go 标准库 + `modernc.org/sqlite` + `gopkg.in/yaml.v3`。**

- 保持 `CGO_ENABLED=0`，保证 macOS、Linux、Alpine 和交叉编译能力；
- 不引入 Redis、消息队列或外部数据库作为运行前置依赖；
- 不为指标、网络或 HTTP 客户端引入大型框架；
- 新依赖必须说明体积、跨平台和维护收益，并通过构建脚本验证。

### 3.2 数据库并发模型

**锁定：SQLite 继续作为唯一事实存储，短期不迁移数据库。**

- 数据库继续使用单实例 store；
- 所有写操作必须经过 store 层，不允许业务包直接执行 SQL；
- 写事务使用显式超时和 busy retry；
- 价格冻结、请求账本和用户状态必须在同一事务边界内完成；
- 先通过基准测试证明单连接成为瓶颈，再讨论写入队列或读写分离。

### 3.3 上游网络安全

**锁定：用户 BYO 上游采用“配置校验 + 实际拨号再校验”双层防护。**

- 配置保存时拒绝回环、私网、link-local、云元数据地址和未指定地址；
- 实际拨号时通过自定义 `net.Dialer` 对最终解析 IP 再检查一次；
- IPv4 和 IPv6 使用同一套策略；
- 系统池 provider 仍由运营者负责，用户 provider 必须经过上述限制；
- DNS rebinding 防护不能只放在 HTTP 层，必须覆盖所有出网路径，包括 `/discover`。

### 3.4 请求转发模型

**锁定：非流式和流式使用不同的资源控制模型。**

- 非流式：限制请求体、响应体和总请求时间；
- 流式：限制请求体和连续空闲时间，不设置固定总时长；
- 客户端主动断开归类为 `client_gone`，不得计为供应商失败；
- 上游响应头成功不等于请求成功，必须等 body 或 SSE 结束后再报告供应商成功；
- 所有重试必须携带明确的失败分类，禁止对 `context canceled` 盲目重试。

### 3.5 路由与会话粘性

**锁定：模型点名映射优先，通配映射只作为无点名映射时的候选。**

- 候选池先按模型声明筛选，再按用户/系统层级、健康状态和权重选择；
- 会话粘性键固定为 `(用户, 会话 ID, 下游模型)`；
- 粘性是软约束，供应商冷却、请求失败或 TTL 到期时允许漂移；
- 新会话可以按有效价目择廉，但不得因为缺少价目而把供应商当作零成本；
- 粘性状态继续只保存在内存，不写入 SQLite。

### 3.6 计量和价格

**锁定：请求开始时冻结价格，历史请求不因改价重算。**

- 上游成本按供应商、上游模型、请求开始时间和时段冻结；
- 用户分发价按用户 scope、下游模型、请求开始时间和时段冻结；
- `in_write` 缺省回落到 `in_miss`；
- 失败请求不得进入成功请求的费用摊分分母；
- CLI、管理 API、用户 API 和网页必须复用同一套 store 计算结果；
- `retain_days: 0` 明确表示永久保留请求明细和冻结账本。

### 3.7 资源上限

**锁定：所有用户可控资源都必须有显式上限。**

至少包括：

- 单请求 body 最大字节数；
- 非流式响应最大字节数；
- 单用户并发数；
- 单用户 provider 数量；
- Transport 缓存数量；
- 粘性会话数量；
- `/discover` 的频率和并发限制。

上限必须可配置，但不能通过配置为负数或异常大值绕过安全保护。

### 3.8 观测与错误分类

**锁定：以稳定错误类型和 request ID 为主要排障接口。**

错误类型至少包括：

- `client_gone`；
- `upstream_idle`；
- `upstream_body`；
- `upstream_timeout`；
- `upstream_http`；
- `upstream_unavailable`；
- `quota_exceeded`；
- `database_busy`。

日志默认不记录请求正文、响应正文、API key 或用户上游密钥。调试日志也不得绕过脱敏规则。

## 5. 代码实施约束

- 新增安全策略必须同时增加正向和反向测试；
- 新增配置项必须有默认值、样例配置、文档和热加载行为说明；
- 业务逻辑不得在 HTTP handler 中复制费用、配额或用户授权判断；
- 所有上游错误必须保留稳定的内部错误类型，再转换为 HTTP 响应；
- 不在日志中打印密钥、请求正文或完整上游错误响应；
- 修改 `internal/server/forwarder.go`、`internal/router/router.go` 或 `internal/store` 时，必须运行完整测试和至少一组基准测试；
- 任何数据库 schema 变更必须提供升级、回滚和旧版本兼容说明；
- 临时排障日志必须带有明确的删除任务，不能进入正式发布。

## 6. 推荐的首批提交拆分

建议按以下顺序拆成独立提交，便于审查和回滚：

1. `security: add final egress IP validation`
2. `server: bound upstream response and discovery resources`
3. `store: unify frozen charge calculation`
4. `store: add restart and concurrent write integration tests`
5. `router: replace affinity eviction with bounded structure`
6. `ci: add race, coverage and cross-platform release checks`

每个提交只解决一类问题，避免安全修复、账务修复和性能重构混在同一个提交中。

## v2.2.0 — 多数据库支持（建议，未开工）

> 这是对 §3.2「SQLite 唯一事实存储」的**有意放宽**，只做存储可替换，不做分布式、不做连接池中间件。

### 目标

- 同一套 `store` 行为可跑在 **SQLite / MySQL / PostgreSQL**；
- 对上层（server / CLI / UI）提供**通用数据库操作界面**：单一 `store.Store` 接口，业务包不感知方言；
- 默认仍是 SQLite（零依赖、单二进制），MySQL/PG 靠配置切换。

### 通用数据库操作界面

把 `store` 从「具体实现」收成接口 + 方言层：

```go
// store/store.go —— 业务只认这一层
type Store interface {
    // 用户 / 上游 / 模型授权
    CreateUser(name, tokenHash string) error
    ListUsers() ([]User, error)
    // …
    // 账本
    InsertRequest(rec RequestRecord) error
    UsageByUser(since time.Time, user string) ([]UsageRow, error)
    RowCharge… // 已是纯函数，不动
    // 价目
    InsertProviderPrice(p *ProviderPrice) error
    ProviderPriceAt(provider, model string, t time.Time) (*ProviderPrice, error)
    // 状态
    SaveProviderStatus(list []ProviderStatus) error
    LoadProviderStatus() ([]ProviderStatus, error)
    Close() error
}

// store/dialect.go —— 只有这里有 SQL 方言差异
type dialect interface {
    Name() string
    Placeholder(n int) string      // $1 / ?
    UpsertSQL(table string, …) string
    NowExpr() string
    Open(dsn string) (*sql.DB, error)
}
```

要求：

1. **业务包零 SQL**：凡 `db.Query/Exec` 只许出现在 `store/`；
2. **占位符与 upsert 走 dialect**，禁止在业务 SQL 里手写 `?` / `$1` / `ON CONFLICT`；
3. **事务边界不变**：价格冻结、请求账本、用户状态仍在同一事务内；
4. **连接参数**：`busy_timeout` / WAL 是 SQLite 专有，方言层吞掉；MySQL/PG 映射到 `max_conns` / `lock_timeout`。

### 配置形状

```yaml
database:
  driver: sqlite          # sqlite | mysql | postgres
  path: ""                # sqlite
  dsn: ""                 # mysql/postgres，支持 ${ENV}
  max_open_conns: 0       # 0 = 方言默认（sqlite=1）
  retain_days: 90
```

### 实施顺序（建议 4 笔）

| # | 提交 | 说明 |
|---|---|---|
| 1 | `store: extract Store interface and dialect layer` | 纯重构，行为不变，现有测试全绿 |
| 2 | `store: add mysql dialect` | 含迁移与并发写测试 |
| 3 | `store: add postgres dialect` | 同上 |
| 4 | `docs: multi-db migration and rollback` | 含 schema 对照表 |

### 风险与代价（必须正视）

| 风险 | 处理 |
|---|---|
| SQL 方言（`ON CONFLICT`、`AUTOINCREMENT`、时间类型） | 全部收口 dialect，用集成测试钉住三端同一行为 |
| SQLite 单连接假设（`SetMaxOpenConns(1)`、锁语义） | MySQL/PG 用连接池；`rowCharge`/冻结语义不随隔离级别漂 |
| schema 迁移 | v2.2 的迁移是「出 SQLite」，需每方言一份 DDL 对照；**旧库不自动搬**，提供导出/导入脚本 |
| 测试矩阵 | CI 从「1 库 × 1 OS」变「3 库」；dev 用 docker 起 mysql/pg |
| 体积与依赖 | mysql/pg 驱动是纯 Go，可接受；继续禁止 CGO |

**先决条件**：v2.1 的 race/e2e/release-check 必须先落地 —— 换存储没有回归网就是裸奔。

# llmproxy 3.0 方向推演

> **产品定位：面向复杂集团型组织的 AI 流量控制平台，以高校作为首个参考垂直场景。**

## 3.0 的核心判断

llmproxy 下一阶段不应继续沿着“再增加几个供应商适配、再增加几个管理页面”的方向扩张。到 v2.5，基础转发、故障切换、用户隔离、价格冻结、审计、告警和多数据库已经具备，继续堆功能的边际收益会快速下降。

它要服务的对象是拥有多个部门、子组织、项目、身份体系、知识域和预算主体的复杂集团型组织。高校是第一个参考垂直场景，因为它同时具备学院、职能部门、实验室、课程、科研项目、教师、学生和行政人员等复杂关系，能够充分验证平台的身份、权限、知识和隐私治理能力。

更可能的方向是：**从 LLM 转发器演进为面向复杂集团型组织、可编排的模型流量控制平面**。

它的核心价值将从“把请求送到一家上游”变成：

> 在预算、延迟、质量、隐私和可用性约束下，为每次请求选择合适的执行路径，并且能够解释、回放和持续优化这个选择。

这意味着 3.0 的中心对象不再只是 provider，而是“请求策略”和“执行结果”。

## 三个大胆推测

### 推测一：模型名称会逐渐失去意义，能力描述会成为入口

用户越来越少关心某家上游的原始模型名，而关心：

- 需要多长上下文；
- 是否支持视觉、工具调用或结构化输出；
- 期望响应速度；
- 可接受的单次成本；
- 是否允许数据离开本地或指定地域。

因此 3.0 可以把下游请求从单一 `model` 扩展为可选的策略描述，例如：

```yaml
route:
  capability: reasoning
  quality: balanced
  max_cost: 0.08
  max_latency_ms: 8000
  data_policy: private
```

网关仍然保持 OpenAI 兼容协议，但内部把能力描述解析成候选模型和 provider 集合。传统的 `model` 仍作为显式覆盖项保留。

### 推测二：最有价值的优化会从“故障切换”变成“成本和质量闭环”

当前路由主要根据可用性、权重、粘性和价格选择。3.0 可以进一步记录匿名化的结果特征：

- 首字节时间和完整响应时间；
- 输出 token 数和重试次数；
- 上游错误类型；
- 用户取消率；
- 可选的客户端质量反馈。

系统据此形成 provider/model 的运行画像，并在策略允许的范围内自动调整候选排序。自动调整必须具备上限、冻结窗口和回滚记录，不能变成不可解释的黑盒路由。

### 推测三：本地模型和远程模型会形成混合执行层

本地 Ollama、vLLM、llama.cpp 和远程 API 的接口会越来越接近。llmproxy 的优势可能不是连接更多云供应商，而是统一管理：

- 本地低成本模型处理摘要、分类、重写和缓存命中请求；
- 远程强模型处理复杂推理和长上下文；
- 敏感请求只允许进入本地或指定区域；
- 远程供应商故障时自动降级到本地模型。

这会让 `block_local_upstream` 之类的安全配置从单纯的 SSRF 开关，发展成“数据出口策略”的一部分，必须把“允许访问本机模型”和“禁止访问任意内网地址”拆成两个概念。

## 3.0 产品目标

### 目标一：策略化路由

增加一层独立的 routing policy：

- 候选条件：能力、上下文、模态、工具调用、区域、隐私级别；
- 优化目标：最低成本、最低延迟、最高可用性或加权组合；
- 约束条件：每用户预算、每模型预算、provider 配额和数据策略；
- 决策解释：返回命中的策略、排除原因、最终选择和降级原因。

验收指标：同一请求在日志和管理 API 中可以还原完整决策链；策略关闭时，旧版静态路由行为保持一致。

### 目标二：可控的自适应路由

先做规则和统计模型，不直接引入在线机器学习：

- 对每个 provider/model 保存延迟、错误率、首字节时间和成本画像；
- 使用滑动窗口和置信度门槛；
- 只有超过最小样本数才影响排序；
- 每次策略调整写入审计记录；
- 支持固定策略、半自动建议和自动策略三档。

验收指标：自动策略可以一键关闭；任何自动调整都能说明触发数据，并能回滚到上一版本。

### 目标三：统一本地与远程执行器

把 provider 抽象为 executor：

- HTTP OpenAI 兼容 executor；
- 本地 Unix socket 或 HTTP executor；
- 批处理 executor；
- 未来可扩展的异步任务 executor。

3.0 只要求同步 OpenAI 兼容和本地执行器，异步任务留出接口但不强行实现。

验收指标：本地 Ollama/vLLM 可以像普通 provider 一样参与模型列表、路由、熔断、计量和健康检查。

### 目标四：可回放的请求账本

在当前不记录正文的原则上增加可选的调试回放能力：

- 默认仍不保存请求和响应正文；
- 用户显式开启短期 debug session 后，正文加密保存并自动过期；
- 回放数据与生产账本分离；
- 管理员只能看到脱敏后的 headers、路由决策和计量信息；
- 任何正文采集都必须有范围、时间和容量上限。

验收指标：能够复现一次路由决策和错误分类，但不会默认改变现有的隐私承诺。

### 目标五：多实例但不默认依赖中心服务

3.0 可以支持多实例部署，但默认仍保持单二进制和本地 SQLite：

- stateless HTTP 层；
- 可选共享数据库；
- 粘性和限流分别声明本地模式与共享模式；
- 不把 Redis 变成默认依赖；
- 对多实例一致性给出明确的“强一致 / 最终一致 / 本地优先”说明。

验收指标：单实例升级不影响现有配置；多实例模式可以明确说明哪些功能共享、哪些功能只在本地生效。

## 3.0 技术锁定

### 保留的核心边界

- 继续使用 Go；
- 继续支持 CGO 关闭构建；
- OpenAI 兼容协议仍是默认外部接口；
- 安全、计量和审计逻辑继续在网关内闭环；
- 不把自动路由做成不可解释的黑盒；
- 不把支付、充值和财务清算纳入产品。

### 允许新增的核心抽象

```text
Request
  -> Policy Resolver
  -> Capability Matcher
  -> Candidate Planner
  -> Executor Selector
  -> Relay
  -> Usage / Cost / Quality Recorder
```

其中 `Policy Resolver` 和 `Candidate Planner` 必须是纯逻辑层，不能直接访问 HTTP、数据库或 UI。这样才能对策略进行确定性测试、回放和基准比较。

### 3.0 不建议采用的方案

- 不直接引入在线强化学习或不可解释的自动模型选择；
- 不在请求热路径调用外部 AI 服务来决定路由；
- 不把所有历史请求正文写入数据库；
- 不用 Redis 掩盖本地状态和一致性设计问题；
- 不为了兼容供应商而复制一套大型 SDK 生态。

## 3.0 版本拆分建议

### 3.0-alpha：策略内核

- routing policy 数据结构；
- 能力标签和模型能力声明；
- 决策解释对象；
- 静态策略的单元测试和回放测试；
- 兼容现有 provider 路由。

### 3.0-beta：质量与本地执行

- provider/model 运行画像；
- 规则化自适应排序；
- Ollama/vLLM 等本地执行器；
- 数据出口策略；
- 本地与远程混合路由。

### 3.0：控制平面

- 管理台策略编辑和模拟运行；
- 路由决策解释与审计；
- 短期加密回放；
- 多实例部署模式；
- 兼容性、性能和灾备文档。

## 3.0 的成功标准

3.0 发布时，用户应该能回答以下问题：

1. 这次请求为什么选择了这个模型和 provider？
2. 如果成本、延迟或隐私约束改变，系统会怎么选？
3. 这次失败是供应商问题、网络问题、客户端取消还是策略拒绝？
4. 本地模型和远程模型如何协同，哪些数据可以出网？
5. 自动策略调整是否可解释、可暂停、可回滚？
6. 多实例部署时，计量、限流、粘性和审计分别保证什么一致性？

如果这些问题无法在管理 API、日志和文档中得到明确答案，说明系统仍然只是功能更多的转发器，还没有成为真正的模型流量控制平面。

## 3.0 特别讨论：智能路由、隐私路由与企业自定义处理

这三项能力可以共同组成企业版的核心，但需要保持清晰的边界：

- **智能路由**决定请求应该走哪条执行路径；
- **隐私路由**决定哪些数据允许进入哪条路径；
- **企业自定义处理**决定请求在进入模型前后需要经过哪些组织内部规则。

三者不能合并成一个任意脚本系统。路由必须可解释，隐私策略必须先于出网，自定义工具必须被限制在受控扩展点中。

### 一、智能路由：从“选供应商”变成“选执行计划”

智能路由的输入不应只包含模型名，还可以包含：

- 请求类型：对话、补全、Embedding、重排序、工具调用；
- 能力要求：视觉、结构化输出、长上下文、推理、JSON schema、函数调用；
- 运行约束：最大延迟、最大成本、最大重试次数；
- 数据约束：本地、指定区域、允许云端、禁止训练；
- 用户和组织上下文：部门、项目、租户、预算、时间段；
- 历史状态：provider 健康度、缓存命中率、近期错误率和延迟。

路由输出不应只是 provider 名称，而应是一个可审计的执行计划：

```json
{
  "executor": "local-vllm",
  "model": "qwen3-32b",
  "fallback": ["private-cloud-1"],
  "retries": 1,
  "reason": ["data_policy=private", "latency<3000ms", "within_budget"],
  "policy_version": "finance-default-v3"
}
```

智能路由需要支持三种模式：

1. **确定性模式**：只按显式规则执行，适合财务、医疗和生产核心链路；
2. **建议模式**：系统给出推荐路径，但由管理员确认后生效；
3. **自适应模式**：在明确约束内根据运行数据调整排序。

默认应使用确定性模式。自适应模式必须具备最小样本量、调整幅度上限、冷却时间、审计记录和一键回滚。

### 二、隐私路由：先做数据分类，再做模型选择

隐私路由不能只依靠用户填写的标签。建议采用“声明 + 检测 + 强制策略”三层结构。

#### 1. 数据策略声明

企业可以为用户、项目、API key 或路径配置数据等级：

```yaml
privacy:
  policy: confidential
  allowed_regions: [cn]
  allow_public_cloud: false
  allow_prompt_logging: false
  redact_before_upstream: true
```

#### 2. 数据检测

网关可以提供轻量级、可插拔的检测器：

- 个人身份信息；
- 手机号、邮箱、身份证号、银行卡号；
- 企业内部项目名和客户编号；
- 代码仓库、数据库连接串、密钥格式；
- 组织自定义正则和词典。

检测结果只用于策略决策时，默认不写入原文。检测器应返回类型、置信度和命中范围摘要。

#### 3. 强制策略

检测到敏感数据后，可以执行：

- 只允许本地模型；
- 只允许指定区域或指定企业私有云；
- 出网前脱敏；
- 禁止请求并返回可解释错误；
- 进入人工审批或隔离队列。

隐私策略必须先于 provider 选择执行。任何“先发给模型再决定是否允许”的设计都不应进入 3.0。

### 三、企业自定义工具：支持处理链，但不开放任意执行

企业确实可能需要自定义处理，例如：

- 请求进入模型前，从内部知识库补充上下文；
- 对合同、票据或工单做脱敏；
- 根据部门和项目注入系统提示词；
- 对模型输出执行格式校验、敏感词过滤和字段落库；
- 将审计事件写入企业内部系统；
- 把模型调用接入内部审批、检索或缓存服务。

这类需求建议抽象成**受控处理器（processor）**，而不是配置一段 JavaScript、Shell 或任意 HTTP 转发脚本。

推荐的处理链：

```text
Request
  -> Authenticate
  -> Classify
  -> PreProcessor
  -> Privacy Policy
  -> Route Plan
  -> Executor
  -> PostProcessor
  -> Meter / Audit
  -> Response
```

处理器只允许挂在固定阶段，并声明自己的输入输出能力：

```yaml
processors:
  - name: redact-finance-fields
    type: builtin-redactor
    phase: before-route
    scope: finance
    fail_closed: true
    timeout_ms: 100

  - name: add-internal-context
    type: http-enricher
    phase: before-upstream
    endpoint: https://rag.corp.example/context
    timeout_ms: 500
    max_response_bytes: 65536
    fail_closed: false

  - name: validate-json-output
    type: json-schema
    phase: after-upstream
    schema: invoice-result-v2
    on_failure: reject
```

### 四、企业工具扩展必须锁定的边界

#### 允许的扩展方式

- 内置处理器：脱敏、字段替换、JSON schema、请求头注入、结果过滤；
- 外部 HTTP 处理器：通过明确的超时、响应大小和出网策略调用；
- 独立 sidecar：企业自己部署，llmproxy 只通过稳定协议调用；
- 编译期插件：由企业维护自己的构建产物，适合强隔离和高性能场景。

#### 不建议允许的方式

- 在配置文件中执行任意 Shell；
- 在请求热路径运行任意用户上传的脚本；
- 允许处理器直接访问 SQLite 文件、主密钥或其它用户的 provider；
- 允许处理器绕过隐私策略直接创建新的出网连接；
- 让处理器修改最终计量、费用或审计结果；
- 让一个租户注册全局处理器影响其他租户。

#### 每个处理器必须具备的属性

- 明确阶段：`before-route`、`before-upstream`、`after-upstream` 或 `audit`；
- 明确作用域：全局、组织、项目、用户或 API key；
- 超时和最大输入输出大小；
- 失败策略：`fail_closed` 或 `fail_open`；
- 是否允许读取正文；
- 是否允许出网，以及允许的目标列表；
- 版本号、配置摘要和审计记录；
- 幂等性说明，避免重试造成重复写入或重复扣费。

### 五、企业定制场景的推荐落地形态

建议把企业能力分成三个层级：

| 层级 | 适用对象 | 形态 |
|---|---|---|
| 基础策略 | 所有部署 | YAML/管理 API 定义路由和隐私规则 |
| 受控处理器 | 大多数企业 | 内置处理器和 HTTP sidecar |
| 私有发行版 | 强定制企业 | 独立编译插件或企业维护分支 |

这样可以让普通用户继续使用单二进制和简单配置，同时为企业保留深度定制空间。企业特殊逻辑不会污染默认安装，也不会迫使核心项目支持每一家企业的内部系统。

### 六、这项需求的产品判断

企业自定义处理是值得进入 3.0 的能力，但它的产品名不应是“自定义脚本”，而应是“策略与处理器扩展”。这个命名会直接约束实现方向：

- 策略负责决定能不能做、应该走哪里；
- 处理器负责做有限、可审计的数据变换；
- 执行器负责调用模型；
- 账本负责记录结果；
- 企业系统通过 sidecar 或稳定接口接入。

这样既能支持企业的特殊数据处理需求，也能保住 llmproxy 的安全边界、可解释性和单二进制基础。

## 复杂集团型组织参考场景：高校优先试点

高校是 llmproxy 3.0 的首个参考垂直场景。它同时具备多类身份、复杂知识权限、模型使用差异、预算管理和较高的隐私要求，能够检验网关是否真正具备集团型组织的策略控制能力。高校验证通过后，同一套核心模型可以映射到企业集团、医疗集团、政务机构和大型研究机构。

高校与企业集团的对象映射保持一致：

| 通用对象 | 高校示例 | 企业集团示例 |
|---|---|---|
| Tenant | 某大学 | 集团公司 |
| Department | 学院、图书馆 | 财务部、研发中心、子公司 |
| Team / Project | 课程、实验室、科研课题 | 项目组、业务线、客户项目 |
| Identity | 教师、学生、行政人员 | 员工、管理者、合作方 |
| KnowledgeScope | 课程资料、制度库、科研文档 | 产品库、制度库、客户资料 |
| BudgetScope | 学校、学院、课题组 | 集团、子公司、部门 |

因此高校章节验证的是通用能力，不定义高校专属的数据模型。

### 场景边界

目标不是建设校园门户，而是提供统一的 AI 模型访问层：

```text
教师 / 学生 / 管理员 / 研究团队
              │
              ▼
       高校身份认证系统
       OIDC / SAML / LDAP
              │
              ▼
       llmproxy 统一入口
              │
   ┌──────────┼──────────┐
   ▼          ▼          ▼
模型权限    知识权限    隐私策略
              │
              ▼
       智能路由与处理链
              │
   ┌──────────┼──────────┐
   ▼          ▼          ▼
校内模型    校内知识库   合规云模型
```

网关负责统一身份、策略判断、模型路由、知识库访问控制、计量和审计。学校原有身份系统、教务系统、科研系统、知识库和财务系统继续作为权威数据源。

### 身份与角色

高校不能只使用一个简单的 `user` 角色。权限至少需要组合身份、组织、项目、认证级别和使用目的：

| 维度 | 示例 | 用途 |
|---|---|---|
| 身份 | 教师、学生、管理员、访客 | 基础模型权限和默认隐私策略 |
| 组织 | 计算机学院、图书馆、实验室 | 继承组织级策略、预算和知识库权限 |
| 项目 | 课题组、课程、科研项目 | 项目级模型、知识库和费用隔离 |
| 认证级别 | 普通登录、强认证、设备可信 | 决定能否访问敏感模型和数据 |
| 使用目的 | 教学、科研、行政、个人学习 | 计量、审计和数据出口策略 |

权限计算采用以下优先级：

```text
effective_policy = deny > explicit_allow > group_allow > default
```

明确拒绝优先于继承授权。角色、组织和项目的合并结果必须产生可解释的决策记录。

身份接入优先支持 OIDC，并兼容 SAML 2.0、LDAP 和可信反向代理。外部身份映射到稳定的学校用户 ID，不能以姓名或邮箱作为主键。角色和组织声明必须带来源、更新时间和过期时间；用户离校、毕业、停用或项目结束后，权限在约定 TTL 内失效。网关消费学校身份系统的结果，不自行创建学校身份。

### 模型权限

模型权限应从“是否能调用”扩展到“在什么约束下调用”：

| 用户群 | 默认能力 | 典型限制 |
|---|---|---|
| 学生 | 普通对话、基础代码、校内知识库 | 低并发、月度额度、禁止敏感数据出网 |
| 教师 | 高级模型、课程知识库、教学工具 | 按学院或课程计量 |
| 科研团队 | 推理模型、批处理、本地模型 | 项目预算、项目数据隔离 |
| 管理员 | 管理和审计接口 | 不默认获得用户正文权限 |
| 访客 | 受限公共模型 | 禁止访问校内知识库 |

模型权限需要支持按角色、组织、项目和用途授权，单独限制流式、工具调用、视觉、长上下文和并发。还要区分“可以看到模型”和“可以实际调用模型”。模型目录应返回权限过滤后的结果，避免暴露学校不希望公开的模型。

### 知识库权限

知识库应采用“检索委托”模式，而不是把它当作没有权限的公共 RAG 服务：

1. 网关根据当前用户生成带身份和项目上下文的检索请求；
2. 学校知识库或 RAG 服务自行执行文档 ACL；
3. 知识库只返回当前用户可见的片段和引用；
4. 网关将结果注入模型前记录知识源摘要；
5. 未授权的文档 ID、标题和内容不得进入响应或日志。

知识库接口至少需要接收 `subject`、`groups`、`project`、`purpose`、`query`、`max_chunks` 和 `data_policy`。网关只记录知识库名称、检索策略版本、返回片段数量和引用摘要哈希，默认不记录完整文档正文。

如果知识库无法执行 ACL，网关不应根据客户端传来的文档标签自行推断权限。该知识库只能标记为“无权限保证”，禁止用于高敏感场景。

### 高校隐私分级

建议预置四级数据策略：

| 等级 | 示例 | 允许路径 |
|---|---|---|
| public | 公开课程资料、公开论文 | 校内或合规云模型 |
| internal | 未公开教学材料、一般行政信息 | 校内模型、指定私有云 |
| confidential | 学生成绩、科研未发表数据 | 校内或项目专属模型 |
| restricted | 身份证、医疗、处分、密钥 | 默认拒绝模型处理，需专门审批 |

最终数据级别取用户策略、检测策略和知识库策略中的最高等级：

```text
effective_data_policy = max(user_policy, detected_content_policy, knowledge_policy)
```

检测器可识别个人身份信息、学生数据、科研项目标识、密钥和学校自定义词典。检测结果默认只保留类型、置信度和范围摘要，不保存原文。

### 高校智能路由

学生询问公开课程内容时，可以选择成本较低的合规云模型；教师处理未公开课程资料时，路由到校内模型；科研团队处理受限项目数据时，只允许项目专属执行器。

一次决策应能够还原：用户、组织、项目、用途、数据等级、候选列表、排除原因、最终执行器、降级路径和策略版本。例如：

```json
{
  "subject": "university:2026001234",
  "purpose": "research",
  "policy": "research-confidential-v2",
  "data_level": "confidential",
  "candidates": [
    {"name": "public-cloud", "rejected": "data_policy"},
    {"name": "campus-vllm", "selected": true},
    {"name": "lab-private-model", "rejected": "project_scope"}
  ],
  "reason": ["project_scope=lab-nlp", "data_level=confidential", "campus_only"]
}
```

故障切换不能绕过模型权限和隐私策略。校内模型不可用时，系统必须根据策略拒绝或降级，不能静默把数据外发。

### 推荐部署形态

```text
校园统一入口
      │
      ▼
边界区 llmproxy
      │
      ├── 身份系统
      ├── 策略 / 审计服务
      └── 校内 llmproxy 执行节点
                    │
                    ├── 校内模型
                    ├── 校内知识库
                    └── 受控云模型出口
```

小型学校可以单实例部署。大型学校应将身份与策略入口和模型执行节点分开，避免知识库、模型和管理接口全部暴露在同一网络边界。

### 高校试点验收

3.0 高校试点至少应验证：

- OIDC 登录后，教师、学生、科研组得到不同模型目录；
- 用户转组、毕业或停用后，权限在约定 TTL 内收敛；
- 同一问题引用不同权限知识库时，检索结果严格隔离；
- 敏感数据不会被路由到禁止的云 provider；
- 模型故障切换不会绕过模型权限和隐私策略；
- 管理员可以看到决策原因、费用和审计事件，但默认不能看到用户正文；
- 学院、课程和科研项目可以分别统计用量和费用；
- 所有策略变更可追踪、可回滚。

高校试点会把以下对象提升为 3.0 的一等对象：`Identity`、`Entitlement`、`DataPolicy`、`KnowledgeScope`、`RoutingPlan`、`Processor`、`BudgetScope` 和 `AuditEvent`。这些对象同时适用于高校、企业集团、医疗集团、政务机构和大型研究机构。

高校试点的最终目标，是验证 llmproxy 能否成为复杂集团型组织的 AI 统一控制层，而不是把 llmproxy 固定成高校专用系统。
