# llmproxy 优化计划与技术锁定

> 文档状态：**v2.0.0 已落地阶段一/二及阶段三热点**；阶段四（发布流程）与剩余性能项见文末
>
> 适用版本：v2.0.0（2026-09）

## 1. 项目现状

llmproxy 是一个 Go 单二进制 LLM 转发网关。它负责下游 OpenAI 兼容协议接入、上游供应商路由、失败重试、熔断、SSE 透传、用户隔离、费用计量、SQLite 记账和网页控制台。

当前架构已经具备较完整的生产基础：

- `server` 负责鉴权、请求解析、限流、计量和 HTTP 接口；
- `router` 负责模型候选筛选、权重选择、会话粘性和熔断；
- `forwarder` 负责上游请求、响应读取、SSE 处理和 usage 提取；
- `dialer` 负责直连、HTTP CONNECT 和 SOCKS5，**用户上游带拨号层出网校验**；
- `store` 负责 SQLite 数据、用户、价格、统计和**统一金额算法**（`RowCharge`）；
- `config` 负责 YAML 配置、校验和热加载（含 `CheckResolvedIP`）；
- `secrets` 负责用户上游密钥加密；
- `logx` 负责日志和轮转。

当前验证结果（v2.0.0）：

- `go test ./...` 与 `go test -race` 通过；
- `go vet ./...` 通过；
- 阶段一（安全）与阶段二（账本）验收项已关闭，见下方实施记录。

变更记录与回滚流程见 [CHANGELOG.md](./CHANGELOG.md)。

## 2. 优化目标

优化工作的目标按以下顺序排列：

1. 关闭用户可控上游带来的网络安全边界缺口；
2. 保证费用、配额和历史账本口径一致；
3. 保证重启、并发写入和故障恢复行为可验证；
4. 在行为稳定后提升高并发下的内存、数据库和粘性路由性能；
5. 建立可重复的构建、测试、发布和运行观测流程。

不改变项目的产品边界：不引入支付系统、不扩展为通用多租户平台、不引入非 OpenAI 协议适配层。

## 3. 技术锁定

以下决定作为实施基线。除非出现明确的性能或安全证据，不在迭代中反复改变。

### 3.1 运行时与依赖

**锁定：继续使用 Go 标准库 + `modernc.org/sqlite` + `gopkg.in/yaml.v3`。**

- 保持 `CGO_ENABLED=0`，保证 macOS、Linux、Alpine 和交叉编译能力；
- 不引入 Redis、消息队列或外部数据库作为运行前置依赖；
- 不为指标、网络或 HTTP 客户端引入大型框架；
- 新依赖必须说明体积、跨平台和维护收益，并通过构建脚本验证。

### 3.2 数据库并发模型

**锁定：SQLite 继续作为唯一事实存储，短期不迁移数据库。**

- 数据库继续使用单实例 store；
- 所有写操作必须经过 store 层，不允许业务包直接执行 SQL；
- 写事务使用显式超时和 busy retry；
- 价格冻结、请求账本和用户状态必须在同一事务边界内完成；
- 先通过基准测试证明单连接成为瓶颈，再讨论写入队列或读写分离。

### 3.3 上游网络安全

**锁定：用户 BYO 上游采用“配置校验 + 实际拨号再校验”双层防护。**

- 配置保存时拒绝回环、私网、link-local、云元数据地址和未指定地址；
- 实际拨号时通过自定义 `net.Dialer` 对最终解析 IP 再检查一次；
- IPv4 和 IPv6 使用同一套策略；
- 系统池 provider 仍由运营者负责，用户 provider 必须经过上述限制；
- DNS rebinding 防护不能只放在 HTTP 层，必须覆盖所有出网路径，包括 `/discover`。

### 3.4 请求转发模型

**锁定：非流式和流式使用不同的资源控制模型。**

- 非流式：限制请求体、响应体和总请求时间；
- 流式：限制请求体和连续空闲时间，不设置固定总时长；
- 客户端主动断开归类为 `client_gone`，不得计为供应商失败；
- 上游响应头成功不等于请求成功，必须等 body 或 SSE 结束后再报告供应商成功；
- 所有重试必须携带明确的失败分类，禁止对 `context canceled` 盲目重试。

### 3.5 路由与会话粘性

**锁定：模型点名映射优先，通配映射只作为无点名映射时的候选。**

- 候选池先按模型声明筛选，再按用户/系统层级、健康状态和权重选择；
- 会话粘性键固定为 `(用户, 会话 ID, 下游模型)`；
- 粘性是软约束，供应商冷却、请求失败或 TTL 到期时允许漂移；
- 新会话可以按有效价目择廉，但不得因为缺少价目而把供应商当作零成本；
- 粘性状态继续只保存在内存，不写入 SQLite。

### 3.6 计量和价格

**锁定：请求开始时冻结价格，历史请求不因改价重算。**

- 上游成本按供应商、上游模型、请求开始时间和时段冻结；
- 用户分发价按用户 scope、下游模型、请求开始时间和时段冻结；
- `in_write` 缺省回落到 `in_miss`；
- 失败请求不得进入成功请求的费用摊分分母；
- CLI、管理 API、用户 API 和网页必须复用同一套 store 计算结果；
- `retain_days: 0` 明确表示永久保留请求明细和冻结账本。

### 3.7 资源上限

**锁定：所有用户可控资源都必须有显式上限。**

至少包括：

- 单请求 body 最大字节数；
- 非流式响应最大字节数；
- 单用户并发数；
- 单用户 provider 数量；
- Transport 缓存数量；
- 粘性会话数量；
- `/discover` 的频率和并发限制。

上限必须可配置，但不能通过配置为负数或异常大值绕过安全保护。

### 3.8 观测与错误分类

**锁定：以稳定错误类型和 request ID 为主要排障接口。**

错误类型至少包括：

- `client_gone`；
- `upstream_idle`；
- `upstream_body`；
- `upstream_timeout`；
- `upstream_http`；
- `upstream_unavailable`；
- `quota_exceeded`；
- `database_busy`。

日志默认不记录请求正文、响应正文、API key 或用户上游密钥。调试日志也不得绕过脱敏规则。

## 5. 代码实施约束

- 新增安全策略必须同时增加正向和反向测试；
- 新增配置项必须有默认值、样例配置、文档和热加载行为说明；
- 业务逻辑不得在 HTTP handler 中复制费用、配额或用户授权判断；
- 所有上游错误必须保留稳定的内部错误类型，再转换为 HTTP 响应；
- 不在日志中打印密钥、请求正文或完整上游错误响应；
- 修改 `internal/server/forwarder.go`、`internal/router/router.go` 或 `internal/store` 时，必须运行完整测试和至少一组基准测试；
- 任何数据库 schema 变更必须提供升级、回滚和旧版本兼容说明；
- 临时排障日志必须带有明确的删除任务，不能进入正式发布。

## 6. 推荐的首批提交拆分

建议按以下顺序拆成独立提交，便于审查和回滚：

1. `security: add final egress IP validation`
2. `server: bound upstream response and discovery resources`
3. `store: unify frozen charge calculation`
4. `store: add restart and concurrent write integration tests`
5. `router: replace affinity eviction with bounded structure`
6. `ci: add race, coverage and cross-platform release checks`

每个提交只解决一类问题，避免安全修复、账务修复和性能重构混在同一个提交中。

## 7. 暂不实施的事项

以下事项暂不列入近期优化：

- 迁移到 PostgreSQL、Redis 或消息队列；
- 支付、充值、发票和完整多租户运营；
- 非 OpenAI 协议的原生适配；
- 自动汇率换算；
- 复杂时区和法定节假日价格计算；
- 为追求抽象而引入大型 Web 或网络框架。

这些变化会扩大产品边界或运行复杂度，必须在出现明确业务需求和容量证据后单独立项。
