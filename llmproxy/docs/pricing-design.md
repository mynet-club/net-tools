# llmproxy 计价与成本模型（设计定稿）

状态：**设计已定，尚未实现**。实施按 B1→B4 走（见文末）。
来源：用户提出四点需求（计价是多维函数 / 记录历史计价 / 消费单元冻结计价 / 分上游与分发两层价），
随后拍板：价格修改必须**整点生效**、消费单元与跨点规则按本文件执行、B1 两张表一起建、历史不回填。

## 1. 目标与边界

目标：

- **路由择廉**（规则 B）：新会话 / 漂移时按当前上游成本从低到高选供应商
- **成本可审计**：每一笔消耗都能查到"当时用了哪一档价、算了多少钱"
- **报价与成本分离**：向用户收多少，与上游收我们多少，是两件独立的事

明确不做：扣款、余额、预付款、对账、发票 —— 那是支付系统的活。这里的金额是**计量**，不是清算。

## 2. 两层价格

```
cost  = f_upstream(供应商, 上游模型, 价格档, 时间点, …)   ← 我们付给上游的钱
price = f_downstream(用户, 下游模型, 价格档, 时间点, …)  ← 我们向用户收的钱
毛利  = price − cost
```

| 层 | 数据源 | 驱动什么 |
|---|---|---|
| 上游价（cost） | `provider_prices` | 规则 B 的路由排序、真实成本报表、"系统付费"部分的记账 |
| 分发价（price） | `user_prices` | 向用户计费、配额消耗的金额口径 |

**路由只看上游价；计费只看分发价。** 两层独立维护，互不影响。

**系统付费 vs 用户自付**：只有走系统上游（`system_paid=1`）的消耗才谈得上分发计价；
BYO 用户自带上游的消耗，网关不掏钱也不向他收钱，记账只为留痕（对网关成本 = 0）。

## 3. 计价函数的维度

| 维度 | 层 | 说明 |
|---|---|---|
| **供应商** | 上游 | 现有 `pricing` 表**没有**这个维度 —— 同名模型各家价格不同，这是引入它的首要原因 |
| **上游模型名** | 上游 | 按上游真实名字计价，不用下游别名（避免串价） |
| **缓存三档** | 两层 | `in_hit` / `in_miss` / **`in_write`** —— 写入有溢价（Anthropic 系约 1.25×；neolink 实测报 `cache_write_tokens`） |
| 时间段 | 两层 | 价目行自带峰谷规则：`peak_hours` + `off_peak_ratio` + **`peak_tz`**（固定偏移，如 `+08:00`）；按**请求开始时刻**判档 |
| **折扣** | 两层 | **不单独建模**：价格行直接记**有效价** + `note` 写明来源（"含 XX 折扣"/"促销至 X 日"） |
| 货币 | 两层 | 多供应商后可能混币种；聚合前换算到基准币 |
| 系统付费标记 | 分发 | 决定这笔消耗算不算用户的钱 |

时段（峰谷）的两条限制，都是有意的取舍：

- **只认周一~周五，不识别中国法定节假日**：节假日会按高峰价算，偏高估（不会低估）。
  要更准就在价目行里直接填均价。
- **`peak_tz` 只支持固定偏移**：表达不了 PST/EDT 这类带夏令时的时区。
  固定偏移不依赖系统 tzdata（Alpine/musl 精简镜像里常缺，`LoadLocation` 会失败），
  而国内供应商本来就固定 +8 —— 真遇到带夏令时的再加，不提前建。

可后加（现在不做）：推理 token 单独计价、长上下文溢价（>200k）、批处理/优先级档、按分组的折扣。

**为什么折扣不建模**：折扣来源太杂（商务谈判、促销、返点、阶梯），模型化只会造出没人用的字段。
账要对得上只需要"生效价 + 什么时候生效"，折扣原因留在 `note` 给人看。
路由侧本来就只关心有效价。

## 4. 消费单元与记账

两个粒度，不要压成一个：

| | 粒度 | 用途 |
|---|---|---|
| **记录单元（账本）** | **每请求** | 一行一请求，冻结当时的有效价与金额 |
| **报表单元（切片）** | **用户 × 小时** | 按请求的**开始时刻**归入小时桶 |

账本不按小时存的理由：小时聚合会丢掉"这一笔是谁、哪个模型、走哪家上游、跑多久、成没成功"，
而这些是排障与对账都要的。请求量级（一天几百条）让明细存储毫无压力。
**请求行是事实，小时聚合是推导视图。**

`requests` 表新增列：

```
price_upstream_id    本次计价用的上游价目行 id（回溯用）
cost_upstream        冻结的上游成本（含币种口径）
price_downstream_id  本次计价用的分发价目行 id
charge               冻结的向用户计费金额（system_paid=0 时为 0）
currency             金额币种
```

请求落库时按**当时有效价**算好写进去。此后 `usage_user_daily` 的金额 = SUM(冻结值)，
**不再实时查价**；配额口径（`limits.go` 的 meters）也改读冻结金额，与账单口径同源。

金额冻结保证账不变；id 保留回溯能力 —— 价目后来改了，仍能查出当时用的是哪一档。

## 5. 价格生效与跨点规则

**约定：价格修改必须整点生效。** 由此：

1. **价目行的 `valid_from` 强制整点** —— 校验时**拒绝**非整点的值，不静默取整。
   静默取整会在"我以为立即生效"的场景里造成意外（配 01:30 生效、系统悄悄变 01:00，账就对不上）。
2. **查价公式**：`hour = Truncate(请求开始时刻, 整点)`，取 `valid_from ≤ hour` 的最后一条有效价。
3. **小时桶同样按请求开始时刻归档** —— "某用户某小时的消耗" = 该小时内开始的所有请求的冻结金额之和，
   与价目生效边界天然对齐。

**跨点请求（开始在上一小时、结束在下一小时）：整单按请求开始时刻的价。**

```
价目表   ├─ 旧价（≤ 01:00）─┤── 新价（≥ 01:00）──┤
请求           [— start 00:55 ————— end 01:35 —]
计价             全程按 00:55 所在小时的旧价
```

四条理由：

1. **可实现性（最硬）**：上游只在响应结束时给一份 `usage` 快照，**没有 token 时间线**。
   要把输出 token 按生成时刻切进两个小时，只能按请求时长摊分 —— 那是估计，不是计量。不做假账。
2. **可审计**：一个请求 → 一个价 → 一个金额，与整点生效的价目表一一对应，没有摊分系数可吵。
3. **符合消费直觉**：输入 token 在发起那一刻就被消费了；输出 token 的口径本来就是"这次请求的输出"。
4. **影响面小**：绝大多数请求远短于一小时；仅当新旧价不同才产生误差，上限就是那点价差。

**代价（明确接受）**：23:59 发起、跑 40 分钟的请求，全程按旧价结算，哪怕新价已在 00:00 生效。
这是这条规则的必然结果，文档写明即可。若将来确实要"跨点切价"，唯一不造假的做法是要求上游
按小时返回分段 usage（没有供应商这么做）；按时长摊分的版本**不做**。

可选字段 `跨价段`（开始与结束落在不同小时 = true）：只供分析长请求的量与金额，**不参与计算**。
**当前决定：暂不实现。**

## 6. 数据模型

### 6.1 `provider_prices`（上游价，带历史）

```
id                 主键
provider           系统供应商名
upstream_model     上游真实模型名
currency           币种（CNY / USD …）
in_miss            每百万 token：未命中缓存的输入
in_hit             每百万 token：命中缓存的输入
in_write           每百万 token：写入缓存的输入（可空 = 与 in_miss 同价）
out                每百万 token：输出
reasoning_out      每百万 token：推理输出（可空 = 与 out 同价）
per_request_fee    每请求固定费（可空）
peak_hours         该价目行的高峰时段（可空 = 沿用全局）
off_peak_ratio     空闲时段系数（可空 = 沿用全局）
peak_tz            时段按哪个时区判，**固定偏移**（如 "+08:00"；可空 = 沿用全局）
valid_from         生效起点，**必须是整点**（校验拒绝非整点）
valid_to           失效终点，整点；空 = 一直有效
note               备注（折扣来源、依据的官网报价链接等）
created_at
```

查询：
- **路由用（当前价）**：`valid_from ≤ now.Truncate(hour)` 且（`valid_to` 为空或 `> now`）的最后一条
- **记账用（某时刻价）**：同上，但用 `Truncate(请求开始时刻)`

拿到价目行之后还要取一次**峰谷档**：按同一时刻、用该行的 `peak_hours`/`off_peak_ratio`/`peak_tz`
（空字段逐项回落全局）算出系数，乘在 token 部分上。**不乘 `per_request_fee`** ——
每请求固定费是接入费，与用量无关，也不随峰谷浮动。

### 6.2 `user_prices`（分发价，带历史）

```
id                 主键
scope              "default"（全局默认）| "user:<用户名>"（单用户覆盖）
model              下游模型名（客户端填的那个）
currency
in_hit / in_miss / in_write / out   同上
peak_hours / off_peak_ratio / peak_tz   同上（两层价格的费率形状一致）
valid_from / valid_to                同上，valid_from 强制整点
note
created_at
```

取价规则：**最具体的那条生效**（`user:<名>` > `default`）。
按分组的折扣第二步再说，当前不建分组维度。

### 6.3 折扣的表达

不建折扣字段。改价时**插入一条新价目行**（旧行填 `valid_to`），`note` 写明原因。
历史行因此天然保留，报表按 id 回溯即可。

## 7. 迁移

- **不回填**：切换前的请求行没有冻结金额，报表里标成"估算段"；只有切换后的新请求冻结。
  回填等于用当前价伪造历史，违背"记录历史计价"的初衷。
- 报表里**区分"估算段"与"冻结段"**，不要把两种口径的数字混在同一个合计里。
- 现有 `pricing` 配置与 `PricingConfig` 在 B2 之后**退役**为"估算兜底"（仅在没有价目行可用时使用），
  README 中"用当前单价而非历史价"一段将被推翻并改写。

## 8. 实施顺序

| 步骤 | 内容 | 满足 |
|---|---|---|
| **B1** | 两张价格表的存储结构 + 整点校验 + 按小时查价 + 单测（不接记账、不接路由） | 数据层 |
| **B2** | 请求落库时冻结**上游价**；成本报表改读冻结值；估算段/冻结段分开 | 记录历史计价、单元冻结（上游侧） |
| **B3** | 分发价接进计费与配额（口径与账单同源） | 分发计价 |
| **B4** | 规则 B 路由：新会话 / 漂移时按当前上游价从低到高试，跳过冷却与近期额度不足的；402/429 记短期冷却并降级 | 最初的目的 |

B4 依赖 B1 的价格数据与已上线的会话粘性（漂移机制是"额度不足降级"的挂点）。

## 9. 与现有系统的差异（一句话版）

现在：全局一张 `pricing`、只按模型名、无供应商维度、无历史、**读取时用当前价现算**。
目标：按供应商×模型的带历史价目、请求落库时冻结、两层价分离、整点生效。
